# 03-平台契约（platform-contract）

能力 ID：`platform-contract`
覆盖：Aether 平台 API 契约层——Connect-native proto（唯一真相源）、三层服务模型（Server/Admin/Internal）、域目录 × srv/dto/enum 文件组织、错误码注册表、状态机/适配器/walking-skeleton fixture。为 `iac-self-service-platform` Wave 1-8 业务实现提供不可误解的接口契约。

## ADDED Requirements

### Requirement: Connect-native 契约单一真相源（D1）
平台 SHALL 以 `contracts/platform/v1/**/*.proto` 为 API 契约的唯一真相源。proto 经 `buf generate` 产出 Go message 类型与 Connect service 接口（handler + client），单个 http.Server 通过 Connect-RPC 原生覆盖 gRPC / gRPC-Web / Connect-JSON 三协议。平台 SHALL NOT 手写 `openapi.yaml` / `schemas/*.schema.json` / `protocol-mapping.md` 作为契约源。

#### Scenario: 前端/CLI 通过 Connect-JSON 调用
- **WHEN** Web 前端或 CLI 以 Connect-JSON 协议调用任一 RPC
- **THEN** 同一 handler 无需额外适配即可服务，响应类型由 proto 生成的 Go struct 序列化

#### Scenario: 改接口只改一处
- **WHEN** 任一 RPC 的请求/响应字段需要变更
- **THEN** 只修改对应域的 `dto.proto`，`buf generate` 重新产出 Go 类型；不存在需要同步修改的 openapi/schema/mapping 文件

#### Scenario: 无手写契约漂移
- **WHEN** 检查 `contracts/` 目录
- **THEN** 不存在 `openapi.yaml`、`protocol-mapping.md`、`schemas/` 目录（如未来需 REST 文档，用 `protoc-gen-openapi` 从 proto 自动生成，不手维护）

### Requirement: 三层服务模型（Server / Admin / Internal）
每个 proto service SHALL 归入且仅归入三层之一。Server 层（用户：浏览/申请/审批）走 OIDC JWT + RBAC，经 Connect `/api/` 暴露；Admin 层（操作员：注册/发布/配置）走 OIDC JWT + admin 角色，经 Connect `/api/` 暴露，拦截器按 service 名前缀鉴权；Internal 层（codegen/executor/CMDB/drift）为进程内函数调用，SHALL NOT 有 proto service。

#### Scenario: 用户调用 Server 层
- **WHEN** 终端用户调用 `LifecycleService.CreateRequest` 或 `CatalogService.ListItems`
- **THEN** Connect 拦截器校验 OIDC JWT + RBAC 角色后放行

#### Scenario: 管理员调用 Admin 层
- **WHEN** 管理员调用 `RegistryAdminService.RegisterModule` 或 `CatalogAdminService.PublishCatalogItem`
- **THEN** Connect 拦截器按 procedure 名前缀（`/aether.platform.v1.RegistryAdmin*` 或 `/aether.platform.v1.CatalogAdmin*`）要求 admin 角色，非 admin 返回 `PERMISSION_DENIED`

#### Scenario: Internal 操作无 proto
- **WHEN** 平台执行 codegen / executor / CMDB ingest / drift scan
- **THEN** 这些操作是同进程函数调用（D39），不暴露 RPC，不出现在任何 `srv.proto`

### Requirement: 域目录 × srv/dto/enum 文件组织（5 域）
proto SHALL 按业务域分目录（`common/` / `lifecycle/` / `catalog/` / `registry/` / `cloud/`）。每个域内 `srv.proto` 只含 `service` 定义（不含 message）；`dto.proto` 含该域全部 message（领域对象 + RPC 请求/响应）；跨域共享枚举集中在 `common/enum.proto`，共享 message 在 `common/dto.proto`。**模块注册（registry）与服务目录（catalog）是独立域**：registry 管 Module/ModuleVersion 的注册与版本，catalog 管 CatalogItem 的发布与浏览，CatalogItem 跨域引用 registry.ModuleVersion。

#### Scenario: srv.proto 可作纯接口清单审查
- **WHEN** 审查者打开任一域的 `srv.proto`
- **THEN** 文件只含 `service` + `rpc` 定义，无 `message`，可作为该域接口清单通读

#### Scenario: registry 与 catalog 分域
- **WHEN** 审查者检查 `contracts/platform/v1/registry/` 与 `contracts/platform/v1/catalog/`
- **THEN** registry 域含 RegistryAdminService + Module/ModuleVersion/ModuleDependency；catalog 域含 CatalogService + CatalogAdminService + CatalogItem（不含 Module*）；catalog/dto.proto `import registry/dto.proto`

#### Scenario: 域划分与 capability 对齐
- **WHEN** 对照父提案 `iac-self-service-platform` 的 capability 列表
- **THEN** proto 域与 capability 一一对应：registry = module-registry（specs/01）、catalog = service-catalog（specs/02），不存在一个 proto 域横跨两个 capability

#### Scenario: 跨域枚举集中
- **WHEN** 新增一个被多个域使用的枚举（如新的 `RequestStatus` 值）
- **THEN** 该枚举定义在 `common/enum.proto`，各域 `dto.proto` 通过 `import` 引用，不在域内重复定义

### Requirement: MVP 全链路 RPC 覆盖（6 service / 24 RPC）
契约 SHALL 覆盖 MVP 主链路的 6 service / 24 RPC，无断点：`LifecycleService`（12 RPC：CreateRequest/GetRequest/ListRequests/ListRequestEvents/CancelRequest/StartPlan/GetArtifact/EvaluateGate/ListPendingApprovals/GetApprovalRun/DecideApproval/StartApply）、`CatalogService`（4 RPC）、`CatalogAdminService`（3 RPC）、`RegistryAdminService`（4 RPC）、`EntitlementService`（1 RPC）。

#### Scenario: 用户可列出工单
- **WHEN** 用户调用 `LifecycleService.ListRequests`（带 requester_id 或 team_id 过滤）
- **THEN** 返回该用户/团队的工单列表 + 分页 token，CLI `tm request list` 可直接对接

#### Scenario: 审批人可取待办队列
- **WHEN** 审批人调用 `LifecycleService.ListPendingApprovals`（带 approver_id）
- **THEN** 平台按 approver_id → role_bindings 解析，返回当前节点路由给该审批人的 pending ApprovalRun 列表，CLI `tm approval list` 可直接对接

#### Scenario: 审批人可查看审批详情含节点链
- **WHEN** 审批人调用 `LifecycleService.GetApprovalRun`（带 run_id）
- **THEN** 返回 ApprovalRun + 节点链（ApprovalNodeRun[]，含会签进度 decided_count/required_count）+ 决策历史（ApprovalDecisionRecord[]），支撑审批工作台渲染

#### Scenario: 管理员链路完整
- **WHEN** 管理员注册模块并发布为目录项
- **THEN** `RegistryAdminService.RegisterModule`（registry 域）+ `CatalogAdminService.PublishCatalogItem`（catalog 域）覆盖，发布后用户经 `CatalogService.ListItems` 可见

#### Scenario: 用户主链路完整无断点
- **WHEN** 用户从申请走到 apply 成功
- **THEN** 链路 `GetCatalogItem → CreateRequest → StartPlan → GetArtifact → EvaluateGate → [ListPendingApprovals → GetApprovalRun → DecideApproval] → StartApply → GetRequest(=succeeded)` 每步都有对应 RPC，审批人侧无断点

### Requirement: proto3 枚举命名规范
所有 proto 枚举值 SHALL 带类型前缀（proto3 规范），如 `REQUEST_STATUS_SUBMITTED`、`CLOUD_PROVIDER_AWS`、`APPROVAL_GATE_PRE_PLAN`。每个枚举的零值 SHALL 为 `<TYPE>_UNSPECIFIED`。

#### Scenario: 枚举前缀通过 buf lint
- **WHEN** 执行 `buf lint`
- **THEN** 所有枚举值符合 proto3 前缀规范，lint 零告警

#### Scenario: 零值为 UNSPECIFIED
- **WHEN** 检查任一枚举（如 `RequestStatus`、`CloudProvider`、`ApprovalGate`）
- **THEN** 零值字段是 `<TYPE>_UNSPECIFIED`，业务值从 1 开始

### Requirement: ApprovalRun 字段完整（双门禁 + 会签进度）
`ApprovalRun` message SHALL 包含双门禁与会签进度所需的完整字段：`run_id` / `status` / `decided_by` / `decided_at` / `request_id` / `gate`（ApprovalGate 枚举：pre-plan/pre-apply，D21 双门禁）/ `current_node` / `started_at` / `finished_at` / `expires_at`。审批详情通过 `ApprovalNodeRun`（节点链）+ `ApprovalDecisionRecord`（决策历史）补充。

#### Scenario: 双门禁可区分
- **WHEN** 审批人查看一个 ApprovalRun
- **THEN** `gate` 字段明确标识是 pre-plan（准入）还是 pre-apply（执行确认），审批人知当前在审的是哪道门

#### Scenario: 会签进度可视化
- **WHEN** 审批人查看 GetApprovalRunResponse
- **THEN** `nodes` 数组含每个节点的 decided_count/required_count/status，会签进度（如 1/2 已签）可见

#### Scenario: 审批可关联到 request
- **WHEN** 审批人从 ApprovalRun 跳回 request 详情
- **THEN** `request_id` 字段提供跳转入口

### Requirement: LifecycleRequest 申请人可追溯
`LifecycleRequest` message SHALL 含 `requester_id`（提交者 identity）与 `current_stage`（当前管道阶段），支撑"我的工单"查询与 UI 阶段提示。

#### Scenario: 我的工单可按申请人过滤
- **WHEN** 用户调用 ListRequests 带 requester_id 过滤
- **THEN** 只返回该 requester_id 提交的工单

#### Scenario: UI 显示当前阶段
- **WHEN** 前端渲染工单详情
- **THEN** `current_stage` 提供粗粒度阶段提示（如 "codegen"/"plan"/"apply"），权威状态仍是 status + version

### Requirement: 审批节点链与决策历史 message
契约 SHALL 提供 `ApprovalNodeRun`（node_id/mode/decided_count/required_count/status/timeout_at）与 `ApprovalDecisionRecord`（approver_id/decision/comment/decided_at）两个 message，用于 `GetApprovalRunResponse` 渲染会签节点链与决策审计轨迹。对应 docs/04 §2.10 approval_node_runs / approval_decisions 表。

#### Scenario: 节点链渲染
- **WHEN** GetApprovalRunResponse 返回 nodes 数组
- **THEN** 每个节点含 mode（single/countersign/conditional）+ 进度计数 + status，前端可渲染完整审批流节点链

### Requirement: 审批相关共享枚举
`common/enum.proto` SHALL 提供 `ApprovalGate`（UNSPECIFIED/PRE_PLAN/PRE_APPLY）、`ApprovalNodeMode`（UNSPECIFIED/SINGLE/COUNTERSIGN/CONDITIONAL）、`ApprovalNodeStatus`（UNSPECIFIED/PENDING/APPROVED/REJECTED/SKIPPED/TIMEOUT）三个枚举，命名遵循 proto3 类型前缀规范。

#### Scenario: 枚举通过 buf lint
- **WHEN** 执行 buf lint
- **THEN** 三个枚举值均带类型前缀（APPROVAL_GATE_*、APPROVAL_NODE_MODE_*、APPROVAL_NODE_STATUS_*），lint 零告警

### Requirement: 错误码注册表（唯一错误行为真相源）
平台 SHALL 在 `contracts/error-codes.yaml` 维护错误码注册表，每个错误码含 `code` / `http_status` / `grpc_code` / `retryable` / `manual_required` / `remediation` / `owner` 七字段。proto 无法表达 remediation/owner/retryable，故用 YAML 补充——YAML 是错误**行为**（重试策略、人工介入、自救指引、owner）的唯一真相源，proto 是错误**形状**（RPC/字段）的唯一真相源。Phase 0 覆盖 20 个错误码。

**消费机制（Wave 1 实现）**：平台 SHALL 在进程启动时将 `error-codes.yaml` 加载为内存注册表单例（运行时加载，非 codegen），handler 返回错误时 SHALL 通过注册表查码（`errors.New(registry, CODE)`），由注册表包装成带 `ErrorInfo` detail 的 Connect 错误（含 code 作 reason、retryable/manual_required/owner 作 metadata）。handler MUST NOT 硬编码 HTTP status / gRPC code / 错误字符串——这些只能来自注册表。改错误行为只改 YAML（重启生效），不重编代码。

#### Scenario: 错误码字段完整
- **WHEN** 审查 `error-codes.yaml` 任一错误码条目
- **THEN** 七字段齐全，`retryable` 与 `grpc_code` 一致（如 `UNAVAILABLE` → retryable=true，`INVALID_ARGUMENT` → retryable=false）

#### Scenario: handler 通过注册表返回结构化错误
- **WHEN** handler 需返回错误（如乐观锁冲突）
- **THEN** 调用 `errors.New(registry, STATE_CONFLICT)`；注册表查 YAML 得 http=409/grpc=ABORTED/retryable=true，包装成 Connect Error（code=ABORTED）+ ErrorInfo detail（reason=STATE_CONFLICT, metadata 含 retryable/owner）；handler 不直接写 `connect.NewError(connect.CodeAborted, ...)`

#### Scenario: 客户端可机器消费错误行为
- **WHEN** 前端/CLI 收到带 ErrorInfo 的 Connect 错误
- **THEN** 按 reason 识别错误类型，按 metadata.retryable 决定自动重试，按 metadata.manual_required 决定提示"需联系运维"，按 remediation 显示自救指引

#### Scenario: 错误码不得硬编码
- **WHEN** 代码审查任一 handler 的错误返回路径
- **THEN** 不出现裸的 `connect.NewError(connect.CodeXxx, errors.New("..."))` 硬编码错误码/状态/文案；所有错误行为源自注册表

### Requirement: 状态机 fixture 可执行
平台 SHALL 在 `contracts/fixtures/state-machine/main-lifecycle.json` 维护请求生命周期状态机的可执行 fixture，覆盖 RLC（主链路）/ ERR（异常）/ IDEMP（幂等）/ CONC（并发）/ EXPR（过期）五类共 17 个用例。每个用例含 `case_id` / `initial_status` / `event_type` / `guards` / `expected_status` / `expected_events` / `expected_outbox` / `idempotency`。

#### Scenario: 主链路状态迁移可测试
- **WHEN** Wave 1+ 实现 lifecycle service 的状态迁移逻辑
- **THEN** RLC-001~008 fixture 驱动表测试，验证 submitted → generating → ... → succeeded 的完整迁移

#### Scenario: 幂等重放安全
- **WHEN** 同一事件（如重复审批）被重放
- **THEN** IDEMP-001/002 fixture 验证返回已有结果而非重复副作用

### Requirement: TerramateAdapter golden case
平台 SHALL 在 `contracts/fixtures/adapter/terramate-adapter.json` 维护 TerramateAdapter 的 4 个 golden case（ADAPTER-001~004：RunPlan / RunApplySavedPlan / RunDriftPlan / RunImportVerify），每个 case 含 `expected_argv` / `expected_env` / `expected_outputs` / `forbidden`。`forbidden` SHALL 明确禁止 Orchestrator 绕过 TerramateAdapter 直接调用 terraform/tofu。

#### Scenario: plan 产出 artifact
- **WHEN** Adapter 执行 RunPlan（ADAPTER-001）
- **THEN** expected_argv 含 `terraform plan -out=plan.tfplan`，产出 plan_binary artifact，hash 可校验

#### Scenario: apply 用 saved plan 不重 plan
- **WHEN** Adapter 执行 RunApplySavedPlan（ADAPTER-002）
- **THEN** expected_argv 含 `terraform apply "plan.tfplan"`，不重新 plan，hash 校验前置

#### Scenario: 禁止绕过 Terramate
- **WHEN** 审查任一 adapter case 的 `forbidden` 字段
- **THEN** 明确列出 Orchestrator 不得直接调用的命令（裸 terraform/tofu），强制经 TerramateAdapter

### Requirement: Walking skeleton seed 数据
平台 SHALL 在 `contracts/fixtures/walking-skeleton/seed-data.json` 维护 walking skeleton 的完整 seed（tenant/env/team/bundle/catalog/module/cloud grant/toolchain/approval/plan artifact）+ 8 步 golden path（Request → Codegen → Plan → Approval → Apply → Reconcile → Query）。

#### Scenario: 一条 golden path 串起全链路
- **WHEN** Wave 5 主干闭环验证时加载 seed-data.json
- **THEN** seed 覆盖从申请到 reconcile 的全部依赖，golden path 8 步可顺序执行无缺失前置数据
