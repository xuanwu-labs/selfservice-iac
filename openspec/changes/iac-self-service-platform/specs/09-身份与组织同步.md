# 11-身份与组织同步（identity-sync）

能力 ID：`identity-sync`
覆盖：企业身份认证（OIDC/SSO）、组织/人员数据同步（SCIM + 飞书/钉钉）、组织 → 平台团队/角色映射。

## ADDED Requirements

### Requirement: OIDC 单点登录（多 issuer 并存 + dex 可选，D10.1）
平台 SHALL 作为 OIDC 服务提供者（SP），**同时信任多个 OIDC issuer**——每个 issuer 一个独立 Verifier，认证源列表存 DB 可配（Web 改、热加载）。[dex](https://github.com/dexidp/dex) 为**可选**桥接适配器（用于 SAML/LDAP/AD 等非 OIDC 源），企业自建 OIDC OP **MUST 支持直接对接不经 dex**。平台 MUST NOT 直接认证 LDAP/AD/CAS（非 OIDC 协议一律经代理或 dex 转 OIDC）。

#### Scenario: 企业自建 OIDC OP 直连（不经 dex）
- **WHEN** 企业已部署 Keycloak/Authing/自研 OIDC OP
- **THEN** 平台在 `oidc_providers` 配 `{name, issuer, client_id, client_secret, claim_mapping}`，用户登录直接 redirect 到企业 OP，**不部署 dex**；平台验证 OP 签发的 JWT → claim_mapping 归一化 → 建 session

#### Scenario: 多 OIDC issuer 并存（集团联邦）
- **WHEN** 集团下 A 公司用 Okta + B 公司用自建 OP + C 公司用 Azure AD
- **THEN** 平台配 3 个 `oidc_providers`，登录页显示 3 个按钮；用户点各自 OP → 平台按 token `iss` 路由到对应 Verifier → 验签成功

#### Scenario: CAS 通过 OIDC 代理接入
- **WHEN** 企业使用 CAS 统一身份认证
- **THEN** 部署 cas-oidc-proxy（CAS ticket → OIDC JWT），平台配 proxy 为 OIDC issuer；**平台代码零改动**，CAS 认证流程由 proxy 处理

#### Scenario: LDAP/AD 经 dex 桥接
- **WHEN** 企业仅有 LDAP/AD（无 OIDC OP）
- **THEN** 部署 dex，dex 后端连 LDAP；平台配 dex 为 OIDC issuer；平台侧只见 OIDC

#### Scenario: 不同 OP 的 claim 字段映射
- **WHEN** Azure AD 的用户名字段是 `upn`，Keycloak 是 `preferred_username`，飞书是 `user_id`
- **THEN** 每个 `oidc_provider` 配 `claim_mapping`，平台内部统一用 `{sub, email, name, groups}` 模型；不同 OP 的 token 经 mapping 归一化后处理一致

### Requirement: 组织数据多源同步
平台 SHALL 定义 `DirectorySyncer` 抽象，提供至少三类实现：SCIM 2.0（国际标准）、飞书开放平台、钉钉开放平台；每个源 MUST 支持增量（事件/webhook 订阅）+ 定时全量拉取双通道。

#### Scenario: 飞书组织增量同步
- **WHEN** 飞书通讯录发生人员/部门变更（如新增 DBA 组成员）
- **THEN** 平台通过飞书事件订阅收到变更，秒级更新本地组织数据；无需等定时拉取

#### Scenario: SCIM 自动同步
- **WHEN** 企业 IDP 通过 SCIM 2.0 推送用户/组变更
- **THEN** 平台 SCIM 端点接收并落库，标准 `/Users`、`/Groups` 资源

### Requirement: 组织到平台归属映射
平台 SHALL 把同步来的组织树映射为平台实体：组织部门 → 团队/项目组，IDP 组 → 平台角色（如"DBA 审批组" → `dba-approver` 角色），映射规则 MUST 可由管理员配置且可审计。

#### Scenario: 部门变团队
- **WHEN** IDP 同步来"数据/DBA"部门
- **THEN** 平台按映射规则创建/更新平台团队 `DBA`，成员自动同步

#### Scenario: 组变角色
- **WHEN** 用户在 IDP 加入"RDS-审批组"
- **THEN** 平台授予该用户 `dba-approver` 角色，无需平台内手工授权

### Requirement: 多源去重与一致性
当多个身份源启用时，平台 SHALL 按可信主源（配置的优先级）去重同一自然人，MUST 标记冲突并告警，避免重复身份。

#### Scenario: 飞书与 SCIM 同时启用
- **WHEN** 同一用户在飞书与 SCIM 都存在
- **THEN** 平台按主源优先级合并为单一身份，记录次要源，不产生重复账号

### Requirement: 同步健康与可观测
平台 SHALL 暴露每个身份源的同步状态（最近成功时间、失败计数、滞后），失败 MUST 触发告警并在平台界面可见。

#### Scenario: 飞书源连续失败
- **WHEN** 飞书同步连续 3 次失败
- **THEN** 平台标记该源 `degraded`，通知管理员，界面显示红点与失败原因
