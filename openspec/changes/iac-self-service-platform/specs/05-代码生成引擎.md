# 05-代码生成引擎（code-generation）

能力 ID：`code-generation`
覆盖：表单 → Terramate stack + Terraform 代码的核心生成引擎；**参数解析 9 阶段管道（详见 specs/18，原「四输入合并」的演化）** + 优先级仲裁；**cardinality 调用方注入（模块零侵入）**；强制注入（tag/state key）；跨层依赖注入；PathGenerator 路径渲染；确定性与幂等。对应 design `D3/D19/D24/D25/D28`、`docs/09-代码生成机制`。

## ADDED Requirements

### Requirement: 模块零侵入（最高约束）
平台 MUST NOT 要求原子 Terraform 模块作者按平台规范修改模块——模块 SHALL 保持标准单实例语义（`variables.tf` 全 scalar、`main.tf` 单实例 resource、`outputs.tf` scalar 输出）。社区模块（terraform-aws-modules / 官方 alicloud / 任意标准 Terraform module）MUST 直接复用零适配。多实例配置（cardinality 等）属于 catalog 项平台元数据，MUST NOT 写入模块仓库或污染 `modules.variables_contract_json`。

#### Scenario: 社区模块直接复用
- **WHEN** 注册 `github.com/terraform-aws-modules/terraform-aws-ecs`（社区模块，未做任何平台适配）
- **THEN** 平台直接拉取解析提取 scalar 契约，catalog 项可声明 cardinality=list/map 让 codegen 在调用方注入 for_each，**模块仓库 0 字节改动**

#### Scenario: cardinality 不污染模块契约
- **WHEN** catalog 项声明 cardinality=map
- **THEN** `modules.variables_contract_json` 只存从 variables.tf 提取的 scalar 契约；cardinality/instance_key/per_instance_fields/shared_fields 存 `catalog_items` 表（平台层），模块 commit hash 与 cardinality 配置正交

### Requirement: 代码生成
平台 SHALL 基于表单输入 + 模块契约 + 最佳实践默认值，生成 Terramate stack 目录与 Terraform 代码（模块引用 + 变量赋值 + backend 配置 + 跨层 data 引用），生成的代码 MUST 通过 `terraform fmt`。**stack 目录路径与 state key 由 PathGenerator 渲染**（specs/04 D24），codegen MUST NOT 字符串拼接路径。

#### Scenario: 生成 stack 与调用模块
- **WHEN** 流水线进入 `generating` 阶段
- **THEN** 平台调用 PathGenerator 按 D29 layer-first Path Contract 渲染路径（如 `application/platform-default/team-a/ecs-prod`），在工作仓库中创建该目录，含 `stack.tm.hcl`、`main.tf`（`module "ecs" { source = ...; instance_type=... }`）、`backend.tf`（state key = PathGenerator 输出）

### Requirement: 代码生成机制（9 阶段参数解析管道 + 强制注入）
平台 codegen SHALL 按 9 阶段管道解析参数（详见 specs/18）：S1 模块契约载入 / S2 catalog defaults / S3 layer rule 注入 / S4 环境上下文绑定（D27）/ S5 tenant 上下文绑定（D27）/ S6 team 策略 / S7 跨层依赖注入 / S8 用户表单 / S9 平台强制注入。最终优先级 MUST 为「S9 平台强制 > S3 layer rule > S6 team 策略 > S8 用户表单 > S5 tenant > S4 env ≈ S7 依赖 > S2 catalog 默认 > S1 契约默认」（治理类 > 用户类 > 上下文类 > catalog 默认 > 契约兜底）。平台强制注入项（L1 platform tags、state key）MUST NOT 被任何来源覆盖。cardinality 配置来自 catalog 项（D25），不来自模块契约。

#### Scenario: 用户表单覆盖默认
- **WHEN** catalog defaults (S2) 指定 storage=100（rank 7），用户表单 (S8) 填 storage=200（rank 4）
- **THEN** 生成代码 storage=200（用户 rank > catalog 默认），resolved_params_json.storage.source=user_form，overridden_from.catalog_default=100

#### Scenario: 强制 tag 不可绕过
- **WHEN** 用户表单 (S8) 尝试传 tags 字段含 platform-managed=false
- **THEN** 平台 S9 强制注入 L1 platform tags（platform-managed=true, platform-team/bundle/stack），覆盖用户值；resolved_params_json.tags.user_overrides_blocked MUST 含 "platform-managed"

#### Scenario: layer rule 覆盖用户值（治理类 > 用户类）
- **WHEN** layer rule (S3) 强制 encrypt_at_rest=true（rank 2），用户表单 (S8) 填 false（rank 4）
- **THEN** 最终 encrypt_at_rest=true，resolved_params_json.encrypt_at_rest.user_attempted_override=true, user_attempted_value=false（治理违规留痕）

#### Scenario: env 上下文自动注入 vpc_id
- **WHEN** 用户不传 vpc_id，env=prod + tenant=corp-a + layer=Application 存在 environment_tenant_bindings 记录（D27）
- **THEN** S4 自动注入 vpc_id（rank 6），resolved_params_json.vpc_id.source=env_context

#### Scenario: 敏感字段隔离
- **WHEN** 模块契约变量 db_password 标 sensitive=true
- **THEN** 生成代码用占位符（如 `__TM_SECRET_rds-password__`），不进 git 明文，运行期由 Executor 从 secret store 注入

#### Scenario: provenance 完整写入
- **WHEN** codegen 完成 generating 阶段
- **THEN** requests.resolved_params_json MUST 含每个变量的 {value, source, rank}，详见 specs/18「Provenance 审计」

### Requirement: cardinality 调用方注入（模块零侵入的多实例）
多实例 SHALL 由 **catalog 项**声明的 `cardinality: single|list|map` 驱动（非模块契约），codegen 在**生成的调用方**注入 TF 原生 `for_each`/`count`——`single`=直接 module 调用、`list`=`count = N`（同质）、`map`=`for_each = tomap({...})`（异构，key=角色名）。per_instance 字段从 `each.value` 取，shared 字段直接注入。MUST NOT 用 wrapper module 包装，MUST NOT 改模块内部。同一模块可被不同 catalog 项以不同 cardinality 调用。

#### Scenario: cardinality=single（默认）
- **WHEN** catalog 项声明 cardinality=single
- **THEN** codegen 生成普通 `module "rds" { source=...; instance_type=... }`（无 for_each），模块 variables.tf 全 scalar

#### Scenario: cardinality=list（同质多实例）
- **WHEN** catalog 项声明 cardinality=list, instance_key=name，表单提供 3 个同规格实例
- **THEN** codegen 生成 `count = 3` 或 `for_each = toset(["i1","i2","i3"])`，per_instance 字段从 each.value 取，shared 字段直接注入；模块零感知

#### Scenario: cardinality=map（异构多实例）
- **WHEN** catalog 项声明 cardinality=map, instance_key=role，表单提供 web/API/batch 三角色不同规格
- **THEN** codegen 生成 `for_each = tomap({ web={spec="c6.large",...}, api={spec="c6.xlarge",...}, batch={spec="r6.2xlarge",...} })`，per_instance 字段从 each.value 取，shared 字段直接注入；模块零感知，**不拆 3 个 stack**

#### Scenario: 同模块不同 cardinality
- **WHEN** 同一 ECS 模块被 catalog 项 A（cardinality=single）和 catalog 项 B（cardinality=map）引用
- **THEN** 两 catalog 项各自配置 cardinality，模块仓库不变，codegen 按各 catalog 项的 cardinality 分别生成调用语法

### Requirement: 跨层依赖注入
平台 codegen SHALL 依据依赖图自动注入跨层 data 引用（`terraform_remote_state` 或云 data source）与变量绑定，MUST NOT 让用户手写跨层引用。

#### Scenario: 自动注入 remote_state
- **WHEN** stack `ecs-prod` 依赖 `vpc-global-prod`
- **THEN** codegen 在 ecs-prod 生成 `data.terraform_remote_state.vpc` 并把 `vswitch_id` 绑到 module 变量，用户无需手写

### Requirement: stack.tm.hcl 生成（Terramate 元数据，D29）
平台 codegen SHALL 为每个生成的 stack 目录生成 `stack.tm.hcl` 文件，包含 `id`（全局唯一，PathGenerator 输出）、`name`、`tags`（layer/tenant/env/team）、`after`（跨层依赖序）、`watch`（上游 stack outputs 变更触发）。此元数据使 Terramate 能做栈发现、依赖排序、标签过滤和变更传播。MUST NOT 依赖 `terramate generate` 生成此文件——由平台 codegen 直接产出。

#### Scenario: 生成含 tags 和 after 的 stack.tm.hcl
- **WHEN** codegen 为 `application/corp-a/team-b/ecs-dev` 生成 stack，依赖 `global/vpc-corp-a-dev`
- **THEN** 生成 `stack.tm.hcl` 含 `id = "app-corp-a-team-b-ecs-dev"`、`tags = ["layer:application","tenant:corp-a","env:dev","team:team-b"]`、`after = ["../../../global/vpc-corp-a-dev"]`、`watch = ["../../../global/vpc-corp-a-dev/outputs.tf"]`

#### Scenario: tags 驱动 Terramate 租户隔离执行
- **WHEN** 平台为租户 corp-a 的 dev 环境工单执行 `terramate run --tags "tenant:corp-a,env:dev" -- terraform plan`
- **THEN** Terramate 只发现 corp-a+dev 的 stack（tags 过滤），其他租户/环境的 stack 不受影响

### Requirement: 确定性与幂等
同一工单重跑 generating 阶段 SHALL 产出相同目录路径与文件内容（确定性），git diff 为空或仅预期变更；生成路径 MUST 由元数据确定性推导（对应 docs/02 路径规则）。

#### Scenario: 重跑产出一致
- **WHEN** 同一工单因中断重跑 generating
- **THEN** 生成的 stack 目录路径与文件内容与首次一致，git 无意外 diff

### Requirement: 代码生成与编排解耦
代码生成引擎 SHALL 作为独立能力（`code-generation`）被编排引擎（`orchestration-engine`，specs/06）在 `generating` 阶段调用；codegen 自身 MUST NOT 调用 Terramate 或感知工单状态机，仅做"输入 → 代码产物"的纯转换。

#### Scenario: codegen 纯转换
- **WHEN** 编排引擎在 generating 阶段调用 codegen
- **THEN** codegen 接收 9 阶段管道输入返回代码产物（目录树 + 文件），不执行 plan/apply、不写工单状态
