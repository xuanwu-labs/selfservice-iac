# 13-工具链版本管理（toolchain-versioning）

能力 ID：`toolchain-versioning`
覆盖：terramate / terraform(opentofu) / provider 三层版本锁定与多版本共存、worker 镜像管理、版本与 stack 兼容校验、**执行隔离与可插拔执行运行时（Executor 三模式，D13/D20）**。

## ADDED Requirements

### Requirement: Terramate 版本平台锁定
平台 SHALL 全局锁定 terramate 版本，同时多版本共存；`TerramateAdapter` 调用 exec 时 MUST 按配置选择版本；版本升级 MUST 灰度（先非生产环境）。

#### Scenario: 灰度升级 terramate
- **WHEN** 管理员把 terramate 从 v0.17.1 升到 v0.18.0
- **THEN** 平台先在 dev/staging 环境生效，prod 保持旧版本，灰度通过后再全量切换

### Requirement: Terraform/OpenTofu 多版本（tenv）
平台 SHALL 用 [tenv](https://github.com/tofuutils/tenv) 管理 terraform/opentofu 多版本；每个 stack 的 `required_version` MUST 决定实际执行版本；平台 MUST 能并存 terraform 1.5（存量 import 兼容）与 1.9（新特性）。

#### Scenario: 存量 stack 用旧版 TF
- **WHEN** 某 stack `required_version = ">= 1.5"`
- **THEN** 平台用 tenv 解析出 1.5.x 执行；与新建 stack 用 1.9.x 并存

### Requirement: Provider 锁定与私有 registry mirror
平台 SHALL 用 `.terraform.lock.hcl` 锁定 provider 版本；企业私有/定制 provider MUST 通过 registry mirror（自建 Terraform Registry 兼容服务或 network mirror）分发，禁止直连公网 registry 作为生产依赖。

#### Scenario: 私有 provider 走 mirror
- **WHEN** stack 引用企业私有 provider `corp/custom`
- **THEN** terraform init 从自建 registry mirror 拉取，不访问公网 registry

### Requirement: Worker 镜像固化工具链
平台 SHALL 把 terramate + terraform/tofu + provider 缓存 + OPA + Infracost 打包进 worker 镜像（对应 design D12/D13）；镜像版本 MUST 与三层工具链版本对齐，通过 CI 构建。

#### Scenario: 工具链升级 = 新镜像
- **WHEN** terraform 升级到 1.9
- **THEN** CI 构建新 worker 镜像 `tm-worker:full-tf1.9`，灰度后生效；旧镜像保留回滚

### Requirement: 版本兼容校验（三时机）
平台 SHALL 在三个时机校验工具链兼容性：①模块注册时——提取 `required_version`/provider 约束，校验存在满足它的工具链 profile；②catalog 发布时——目录项声明目标工具链 profile（terramate + tf/tofu + providers 版本组合）；③**执行前**（orchestrator 调 Executor 前）—— `validateCompatibility(stack, sandbox)`：sandbox 是镜像（解 tag/manifest 取版本）或预装节点（取 `toolchain_manifest`），用 semver 匹配 `stack.required_version` + provider 存在性 + terramate 版本，不兼容 MUST 阻断并给可操作提示。

#### Scenario: stack 要求 TF>=1.7 但镜像只有 1.5
- **WHEN** 工单的 stack `required_version >= 1.7`，被调度到 `tm-worker:legacy-1.5`
- **THEN** 平台执行前校验失败，阻断并提示"需切换到 tf1.9 镜像"

#### Scenario: process 模式 provider 缺失
- **WHEN** process 模式节点未预装 stack 所需的 `corp/custom` provider
- **THEN** 校验读节点 `toolchain_manifest` 发现缺失，阻断并提示"节点需装 provider corp/custom"

### Requirement: 节点工具链安装（自动优先 + 手动兜底）
process 模式下，平台 SHALL 提供 `installer` 按平台 Web 设的工具链基线（D15 存 DB）自动 reconcile 节点：从 mirror/制品仓下载 → checksum 校验 → 装到 `/opt/tm/toolchains/<ver>/` + symlink active + 写 `toolchain_manifest`；离线/air-gap 场景 SHALL 支持手动投放二进制到约定目录，installer 仅注册不下载。节点 `toolchain_manifest` MUST 作为版本校验与可见性的真相源。

#### Scenario: 自动安装 reconcile 到基线
- **WHEN** 管理员在 Web 把工具链基线 terraform 升到 1.9（mode=process）
- **THEN** installer 自动下载校验安装到各执行节点并更新 manifest，无需人工

#### Scenario: 离线手动投放
- **WHEN** air-gap 环境无制品仓可达
- **THEN** admin 把二进制投放约定目录，installer 注册进 manifest（不下载），版本校验正常工作

### Requirement: Worker 镜像构建（BuildDriver 可插拔）
container 类模式下，`ImageBuilder` SHALL 通过可插拔 `BuildDriver` 构建镜像（`docker`=本地/构建节点 docker daemon；`buildah`=daemonless 进程；`kaniko`=K8s 内无 daemon 构建），MUST NOT 强制宿主有 docker daemon；构建 MUST 由 Web 保存版本组合触发（pin 全部版本到 Dockerfile）→ tag → push 可插拔 `ImageRegistry` → 灰度。process 模式 MUST NOT 触发镜像构建。

#### Scenario: K8s 模式用 kaniko 无 daemon 构建
- **WHEN** mode=kubernetes 且无 docker daemon
- **THEN** ImageBuilder 用 kaniko BuildDriver 在 K8s 内构建镜像并 push，无需宿主 docker

#### Scenario: buildah daemonless 进程构建
- **WHEN** mode=container 但宿主不愿跑 docker daemon
- **THEN** ImageBuilder 用 buildah BuildDriver 以进程方式构建，tag，push 到 registry

### Requirement: 执行隔离（每工单独立沙箱）
平台 SHALL 在独立沙箱内执行每个工单的 plan/apply（worker 镜像或预装工具链 + 挂载该工单的 git worktree），提供工单级 CPU/内存/磁盘/网络隔离；MUST NOT 在平台进程内直接执行 terraform/terramate（隔离弱、爆炸半径大）。

#### Scenario: 工单级隔离
- **WHEN** 两个工单并发执行
- **THEN** 各自运行在独立沙箱（进程+目录 / 容器 / Pod / 远程），worktree、资源、网络互不污染；一个工单故障 MUST NOT 影响另一个

### Requirement: 可插拔执行运行时（Executor 四模式，K8s 与镜像仓库均非必需）
平台 SHALL 定义 `Executor` 接口抽象沙箱执行，提供 **process / container / kubernetes / remote** 四种可插拔实现；编排引擎（specs/06）与漂移检测（specs/07）MUST 通过该接口调用，MUST NOT 硬编码任何运行时；**K8s 与镜像仓库 MUST NOT 是必需依赖**——process 模式为零基础设施默认（节点预装工具链，无容器/镜像/仓库）。模式选择存 `adapters_config`（DB，D15），Web 可切换、热加载、审计。

#### Scenario: process 模式零容器零仓库
- **WHEN** 小团队 / 开发 / 内网环境配置 `executor.mode=process`
- **THEN** 平台在执行节点用预装工具链 + worktree 目录 + 子进程 + cgroups 执行，无需容器/镜像/镜像仓库/K8s

#### Scenario: container 模式本地镜像
- **WHEN** 配置 `executor.mode=container`，宿主机有 docker/podman + worker 镜像
- **THEN** 每工单起一个容器（worker 镜像），挂载 worktree 执行

#### Scenario: kubernetes 模式水平扩展
- **WHEN** 企业有 K8s 集群，配置 `executor.mode=kubernetes` + namespace + kubeconfig + 镜像仓库可达
- **THEN** 每工单提交一个 Job 到该 namespace，按 ResourceQuota 限资源，多工单跨节点并行

#### Scenario: remote 模式离线裸机
- **WHEN** 离线环境 / 复用存量主机，配置 `executor.mode=remote` + SSH 节点池（每节点标 process 或 container）
- **THEN** 平台经 SSH 派发到 worker 节点执行，节点可走预装工具链（process）或容器

#### Scenario: 运行时可切换
- **WHEN** 管理员在 Web 把 `executor.mode` 从 process 切到 kubernetes
- **THEN** 新工单按新模式调度，存量在跑工单不中断；配置走 DB 热加载并记审计

### Requirement: Worker 镜像构建管线（仅容器类模式）
当 `executor.mode` 为 container / kubernetes / remote(container) 时，平台 SHALL 提供 `ImageBuilder`：Web 保存工具链版本组合 → 异步渲染 Dockerfile（terramate + tenv tf/tofu + provider mirror + opa + infracost，全部 pin）→ 构建 → 打 tag（版本组合）→ push 到可插拔 `ImageRegistry` 适配器（Harbor / 阿里云 ACR / AWS ECR / Azure ACR / Docker Registry / 内嵌本地 / 文件中转离线）；process 模式 MUST NOT 触发镜像构建。

#### Scenario: 配版本触发构建
- **WHEN** 管理员在 Web 把 terraform 升到 1.9 并保存（mode=kubernetes）
- **THEN** 平台异步构建 `tm-worker:tm0.17-tf1.9-DATE` 并 push 到配置的 registry，灰度后生效；旧镜像保留回滚

#### Scenario: process 模式无镜像
- **WHEN** mode=process
- **THEN** 平台不构建/不拉取镜像，工具链由节点预装（installer 维护）

### Requirement: 执行沙箱统一契约
无论哪种 Executor 模式，沙箱 MUST 统一提供：工具链（预装或 worker 镜像 D12）、git worktree 挂载（D4）、CPU/内存/磁盘限制、网络出口策略（egress 白名单 / 断网）、超时、退出码捕获、stdout/stderr 流式回传工单日志（`request_events`）。

#### Scenario: 四模式行为一致
- **WHEN** 同一工单分别用 process / container / kubernetes / remote 执行
- **THEN** 退出码、日志格式、worktree 路径、工具链版本一致（仅运行时拓扑不同），四模式可互换不改变执行语义
