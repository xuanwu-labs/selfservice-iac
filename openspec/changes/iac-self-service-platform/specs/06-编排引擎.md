# 06-编排引擎（orchestration-engine）

能力 ID：`orchestration-engine`
覆盖：表单提交 → 代码生成（由 `code-generation` 能力提供，specs/05）→ plan → 审批 → apply → 反馈的端到端流水线，调度 Terramate 执行，治理执行目录。

## ADDED Requirements

### Requirement: 端到端流水线
平台 SHALL 提供一条确定性流水线：`表单提交 → 代码生成（specs/05）→ terramate run ... plan → 审批/策略 → terramate run ... apply → reconcile`，每个阶段 MUST 有持久化状态与可观测事件。代码生成阶段 SHALL 由编排引擎调用独立的 `code-generation` 能力（specs/05），编排引擎自身 MUST NOT 包含代码生成逻辑。

#### Scenario: 业务提交 RDS 申请
- **WHEN** 业务用户提交"申请 RDS"表单，填写 `instance_type`、`storage_size`
- **THEN** 平台创建一个工单，依次推进 `submitted → generating（调用 specs/05）→ planning → plan-ready → pending-approval → applying → reconciling → succeeded`，每步可查询状态与日志

### Requirement: 调度 Terramate 执行
平台 SHALL 通过执行 `terramate run`（在指定 stack / bundle 范围）调用 Terraform 进行 `plan` 与 `apply`，捕获退出码、stdout/stderr，写入工单日志；MUST NOT 绕过 Terramate 直接调 Terraform。`terramate run` SHALL 在执行运行时（`Executor` 接口，specs/11 D20）提供的隔离沙箱内运行，编排引擎 MUST NOT 硬编码容器/Pod/进程细节。

#### Scenario: plan 成功后等待审批
- **WHEN** `terramate run -- terraform plan` 退出码 0 且有变更
- **THEN** 平台把变更摘要（含 Infracost 成本估算）和 plan artifact 写入工单，状态置为 `plan-ready` 后进入 `pending-approval`，通知审批人

### Requirement: 执行目录治理
平台 SHALL 维护一个或多个"Terramate 工作仓库"作为执行目录：负责 `git clone / fetch / pull`、把生成的 stack 提交到分支、执行后回写元数据；平台重启后 MUST 能依据元数据恢复执行目录到一致状态。代码生成（specs/05）产物 SHALL 由执行目录治理提交到内置 git 工作仓库的工单分支，commit SHA 持久化为 `pinned_commit`；`Executor`（specs/11）据此检出 worktree 执行 plan/apply。

#### Scenario: 代码生成产物提交并锚定 commit
- **WHEN** 流水线进入 generating 阶段，codegen 产出 stack 文件树
- **THEN** 平台在工单分支 `git add + commit`，记录 `pinned_commit`；后续 Executor 检出该 commit 为 worktree 执行；同工单重跑 generating 产出相同 commit（确定性）

#### Scenario: 平台重启后恢复执行目录
- **WHEN** 平台进程重启
- **THEN** 平台读取元数据库中的"工作仓库 remote + 分支 + commit"，重新 `git clone/fetch` 到本地工作目录，恢复到该 commit，无需人工干预

#### Scenario: 执行目录的并发隔离
- **WHEN** 两个工单同时操作同一 bundle
- **THEN** 平台为每个执行分配独立的工作目录副本或分支锁，避免互相覆盖

### Requirement: 审批双门禁（准入 + 执行确认）
平台 SHALL 在流水线设置两道审批门，均复用 `ApprovalEngine`（specs/10）但为独立审批流定义：①**准入审批**（generating 后、planning 前）判断申请是否被授权执行（低危可由 OPA 策略自动放行，中高危单审批人审）；②**执行确认审批**（planning 后、applying 前）判断 plan 产物是否可安全落地（输入=plan 差异 + Infracost 成本 + plan 后轻量漂移校验）。完整状态机 SHALL 为 `submitted → generating → pending-admission? → planning → plan-ready → pending-approval(pre-apply) → applying → reconciling → succeeded`。Phase 1 MAY 省略 `pending-admission`，只保留 pre-apply 门。

#### Scenario: 准入审批放行后才 plan
- **WHEN** 业务提交高危申请（如生产 RDS）
- **THEN** 代码生成后置 `pending-admission`，项目经理审批通过才进入 planning；低危申请由 OPA 自动放行跳过该门

#### Scenario: plan 后阻塞等执行确认审批
- **WHEN** `terramate run ... plan` 完成且 OPA 未拒绝
- **THEN** 平台解析 plan 差异 + Infracost 成本 + plan 后漂移校验，置 `pending-approval`，挂起执行确认审批流并通知审批人；UI 展示 plan diff 与漂移状态供审查

#### Scenario: OPA 拦截高危变更
- **WHEN** plan 结果包含删除生产 RDS
- **THEN** OPA 策略返回 deny，平台阻断 apply，工单状态置为 `blocked-policy`，记录违规规则

### Requirement: plan/apply 解耦（两次独立 Executor 调用 + 沙箱释放）
plan 与 apply SHALL 是两次独立的 `Executor`（specs/11）调用，中间由状态机阻塞：plan 完成后 MUST 把 plan 产物持久化到对象存储并销毁沙箱（MUST NOT 保持容器/进程等待人工审批）；apply 时 MUST 用新沙箱检出同一 `pinned_commit` + 下载已审 plan 产物，通过 `TerramateAdapter.RunApplySavedPlan` 执行 `terramate run -- terraform apply "<plan>"`（MUST NOT 重新 plan，确保执行内容与已审 diff 一致；MUST NOT 由 Orchestrator 绕过 Terramate 直接调用 Terraform）。

#### Scenario: plan 后释放沙箱，审批通过后新沙箱 apply
- **WHEN** plan 完成，进入 `pending-approval` 人数小时
- **THEN** plan 沙箱已销毁、plan 产物持久化；审批通过后启新沙箱检出 pinned_commit + 下载 plan 产物 apply；审批驳回则工单终止、无 apply

#### Scenario: apply 前漂移护栏
- **WHEN** plan 之后、apply 前漂移检测发现世界已变（state/云被改）
- **THEN** 平台告警并要求重 plan（已审 plan 过期），阻断直接 apply

### Requirement: 失败重试与幂等
平台 SHALL 区分可安全重试与必须人工介入的失败。codegen、plan、outbox/reconcile 可进入 `failed-retryable` 并受控重试；apply 若因云厂商瞬时错误失败可基于同一 `pinned_commit + plan_binary + sha256 + toolchain hash` 受控重试；apply 中断、state lock 异常或 state 不确定 MUST 进入 `waiting-manual` 并生成 `manual_intervention_tasks`，MUST NOT 盲重试。

#### Scenario: apply 失败可重试
- **WHEN** `apply` 因云厂商瞬时错误失败
- **THEN** 平台标记 `failed-retryable`，允许在界面点击"重试"，按同一 plan 或重 plan 策略受控执行，不产生重复资源

#### Scenario: apply 中断进入人工介入
- **WHEN** Executor 在 apply 期间失联或 state lock 异常
- **THEN** 平台标记 `waiting-manual`，生成 `manual_intervention_tasks`，要求人工 state 检查后再决定重试或修复

### Requirement: 事件与状态查询
平台 SHALL 在流水线每个阶段发布事件（状态变更、plan 就绪、审批完成、漂移发现），事件可通过 API / Webhook 订阅。

#### Scenario: plan 就绪通知
- **WHEN** plan 阶段完成
- **THEN** 平台发布 `plan.ready` 事件，通知审批人（站内信 / Webhook）
