# 18-标签与参数解析（tag-layering-and-parameter-resolution）

能力 ID：`tag-layering-and-parameter-resolution`
覆盖：Tag 来源 7 层合并 + 参数解析 9 阶段管道 + provenance 审计 + 校验门。对应 design `D28`、`docs/08-标签分层与参数解析管道`。本能力是 specs/05（code-generation）参数合并部分的权威细化（specs/05 的「四输入合并」演化为本能力的 9 阶段管道）。

## ADDED Requirements

### Requirement: Tag 来源 7 层 + 合并规则
平台 codegen SHALL 把 tag 来源分为 7 层，按 L1→L7 顺序合并：L1 platform-mandated（平台常量）/ L2 env（`environments.tag_namespace_json`）/ L3 tenant（`tenants.tag_namespace_json`）/ L4 team-bundle（`teams.tags_json` + `bundles.tags_json`）/ L5 stack（codegen 自动派生）/ L6 catalog（`catalog_items.default_tags_json`）/ L7 user form（`requests.form_values_json.tags`）。合并规则 MUST 为：L1 永远赢（用户尝试覆盖 silently ignore + 审计）；L2-L6 后层覆盖前层；L7 受 `catalog_items.user_allowed_tag_keys_json` 白名单约束；L7 不可覆盖 L1-L6。

#### Scenario: L1 强制不可覆盖
- **WHEN** 用户表单提交 `tags={"platform-managed":"false","owner":"zhangsan"}`
- **THEN** 平台在 S8 接收 user tags 时 silently ignore `platform-managed`（L1 永远为 `true`），保留 `owner=zhangsan`；resolved_params_json.tags.user_overrides_blocked MUST 含 `"platform-managed"`

#### Scenario: L7 受白名单约束
- **WHEN** catalog 项 user_allowed_tag_keys_json=["owner","ticket"]，用户表单提交 `tags={"owner":"zhangsan","secret-key":"xxx"}`
- **THEN** 平台 S8 校验失败，返回 422 + `{"error":"tag_key_not_allowed","key":"secret-key","allowed":["owner","ticket"]}`

#### Scenario: L2-L6 后层覆盖
- **WHEN** env.tag_namespace_json={"cost-center":"CC-P-01"} + team.tags_json={"cost-center":"CC-DBA-02"}
- **THEN** 合并后 cost-center="CC-DBA-02"（L4 团队层覆盖 L2 env 层）；resolved_params_json.tags.layers_merged_summary 记录各层贡献

#### Scenario: catalog 注册者声明默认 tag
- **WHEN** catalog 项 default_tags_json={"app":"order-service"}
- **THEN** 该 catalog 项申请生成的 module 调用 MUST 含 `app=order-service` tag（L6）；用户可在白名单内追加但不可移除

### Requirement: 参数解析 9 阶段管道
平台 codegen SHALL 按 9 阶段顺序解析参数：S1 模块契约载入 / S2 catalog defaults / S3 layer rule 注入 / S4 环境上下文绑定 / S5 tenant 上下文绑定 / S6 team 策略 / S7 跨层依赖注入 / S8 用户表单 / S9 平台强制注入。最终优先级 MUST 为 S9(1) > S3(2) > S6(3) > S8(4) > S5(5) > S4/S7(6) > S2(7) > S1(8)。**治理类（S3/S6/S9）高于用户类（S8）；用户高于上下文（S4/S5/S7）；上下文高于 catalog 默认（S2）；契约默认兜底（S1）**。同 rank tie-breaker：S4(env binding) > S7(dep graph)。

Phase 1 MAY 实现简化 5 阶段：contract(S1) / defaults(S2) / governance(S3+S6+S9) / user(S8) / dependency(S7)，但 source、rank 与 provenance 必须可映射到完整 S1-S9。

#### Scenario: 模块契约兜底
- **WHEN** 用户未传 storage，catalog 无 default，模块 variables.tf 默认值 storage=50
- **THEN** 最终 storage=50，resolved_params_json.storage.source="module_contract", rank=8

#### Scenario: 用户覆盖 catalog 默认
- **WHEN** catalog defaults storage=100（rank 7），用户表单 storage=200（rank 4）
- **THEN** 最终 storage=200，provenance.source=user_form, overridden_from.catalog_default=100

#### Scenario: layer rule 覆盖用户值
- **WHEN** layer rule 强制 encrypt_at_rest=true（rank 2），用户表单 encrypt_at_rest=false（rank 4）
- **THEN** 最终 encrypt_at_rest=true，provenance.source=layer_rule, user_attempted_override=true, user_attempted_value=false（治理违规留痕）

#### Scenario: env context 注入 vpc_id
- **WHEN** 用户不传 vpc_id，env=prod + tenant=corp-a + layer=Application 存在 binding（vpc_stack_id=vpc-corpA-prod）
- **THEN** S4 注入 vpc_id="vpc-bp1xxx"（rank 6），provenance.source=env_context, env_id/tenant_id/binding_id 记录

#### Scenario: team policy 成本双阈值（硬上限拒绝 + 软上限升级审批）
- **WHEN** team policy_json.cost_cap_cents=50000，用户表单选大规格 RDS，Infracost 预估月成本 80000 cents（1x~2x cap 软上限区间）
- **THEN** S6 **不拒绝**，标记 `resolved.cost_overrun={true, estimated_cents:80000, cap_cents:50000}` 透传到 pre-apply 门禁；D21 审批 DSL `when: cost_overrun==true` 插入成本升级审批节点（更高级别审批人）；provenance 记 `source=team_policy, cost_overrun=true`
- **WHEN** Infracost 预估月成本 120000 cents（>2x cap 硬上限）
- **THEN** S6 校验失败（安全阀），返回 422 + `{"error":"cost_hard_limit_exceeded","team":"dba","cap_cents":50000,"hard_limit_cents":100000,"estimated_cents":120000}`；**绝不放行**，即使更高级别审批人也不可覆盖

### Requirement: Provenance 审计（resolved_params_json）
平台 codegen MUST 在 generating 阶段完成后把每个解析变量写入 `requests.resolved_params_json`，结构 MUST 含 `{value, source, rank, optional: overridden_from/rule_id/env_id/tenant_id/binding_id/user_attempted_override/user_attempted_value}`。tags 字段例外，source="merged"。所有治理类覆盖用户类 MUST 记 `user_attempted_override=true` + `user_attempted_value`。

#### Scenario: resolved_params_json 完整性
- **WHEN** codegen 完成 generating 阶段
- **THEN** 每个 variables_contract 中的变量 MUST 在 resolved_params_json 中存在；缺失则 codegen 报警 + 拒绝进入 planning

#### Scenario: 治理覆盖留痕
- **WHEN** layer rule (S3) 强制 encrypt=true 覆盖用户值 false
- **THEN** resolved_params_json.encrypt_at_rest MUST 含 `user_attempted_override: true, user_attempted_value: false`（用于审计追溯）

#### Scenario: tags 层级记录
- **WHEN** codegen 完成
- **THEN** resolved_params_json.tags MUST 含 `source:"merged"`, `layers_applied:[...]`, `user_overrides_blocked:[...]`, `layers_merged_summary:{L1:[...],L2:[...],...}`

#### Scenario: vpc_id 来源可追溯
- **WHEN** 审批人查询某工单想了解 vpc_id 来源
- **THEN** 平台从 resolved_params_json.vpc_id.source 返回 "env_context"（或 "user_form" 如果用户显式指定），含 env_id/tenant_id/binding_id

### Requirement: 校验门（每阶段可拒绝）
平台 codegen MUST 在每个参数解析阶段后跑校验门，失败 MUST 返回结构化错误阻断 codegen（拒绝进入 planning）：S1 必填字段缺失 / S2 类型不匹配 / S3 layer rule 违反 / S4 binding 缺失 / S5 tenant 隔离违反 / **S6 成本超硬上限（>2x cap 拒绝；1x~2x cap 标记 cost_overrun 透传 pre-apply 门，不拒绝）** / S7 依赖不存在 / S8 类型/枚举/白名单不符 / S9 L1 强制 tag 完整性。

#### Scenario: S3 layer rule 违反
- **WHEN** layer rule allowed_regions=["cn-hangzhou","cn-shanghai"]，用户表单 region="cn-beijing"
- **THEN** S3 校验失败，返回 422 + `{"error":"region_not_allowed","value":"cn-beijing","allowed":["cn-hangzhou","cn-shanghai"],"rule_id":"rule-prod-region"}`

#### Scenario: S4 binding 缺失
- **WHEN** 工单 (env=prod, tenant=corp-a, layer=Application) 无对应 environment_tenant_bindings 记录
- **THEN** S4 校验失败，返回 `{"error":"binding_missing", ...}`（详见 specs/17）

#### Scenario: S9 强制 tag 完整性
- **WHEN** codegen 完成后最终 tags 不含 `platform-managed` / `platform-team` / `platform-bundle` / `platform-stack` 任一
- **THEN** S9 校验失败（这些是 L1 强制），返回 500 + `"platform mandatory tags missing, codegen bug"`

### Requirement: tag 值云厂商约束校验
平台 codegen MUST 在 S9 阶段对每个 tag key/value 按云厂商约束校验（长度/字符集/保留字），违规 MUST 拒绝（默认）或 sanitize（运维显式开 sanitize 模式）。校验规则 per-provider adapter，借鉴阿里云/AWS/Azure 官方约束。

#### Scenario: 阿里云 tag value 长度违规
- **WHEN** 用户提交 tag value 长度 200（阿里云上限 128），provider=alicloud
- **THEN** S9 校验失败，返回 422 + `{"error":"tag_value_too_long","key":"owner","value":"...","max":128,"provider":"alicloud"}`

#### Scenario: AWS 保留字违规
- **WHEN** tag key="aws:xxx"（AWS 保留前缀），provider=aws
- **THEN** S9 校验失败，返回 422 + `"tag key uses reserved prefix 'aws:'"`

#### Scenario: sanitize 模式
- **WHEN** 运维为某 env 开启 tag_sanitize=true，用户提交含特殊字符 tag value
- **THEN** S9 sanitize 替换非法字符（如把空格换 `_`），保留 sanitized value + provenance 记录原值

### Requirement: 模块零侵入不破坏（与 specs/05 一致）
本能力 MUST NOT 破坏 specs/05 模块零侵入约束——9 阶段管道在调用方生成代码时合并参数，**模块仓库 0 字节改动**。模块 variables.tf 仍是 scalar 单实例语义，多实例仍由 D25 cardinality 在调用方 for_each 注入。

#### Scenario: 9 阶段管道不影响模块
- **WHEN** codegen 跑 9 阶段管道合并参数后生成 module 调用
- **THEN** 生成的代码是标准 `module "x" { source=...; var1=...; var2=... }` 形式，模块仓库无任何改动

#### Scenario: 9 阶段管道与 cardinality 正交
- **WHEN** catalog 项声明 cardinality=map + 9 阶段管道跑完
- **THEN** codegen 在 for_each 调用语法基础上合并每实例参数，模块零感知

### Requirement: 与 specs/05 关系（演化不推翻）
本能力是 specs/05「四输入合并」的权威细化：原四输入（模块契约 + defaults + 表单 + 依赖图）保留并重新编号为 S1/S2/S8/S7，新增 S3/S4/S5/S6/S9 五个阶段。specs/05 表述更新为「9 阶段管道（详见 specs/18）」，原 specs/05「优先级：平台强制 > 表单 > defaults > 契约」演化为「S9 > S3 > S6 > S8 > S5 > S4/S7 > S2 > S1」（治理类 > 用户类 > 上下文类 > catalog 默认 > 契约兜底）。**同 rank tie-breaker**：S4(env binding) > S7(dep graph)——S4 注入 `vpc_stack_id` 元变量，S7 用它生成 remote_state；同变量冲突时 S4 赢（治理决策 > 实现细节）。

#### Scenario: specs/05 + specs/18 协同
- **WHEN** 编排引擎调用 codegen 在 generating 阶段
- **THEN** codegen 按 specs/05「生成 stack 与调用模块」生成代码，参数合并细节按 specs/18「9 阶段管道」执行；两 spec 无冲突
