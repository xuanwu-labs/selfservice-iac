## 2. 方案理解

### 2.1 平台目标

在不侵入 Terramate 核心的前提下，向上叠加一层"基础设施产品化"能力：将 Terraform/Terramate 从"工程师 CLI 工具"升级为"DBA / 中间件 / 业务团队都能自助使用"的内部基础设施平台，同时保留可插拔、可自主掌控、可避免厂商锁定的弹性。

### 2.2 业务问题

- 模块、表单、审批、状态治理、漂移检测、多团队分层治理在 Terramate 上全部缺失，企业大规模采用 IaC 必须的"产品化"层空白。
- 自建以避免 Spacelift / Env0 / TFC 的厂商锁定与商业成本。
- 内部需要严格多团队分层治理（网络运维 / DBA / 中间件 / 业务），现有商业产品的"flat workspace + label"模型不够。

### 2.3 核心用户

- **DBA / 中间件 / 业务开发**：自助申请基础设施。
- **平台运维（platform-ops）**：守护云账号、模块、layer 规则、凭据。
- **资源 Owner / Team Lead**：双门审批人。
- **AI Agent（D17）**：通过 MCP / CLI 接入，治理不豁免。

### 2.4 角色清单

`admin` / `platform-ops` / `team-owner` / `approver` / `requester` / `service-account` / `ai-agent`

### 2.5 整体执行链路（22 步主链路）

```
[OIDC 登录] -> [选 catalog 项（按 team_cloud_grants + env_scope 过滤）] -> [填表]
-> [POST /requests 同步建单（幂等键）] -> [异步：codegen 9 阶段管道（S1-S9）]
-> [PathGenerator 渲染 stack 目录 + state key] -> [CardinalityInjector 注入 for_each]
-> [stack.tm.hcl 生成（D29）+ terraform fmt] -> [git commit pinned_commit]
-> [Executor 沙箱（D20 四模式之一）] -> [terramate run -- terraform plan]
-> [plan 产物上传对象存储 + sha256 + 销毁沙箱]
-> [pre-plan 审批挂起（D21 准入门）]
-> [pre-apply 审批挂起（D21 执行确认门，输入 = plan diff + Infracost + 漂移校验）]
-> [审批通过 + 漂移护栏] -> [新沙箱 + 注入 STS（D23 OIDC 联邦）]
-> [terraform apply "<plan>"] -> [资源回写 CMDB（D18 ingester）]
-> [tag 归集 cost_records] -> [事件 + Webhook 通知]
-> [周期 DriftDetector 复用 Executor 跑只读 plan]
```

### 2.6 核心组件（25+）

Orchestrator / Codegen / ParamResolver(9 阶段) / TagMerger(7 层) / PathGenerator / CardinalityInjector / StackModel(D24+D26) / EnvTenant(D27) / Executor(四模式 D20) / ImageBuilder + BuildDriver(docker/buildah/kaniko) / Installer / Workspace(go-git+worktree) / TerramateAdapter / DriftDetector / ApprovalEngine(YAML DSL+双门禁) / OIDC Multi-Provider(D10.1) / DirectorySyncer(SCIM/飞书/钉钉) / CloudCreds(三层凭据 D23) / CMDB Ingester / FinOps(Infracost+账单) / MigrationPlanner+StateMover+SunsetTracker(D26) / Importer(D14) / Gate(D16) / CLI(`tm` + MCP server D17) / Skills

### 2.7 控制流 / 数据流 / 凭据流

- **控制流**：HTTP → Orchestrator 状态机 → ApprovalEngine → 异步队列 → Executor → exec(terramate)。
- **数据流**：form → resolved_params_json（含 provenance）→ .tf 文件 → git → state → CMDB。
- **凭据流**：Vault/KMS（bootstrap）→ OIDC token → STS（短期）→ Executor env（绝不入 git / 日志 / codegen）。

### 2.8 理解不清晰处（需方案补充）

1. **D17 `tm ai` 后端 LLM** 与 **D17 MCP 让外部 agent 接入**职责重叠：同一查询既可走平台后端 LLM 也可走 Claude Code，治理边界与"谁主导推理"未明确。
2. **D27 binding 与 D26 layer 版本化交互**：layer_rule_set v1→v2 改了 `path_template`，已存在的 `environment_tenant_bindings` 是否需要重建？binding.vpc_stack_id 引用的 stack path 在 v2 已变，迁移期 codegen 走哪个版本？
3. **CMDB ingester（D18）事务边界**：apply 成功但 ingester 失败时，CMDB 与 state 不一致如何修复？未见补偿（retry / dead-letter / 对账触发）机制。
4. **元数据 DB 灾难恢复**：DB 完全丢失时，单靠工作仓库 + remote state 能恢复哪些元数据？grants / approvals / migrations / audit 是否可重建？未定义 DR-SOP。

## 3. 逻辑串联性评审

### 3.1 正常链路评估

主干 `提交 → codegen → plan → 审批 → apply → CMDB` **闭环清晰**：

- **D21 双门禁 + plan 产物 sha256 + 漂移护栏**：与 TFC speculative plan 同构，是企业级实践。
- **9 阶段参数管道 + 7 层 tag + provenance（D28）**：在同类自研平台中是最完整的设计。
- **D29 单仓 + stack.tm.hcl 生成**：与 Terramate 源码原生设计契合，源码级证据充分。

### 3.2 缺失链路

| # | 缺失环节 | 影响 |
|---|---------|------|
| L1 | **plan 产物 TTL 失效**：plan 到 apply 若间隔 > N 小时，世界已变但漂移护栏未触发 | 审批通过 → apply 失败 → 体验差 |
| L2 | **审批人不在岗回退**：D11 提到超时升级，但升级到谁、最终兜底人是谁未明确 | 流水线僵尸工单 |
| L3 | **跨层依赖反向变更阻断**：Application stack `watch` Global VPC，但 VPC 删除/变更只触发下游 plan，不阻断 VPC apply | VPC 误删 → 下游全爆 |
| L4 | **codegen 失败的产物清理**：codegen 写到一半失败，worktree 残留半成品的 git reset 时机未明 | worktree 污染影响后续工单 |
| L5 | **catalog 项 sunset**：D24 sunset 是 layer 级别，catalog 项级别的下线缺失 | 弃用 catalog 仍被复用 |
| L6 | **bootstrap 凭据吊销 cascade**：D23 提到轮换但未提"云账号注销 → 自动 cascade 到 grants / credentials / 已执行身份" | 凭据泄漏面扩大 |
| L7 | **migration 中 in-flight 工单**：D26 QuiesceBatch 冻结，但**冻结期间已 plan 未 apply** 的工单 apply 用 v1 还是 v2？未明确 | 状态不一致 |
| L8 | **AI 决策记忆**：tm ai 触发 destroy 被审批拒绝后，下次同 prompt 是否会重试？skill 是否记忆历史决策？ | 反复触发审批，疲劳轰炸 |

### 3.3 冲突链路

1. **D17 vs D11**：tm ai → skill 编排 → 多步 CLI 调用，每步独立 RBAC 校验，但整条 skill 链是否需"整体批准"？当前模型每步审批 = 用户疲劳。
2. **D20 Executor 切换 vs D22 工具链校验**：admin 在 Web 切了 `mode=k8s` 后，process 模式 installer 写的 `toolchain_manifest` 是否仍是真相源？切模式后兼容校验是否重跑？未明确。
3. **D28 S6 team policy 拒绝 cost_cap vs D21 pre-apply 审批 Infracost 升级**：成本超 cap 在 codegen 阶段被 S6 直接拒绝，就走不到 pre-apply 升级审批，"超预算需更高审批"链路其实失效。
4. **D29 单仓 vs D27 多租户**：单仓 RBAC + tags 实现"租户隔离"，但 git 层无强隔离——租户 A 的 commit 会出现在租户 B 的 git log，对强合规客户不可接受。

### 3.4 建议补充链路

| # | 建议 | 价值 |
|---|------|------|
| A1 | **plan 产物 TTL 强制重 plan**：apply 时 `plan_age > 4h` 强制重 plan + 重 pre-apply | 避免审批通过的 plan 与世界脱节 |
| A2 | **审批超时降级 SOP**：超时 → team lead → platform-ops → 最终 cancel + 通知申请人 | 消灭僵尸工单 |
| A3 | **catalog sunset 三态机**：active → deprecated（禁新申请）→ archived（拒引用，存量待迁移） | 弃用 catalog 不残留 |
| A4 | **codegen 临时目录事务**：临时目录构建 → 验证 → 原子 mv 到 worktree，失败丢弃 | 杜绝 worktree 污染 |
| A5 | **cloud_account 注销 cascade**：注销 → cascade 到 grants → cascade 到 credentials → 触发凭据吊销 job | 防泄漏面扩大 |
| A6 | **AI 决策历史 ai_decision_history**：skill 执行结果（含 reject）落库，同 prompt 重试时引用 | 防 AI 疲劳轰炸 |
| A7 | **migration in-flight 失效**：冻结开始时该批 stack 所有 plan 产物失效，apply 前强制重 plan | 防 v1/v2 混用 |

### 3.5 隐式前置条件（未在方案中说明）

1. **PostgreSQL 强一致事务**：状态机 / grant / provenance 都假设事务性，但 9 阶段 codegen + git commit + DB 更新**不在同一事务**——故障窗口存在。
2. **对象存储版本化**：plan 产物 sha256 校验依赖 S3 versioning + object lock。
3. **Executor 节点时钟同步**：AK/SK SigV4、plan TTL、审批超时均强依赖 NTP，方案未提。
4. **DNS / mirror 可用性**：terraform init / provider mirror 不可用时全平台不可用，无降级路径。
5. **OIDC issuer JWKS rotation**：D10.1 多 issuer 并存假设 JWKS 定期刷新，issuer 证书过期场景未提。
6. **Terramate CLI 二进制 sha256 pin**：D1 锁版本但未提哈希校验，CI 拉错版本风险存在。

## 5. 风险评估

### 5.1 技术风险

| # | 风险 | 影响范围 | 概率 | 严重 | 缓解措施 | 优先级 |
|---|------|---------|------|------|---------|-------|
| T1 | StateMover 自动化引发资源重建 | 单 stack | 中 | **极高** | 默认禁用；自动化 feature flag + 双人审批 + plan=0 死硬校验 | **P0** |
| T2 | Terraform Provider 升级 plan diff 突现 | 全 stack | 高 | 中 | provider lock.hcl + dependabot 自动 PR + canary stack 先升 | P0 |
| T3 | 并发 apply 同一 stack（race） | 单 stack | 中 | 高 | DB 行级锁 `requests.stack_id` + state DynamoDB 锁双锁 | P0 |
| T4 | Backend state 不可用（S3/MinIO 宕） | 全平台 | 低 | 极高 | 多 AZ S3 + 读后写一致性测试 + 工单自动 backoff | P0 |
| T5 | Pipeline Executor OOM / panic | 单工单 | 高 | 中 | cgroups 内存软限 + 超时 + 自动重试 1 次 | P1 |
| T6 | Terramate 版本升级输出格式变 | 全平台 | 中 | 高 | golden file CI + 版本 pin + 灰度升级 | P1 |
| T7 | 多云 SDK 版本兼容（alicloud SDK 大版本） | 多云 stack | 中 | 中 | adapter 接口 + contract test 隔离 | P1 |
| T8 | 漂移检测打满云 API（限流） | 全平台 | 高 | 中 | 限流 + 分层时间窗 + 退避；漂移粒度小时降级到天 | P1 |
| T9 | go-git worktree 池泄漏（1000+ 工单后） | 单节点 | 中 | 高 | 定期 reconcile + worktree GC + 节点重启自愈 | P1 |
| T10 | codegen 9 阶段管道某阶段 bug | 全工单 | 中 | 高 | 每阶段单元测试 + provenance 完整性断言 + canary 工单 | P1 |

| T12 | Vault / KMS 不可用 | 全平台 | 低 | 极高 | Vault HA + 平台 fallback 缓存（短期 5min） | P1 |

### 5.2 组织风险

| # | 风险 | 缓解措施 | 优先级 |
|---|------|---------|-------|
| O1 | **平台团队成瓶颈**：模块 / catalog / layer 全过平台，2-3 人撑不起 100+ 团队 | 模块注册自助 + catalog 团队 owner 可发布 + layer 改动季度 review | P0 |

## 7. 安全与合规评审

### 7.1 RBAC 设计

- **优点**：D9 + D27 把 RBAC 拆到 team × project × bundle × stack × layer × env × action 七维，覆盖面完整。
- **问题**：
  - 权限矩阵未给出具体定义文件（如 `role_definitions.yaml`），落地易碎片化。
  - **service-account / ai-agent / human** 三类 actor 在 RBAC 引擎是统一通道，但**审计字段**未区分高危度（AI 操作应高亮）。
- **建议**：抽象 `RoleDefinition` 表 + 内置模板（platform-admin / team-owner / approver / requester / sa-readonly / sa-execute / ai-agent-skill），actor_kind 字段强制写入 audit_logs，AI 操作 audit 标 `risk_marker=ai`。

### 7.2 最小权限

- **优点**：D23.5 catalog 项 `required_permissions` 聚合生成 IAM 角色，方向正确。
- **问题**：catalog 注册时**没有审核者校验聚合后的 IAM policy 不爆炸**——多个 catalog 项聚合可能合并出过宽权限。
- **建议**：聚合后的 IAM policy 必须经 OPA 二次校验（禁 `*:*` / 禁通配 region / 禁 root account 操作）+ 注册时人工 review。

### 7.3 Secret 管理

- **优点**：D23 + 19.6 占位符 + Vault/KMS + 不入 git / log / codegen，方向是 PCI-DSS 级实践。
- **问题**：
  - **凭据缓存窗口** 未限制：`CredentialResolver` 解析 STS 后是否在 Executor 节点缓存？缓存多久？
  - **日志脱敏** 仅靠正则，未覆盖 base64 / hex / 编码变形。
- **建议**：STS 仅活在单次 `Executor.Run` 进程内（env 注入，进程退出销毁）；日志脱敏增 base64 解码扫描 + 已知 secret 值哈希前缀匹配。

### 7.4 Terraform State 敏感字段

- **问题**：state 可能含 RDS root password / TLS 私钥等明文（Terraform 已知问题），方案未提任何保护。
- **建议**：①state 后端强制服务端加密（KMS CMK）+ 客户端加密（state-at-rest double encrypt）；②CMDB ingester 必须 strip sensitive 字段（按 schema 黑名单）；③state download API 走 RBAC 高权限 + 审计 + IP 白名单。

### 7.5 审批链设计

- **优点**：D21 双门禁 + plan 产物 sha256 是审批审计的金标准。
- **问题**：plan 产物上传对象存储后，**审批人查看的 diff** 来自后端解析；如果后端解析与实际 `terraform apply` 行为不一致（不同 Terraform 版本输出微差），审批基础不可信。
- **建议**：apply 时强制对 plan 产物 sha256 二次校验 + Terraform 版本 pin（plan 与 apply 必须同版本，否则拒绝）。

### 7.6 操作审计 / 发布审计

- **优点**：D9.4 append-only audit_logs + 事件总线齐全。
- **问题**：审计日志的**完整性证明**（防篡改）未提，强合规客户审计需要 HMAC chain 或外部 immutable storage。
- **建议**：audit_logs 双写到 S3 object lock（governance mode）+ 每日 HMAC chain 签名 + 季度审计员可独立验证。

### 7.7 Break Glass 机制

- **问题**：**完全缺失**。生产故障时如何绕过审批做紧急 apply / destroy？方案无任何描述。
- **建议**：
  - 引入 `emergency_mode`：双人 break-glass 凭据（独立 vault path）→ 绕过审批 → 自动全程录屏 + 操作后强审计 review + 24h 内必须补审批回填。
  - emergency 操作触发 platform-ops oncall + CISO 邮件通知。

### 7.8 多租户隔离

- **优点**：D27 vpc-per-env 默认 + EnvironmentTenantBinding 三元组，业界共识。
- **问题**：
  - D29 单仓让租户 A 的 commit / git log 暴露给租户 B（git RBAC 颗粒度不够）。
  - 元数据 DB 是单库多 schema 还是租户分库未明确——强合规客户要求数据物理隔离。
- **建议**：
  - 强合规租户 escape hatch：允许独立 git 仓库 + 独立 backend bucket + 独立 DB schema（accept 单租户运维成本翻倍）。
  - DB 行级 RLS（Row-Level Security）作为最低保障 + tenant_id 全字段强制注入。

### 7.9 合规要求

| 标准 | 关键控制 | 当前方案 | 差距 |
|------|---------|---------|------|
| SOX | 变更审批可追溯 / 职责分离 | D21 双门禁 + D9.4 audit 满足 | 缺 break-glass 与 emergency 路径的可追溯；缺审计员独立审查接口 |
| ISO27001 | A.9 访问控制 / A.12 操作 / A.18 合规 | RBAC / 审计 / 凭据较完整 | 缺 incident response SOP / DR drill / vendor risk assessment |
| PCI-DSS（如涉及支付） | secret 不入日志 / 双人审批 / 加密传输 | D23 已覆盖 | 缺 cardholder 数据隔离声明（如适用） |
| 等保 2.0 三级 | 国密 / 日志 180 天 / 鉴别 | OIDC 满足鉴别 | 缺国密 SM2/3/4 支持声明 |

- **不足**：

|------|------|--------|

| State Lock Duration | `histogram_quantile(0.99, tm_state_lock_duration_seconds_bucket)` | Executor 埋点 |

### 8.4 容量规划

- **缺失**：方案未给容量基线（多少 stack / 多少并发 / 多大 DB）。
- **建议**：建立 capacity_model（small/medium/large 三档）+ 季度容量审计 + 自动扩缩容触发线（worktree 池利用率 > 70% 加节点）。

## 9. 成本收益评审

### 9.1 短期收益（0-12 月）

- **变更可审计**：所有基础设施变更走平台 = SOX/等保审计成本降低 50%+。
- **新业务接入提速**：业务团队自助 RDS / ECS 从工单走 IT 工单（3-7 天）→ 自助申请（小时级）。
- **凭据集中管理**：D23 OIDC 联邦消除"业务持有云 AK/SK"，泄漏面收敛 80%+。

### 9.2 长期收益（12-36 月）

- **多团队治理可扩展**：D24 + D27 + D28 体系成熟后，新增团队 / 租户 / 环境是配置而非开发。
- **FinOps 闭环**：D18 强制 tag + 双成本源 → 团队成本可视化 → 反推优化（rightsize / RI / 孤儿）。
- **AI 辅助运维**（D17 落地后）：常规申请 / 漂移修复 / 成本优化的自然语言入口，进一步降低门槛。

### 9.3 建设成本估算

| 类别 | 投入 | 备注 |
|------|------|------|
| Phase 1 主干闭环 | ~36 人月 | 6 人 × 6 月（后端 3 + DBA 1 + 前端 1 + DevOps 1） |
| Phase 2 多团队治理 | ~54 人月 | 9 人 × 6 月（叠加 SCIM / approval / FinOps） |
| Phase 3 AI + 迁移 + 全多云 | ~42 人月 | 7 人 × 6 月 |
| **合计** | **~132 人月（18 月）** | 不含运维与产品 |
| 基础设施 | PG 主从 + MinIO 集群 + Executor 节点池 + Vault HA | 月成本 ~$3-10k（视规模） |
| Terramate / Terraform 商业 license | 无（开源） | OpenTofu 同 |

### 9.4 维护成本

- 人力：2-3 人长期 platform-ops（含 oncall）。
- 镜像构建管线：CI 算力 + 镜像仓库存储（线性增长）。
- 漂移检测 plan 调用：云 API 调用成本（限流后可控）。

### 9.5 ROI 判断

- **适配规模**：50+ 业务团队 / 500+ stack / 多云环境时 ROI > 3。
- **收益递减点**：< 10 团队 + 单云 + < 50 stack 时，自建 ROI 不如直接采买 Spacelift / Env0。
- **拐点**：30 团队、200 stack、跨云、强合规要求 → 自建必要性显现。
