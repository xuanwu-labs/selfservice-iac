# 优化后 IaC 自助平台架构复评报告

评估对象：`openspec/changes/iac-self-service-platform`

评估日期：2026-06-26

评估视角：平台架构师、代码工程师、云架构师

## 1. 复评结论

本轮优化后，方案已经从“大而全资源管理平台”明显收敛为“受治理的 IaC 变更控制面”。原先最致命的多权威冲突已经得到较大修复：路径契约、工单状态机、参数优先级、元数据 schema、存量导入生命周期、CI/CD gate 语义均形成了更清晰的主线。

综合评分：**78 / 100**。

- 可落地性：**78 / 100**。Phase 1 已收敛到标准模块自助申请、plan、pre-apply 审批、apply、审计/CMDB index 的最小闭环，具备启动工程拆解的基础。
- 逻辑连续性：**80 / 100**。Saga、Outbox、Reconcile、`manual_intervention_tasks` 已补入主设计，长流程中断后不再“失忆”。
- 自洽性：**82 / 100**。`docs/08` 成为参数 rank 权威，`docs/09` 改为引用；`docs/02` 收敛到 D29 layer-first Path Contract。
- 架构优雅性：**76 / 100**。核心实体已收敛，但部分 Phase 2/3 能力仍然在文档中显得偏重，需要实现时继续守住 MVP 边界。
- 工程施工成熟度：**72 / 100**。状态机、表结构、断点补偿更完整，但 API 契约、状态迁移测试矩阵、运维 runbook 还不足以直接进入编码。

一句话结论：**方案已经从“概念架构”进入“可拆解施工图前夜”，但还需要补齐 API 契约、运行手册、测试矩阵和云凭据 bootstrap 细节，才能降低实施期返工。**

## 2. 已明显修复的问题

### 2.1 四个权威模型基本冻结

`design.md` 新增了优化后的设计收敛原则，明确四个权威模型：

- `Path Contract`：以 D29 的单仓 layer-first 拓扑为准，PathGenerator 输出 `repo_path`、`state_key`、`stack_id`、Terramate tags。
- `RequestLifecycle`：收敛到 `submitted → generating → pending-admission? → planning → plan-ready → pending-approval → applying → reconciling → succeeded`。
- `ParameterResolution`：以 `docs/08` / `specs/18` 为唯一 rank 权威。
- `Metadata Schema`：以 `docs/04` 为数据库权威，补齐 codegen、approval、drift、import、CMDB、CICD 依赖实体。

这解决了原方案中“同一概念在多个文档各自定义”的核心断层。

### 2.2 Path Contract 已从冲突模板收敛为单一模型

`docs/02` 已明确采用 layer-first 单仓拓扑：

- `global/<component>-<tenant>-<env>`
- `middleware/<tenant>/<component>-<env>`
- `application/<tenant>/<team>/[bundle/]<component>-<env>`

这比旧文档同时出现 `globals/<env>`、tenant-first、application 无 tenant 的写法更自洽。`state_key` 默认等于 `repo_path`，Terramate tags 与路径共同构成 stack 身份契约，后续 codegen、CMDB、drift、迁移可以共享同一来源。

### 2.3 状态机和长流程断点更完整

`docs/01`、`docs/10`、`docs/12` 已补入关键断点：

- git commit 成功但 DB 写 `pinned_commit` 失败，由 reconcile 找回或回滚孤儿 commit。
- plan 上传成功但 artifact row 写入失败，由对象存储扫描补偿。
- apply 成功但 CMDB/通知/FinOps 失败，进入 `reconcile-pending`，不把 apply 判失败。
- apply 中断、state 不确定时进入 `waiting-manual`，生成 `manual_intervention_tasks`，不盲目重试。

这使长流程从“同步流水线”升级为具备 Saga 语义的可恢复流程。

### 2.4 存量导入从“一步纳管”变成安全过渡

`docs/15` 和 `specs/12` 增加了：

`discovered → candidate → imported-limited → managed-readonly → managed-changeable → standard`

这是非常关键的修正。现实存量资源通常不满足 tag、命名、模块契约、owner、依赖图等标准，直接进入可 apply 状态风险很高。现在默认先进入 `managed-readonly`，平台先获得可观测性和审计，再逐步开放变更，落地性明显提升。

### 2.5 CI/CD gate 语义修正

`docs/16` 和 `specs/13` 已把幂等键改为：

`pipeline + commit + catalogItem + form_hash`

并区分：

- `approval_granted`：审批通过。
- `apply_succeeded`：资源实际落地。

这解决了原方案中“审批通过是否等于 CD 可继续”的语义漏洞。默认 `tm gate --wait` 等待 `apply_succeeded` 是更安全的工程选择。

## 3. 当前仍存在的关键风险

### P1-1：Phase 1 的 codegen 范围仍需进一步固化

计划中 Phase 1 说“4 输入 codegen”，文档优化后改成“5 阶段简化”：

- contract
- defaults
- governance
- user
- dependency

这是合理的，但实现前还需要把 Phase 1 的 exact input/output contract 写成更像接口文档的形式，包括：

- `ResolvedParams` JSON schema
- `PathGenerator` 输入输出 schema
- `stack.tm.hcl` 生成字段
- `backend.tf` 生成字段
- `plan artifact` 元数据字段

否则工程阶段仍容易在 codegen 与 orchestrator 之间重新产生隐式契约。

### P1-2：云凭据 bootstrap 仍是落地关键路径

文档已经有 OIDC-first、Bootstrap/Admin、Execution、Personal 三层凭据模型，但生产落地还缺少更明确的 bootstrap 顺序：

1. 首个云账号如何接入。
2. Bootstrap 凭据如何进入 Vault/KMS。
3. 平台 OIDC issuer / JWKS 如何被云账号信任。
4. 首个 team execution role 如何创建。
5. `team_cloud_grants` 如何从无到有。

这不是架构方向问题，而是“第一天怎么启动”的问题。若不补，Phase 1 会卡在第一条真实 apply 链路。

### P1-3：状态机有设计，但缺测试矩阵

`docs/12` 已有迁移矩阵，但 tasks 中还需要继续具象化测试用例，至少覆盖：

- codegen 失败重试
- git commit 成功 / DB 失败补偿
- plan artifact 过期
- approval timeout/escalation
- apply interrupted → waiting-manual
- apply succeeded / CMDB failed → reconcile-pending
- duplicate request idempotency
- CI duplicate with same form_hash vs changed form_hash

没有这些测试，状态机虽然写清楚了，但工程实现仍可能退化成 if/else 堆叠。

### P1-4：OpenAPI / API 契约仍偏弱

目前文档有很多表结构和流程，但 API 级契约仍不够：

- `POST /requests`
- `GET /requests/{id}`
- `GET /requests/{id}/gate`
- `POST /approvals/{run_id}/decide`
- `POST /catalog`
- `GET /catalog?team_id&cloud_account_id&env`
- `GET /stacks/{id}/events`

这些 API 的 request/response、错误码、幂等头、correlation_id 规则还需要成为实施前置产物。否则前端、CLI、CICD adapter、orchestrator 会并行猜接口。

### P2-1：`prototype/index.html` 仍有旧路径示例

核心 docs/specs 已收敛，但原型中仍可见旧路径，如 `middleware/prod/...`、`globals/prod/...`、`application/team-a/...`。这不会影响规范本身，但会影响评审和演示认知。

建议后续把原型统一更新为：

- `global/vpc-platform-default-prod`
- `middleware/platform-default/rds-orders-prod`
- `application/platform-default/team-a/orders/ecs-prod`

### P2-2：StateMover 降级方向正确，但 UI 仍可能误导

文档已经把 StateMover 降级为 Phase 3、默认关闭、人工 SOP 优先。但如果原型或任务中展示“自动 state mv ✅”过于积极，容易让后续实现误判为必须自动化。

建议所有 StateMover 文案统一表达为：

“迁移计划 + 影响面 + 人工 SOP + 审计；半自动执行默认关闭。”

## 4. 生产落地路径建议

### Phase 0：施工前冻结

目标：把文档转成工程契约，而不是继续扩展能力。

必须产出：

- API 契约草案。
- RequestLifecycle 状态迁移测试矩阵。
- PathGenerator 输入输出 schema。
- ResolvedParams JSON schema。
- plan artifact 元数据 schema。
- bootstrap cloud account runbook。

### Phase 1：最小闭环

只做：

- 单 tenant：`platform-default`
- 固定三层：`global/middleware/application`
- 单云或单主云账号
- 标准 catalog item
- 5 阶段简化 codegen
- Git pinned commit
- Terraform plan artifact sha256 + TTL
- 单 pre-apply 审批
- 一个 Executor 模式
- apply 后 CMDB index
- request_events + audit_logs

不要做：

- AI/MCP
- 自动 StateMover
- 多 Executor 四模式
- 复杂审批 DSL
- FinOps 账单核销
- 孤儿自动释放

### Phase 2：生产治理

增加：

- 双门禁
- 9 阶段参数管道 + provenance
- OIDC-first execution credentials
- drift detection
- managed-readonly → managed-changeable 的存量导入生命周期
- CI/CD gate
- CMDB reconcile
- 基础成本视图

### Phase 3：高级平台化

增加：

- 多 tenant / account-per-env
- Layer 规则版本化
- 半自动 StateMover，但默认关闭
- AI/MCP/skills
- FinOps 优化建议
- 云侧 inventory 孤儿检测

## 5. 最终判断

这轮优化已经解决了原方案中最危险的三个问题：

1. 多权威模型冲突。
2. 长流程断点失控。
3. MVP 目标过大。

但它还不是“立刻写代码”的最终形态。下一步不应继续加能力，而应把现有设计压成工程契约：API、schema、状态迁移测试、bootstrap runbook、错误码和幂等规则。

最终结论：**可以进入实施准备阶段，但不建议直接进入大规模编码；先用 1 个标准 catalog item 做端到端 walking skeleton，验证 Request → Codegen → Git → Plan → Approval → Apply → Reconcile 的最小闭环。**
