# 08-标签分层与参数解析管道

> 对应 design `D28`、spec `specs/18-标签与参数解析`。回应：tag 来源分层、参数合并优先级、provenance 审计、校验门、冲突解析。

## 1. 为什么需要分层（业界共识）

| 问题 | 单层模型的痛点 | 分层模型如何解 |
|------|--------------|--------------|
| Tag 冲突 | 用户填 `platform-managed=false` 篡改治理 | L1 永远赢，silently ignore + 审计 |
| 成本归集不准 | 没有 env/tenant 维度 tag | L2/L3 强制注入，云账单按 tag 归集 |
| 默认值不知来源 | codegen 输出无法解释为何某值是 X | provenance 记录每变量 source/rank |
| 治理与体验冲突 | layer rule 强制 encrypt=true 但用户改了 | 治理类 (rank 2/3) 高于用户 (rank 4)，留痕 user_attempted_override |

业界成熟模式：**Helm values 分层合并 + Kustomize strategic merge + Terraform 变量优先级 + Crossplane Function pipeline provenance + AWS Tag Policies**——共识是**分层来源 + 显式优先级 + provenance 可审计 + 治理永远赢**。

## 2. Tag 来源 7 层（权威见 docs/04 §2.14）

| 层 | 来源 | 示例 | 谁配 | 谁能改 |
|----|------|------|------|--------|
| **L1 platform-mandated** | 平台常量 | `platform-managed=true` | 平台硬编码 | 任何人不能 |
| **L2 env** | `environments.tag_namespace_json` | `env=prod`, `cost-center=CC-P-01` | 平台运维 | env owner |
| **L3 tenant** | `tenants.tag_namespace_json` | `tenant=corp-a`, `compliance=pci` | 平台运维 | tenant owner |
| **L4 team/bundle** | `teams.tags_json` + `bundles.tags_json` | `platform-team=dba`, `platform-bundle=orders` | 团队 owner | team owner |
| **L5 stack** | codegen 自动派生 | `platform-stack=rds-orders-prod` | 自动 | 任何人不能 |
| **L6 catalog defaults** | `catalog_items.default_tags_json` | `app=order-service` | catalog 注册者 | catalog owner |
| **L7 user form** | `requests.form_values_json.tags` | `owner=zhangsan` | 申请者 | 受白名单约束 |

### 2.1 合并规则

```
最终 tags = merge(L1, L2, L3, L4, L5, L6, L7)
```

- **L1 永远赢**：用户尝试覆盖 `platform-managed` / `platform-team` / `platform-bundle` / `platform-stack` → silently ignore + `user_overrides_blocked` 记入 resolved_params_json
- **L2-L6 后层覆盖前层**：如 L4 与 L2 同 key，L4 值胜出
- **L7 受白名单约束**：`catalog_items.user_allowed_tag_keys_json` 列出允许的 key；白名单外 → 拒绝（结构化错误：`"user tag key '...' not in allowed list [...]，请联系 catalog 注册者"`）
- **L7 不可覆盖 L1-L6**：同 key 时低层（L1-L6）胜出，L7 silently ignore + 审计告警

### 2.2 tag 值校验（codegen Stage 9）

每个云厂商 tag 有约束（长度/字符集/保留字），codegen MUST 校验：

| 云 | key 长度 | value 长度 | 字符集 |
|----|---------|----------|--------|
| 阿里云 | 1-128 | 1-128 | 字母数字 + `._-/:=@+-` |
| AWS | 1-128 | 0-256 | UTF-8（部分保留字） |
| Azure | 1-512 | 0-256 | `<->`、`<>` 不能用 |

违规处置：sanitize（截断/替换非法字符）或拒绝（结构化错误）。**默认拒绝**，运维显式开 sanitize 才软化处理。

## 3. 参数解析 9 阶段管道

> **唯一 rank 权威**：本节是参数优先级的唯一事实源。`docs/09`、`design.md`、`specs/05` 只能引用本节，不再重复定义不同 rank 表。Phase 1 可实现 5 阶段简化管道，但必须能无损映射到本节 S1-S9。

### 3.0 Phase 1 简化映射（MVP）

| Phase 1 阶段 | 映射到 S1-S9 | 说明 |
|--------------|--------------|------|
| `contract` | S1 | 模块契约兜底 |
| `defaults` | S2 | catalog defaults + default tags |
| `governance` | S3 + S6 + S9 | Phase 1 只放平台强制 tag、state key、少量硬规则；复杂 layer/team policy Phase 2 展开 |
| `user` | S8 | 用户表单显式输入 |
| `dependency` | S7 | 跨层依赖图，Phase 1 可只支持固定 Global VPC 依赖 |

Phase 1 不引入完整 env/tenant/binding 解析，默认 `tenant=platform-default`，env 仅作为表单和路径上下文。进入 Phase 2 后，`governance` 拆回 S3/S6/S9，`dependency` 与 S4/S5/S7 按下表完整执行。

| # | 阶段 | source | 优先级 rank | 拒绝门 |
|---|------|--------|-----------|--------|
| S1 | 模块契约载入 | `module_versions.variables_contract_json` | 8（兜底）| 必填字段缺失 |
| S2 | catalog defaults | `catalog_items.default_values_json` + L6 default_tags | 7 | 类型不匹配 |
| S3 | **layer rule 注入** | `layer_rule_set_versions` (D26 pinned) | **2（治理硬规则）** | 用户值违反 rule（如 region 不在 allowed） |
| S4 | **环境上下文绑定** | `environments` + `environment_tenant_bindings` (D27) | 6（上下文）| (env, tenant, layer) 无 binding |
| S5 | **tenant 上下文绑定** | `tenants.tag_namespace_json` (L3) + tenant 网络 | 5（上下文）| tenant.kind=external 引用共享资源 |
| S6 | **team 策略** | `teams.policy_json`（allowed_regions/cost_cap/mandatory_tags L4） | **3（治理类）** | 成本超 2x cap（硬上限拒绝）；1x~2x cap 标记 cost_overrun 透传 pre-apply |
| S7 | 跨层依赖注入 | `stack_dependencies` 解析图 → remote_state/data source | 6（上下文）| 依赖不存在 |
| S8 | **用户表单** | `requests.form_values_json`（含 L7 user tags） | **4（用户显式）** | 类型/枚举不符 |
| S9 | **平台强制注入** | 平台常量：L1 tags、ownership metadata | **1（绝对）** | （不拒绝，silently 覆盖）|

**最终优先级**：S9(1) > S3(2) > S6(3) > S8(4) > S5(5) > S4/S7(6) > S2(7) > S1(8)。

**同 rank tie-breaker（S4 vs S7）**：S4(env binding) > S7(dep graph)。S4 注入 `vpc_stack_id`（元变量——哪个 VPC stack 属于此 stack），S7 用它生成 `terraform_remote_state` data source + 变量绑定。两者协作不冲突：S4 告诉 S7 引用**哪个** stack，S7 生成**如何**引用。当两者试图设同一变量的值时，S4 赢（binding 是平台治理决策 > dep graph 是实现细节）。

### 3.1 治理类 vs 用户类 vs 上下文类（核心区分）

- **治理类（rank 1/2/3，S3/S6/S9）**：layer rule / team policy / platform mandate——治理永远赢，用户填了也是被覆盖（留痕 `user_attempted_override=true`）
- **用户类（rank 4，S8）**：用户显式选择——用户高于上下文与 catalog 默认
- **上下文类（rank 5/6，S4/S5/S7）**：env/tenant/依赖——用户不填时自动注入；用户填了覆盖上下文（rank 4 > 5/6）

### 3.2 为什么 S3/S6 治理类高于 S8 用户

specs/05 原始优先级「平台强制 > 表单 > defaults > 契约」中，"平台强制"实际包含 layer rule + team policy + platform mandatory 三类。D28 显式拆分：
- **layer rule (S3) 强制治理**：如 prod 强制 `encrypt_at_rest=true`——用户填 false 也必须 true
- **team policy (S6) 治理**：如团队 cost_cap——用户选大规格超 **2x cap** 直接拒绝（安全阀）；**1x~2x cap** 标记 `cost_overrun=true` 透传到 pre-apply 门，D21 审批 DSL `when: cost_overrun` 插入成本升级审批节点（更高级别审批人决定）
- **platform mandatory (S9) 绝对**：tag/ownership 元数据

这是 specs/05 模型的**精确化**，不是推翻。

## 4. Provenance 审计（resolved_params_json）

每变量 MUST 含 `{value, source, rank, ...}`。完整结构：

```json
{
  "instance_type": {
    "value": "mysql.n2.large.1c",
    "source": "user_form",
    "rank": 4,
    "overridden_from": {"value": "mysql.n2.medium.1c", "source": "catalog_default", "rank": 7}
  },
  "vpc_id": {
    "value": "vpc-bp1xxx",
    "source": "env_context",
    "rank": 6,
    "env_id": "env-prod",
    "tenant_id": "tenant-corp-a",
    "binding_id": "etb-xxx",
    "vpc_stack_id": "stack-vpc-corpA-prod"
  },
  "encrypt_at_rest": {
    "value": true,
    "source": "layer_rule",
    "rank": 2,
    "rule_id": "rule-prod-encrypt-mandatory",
    "user_attempted_override": true,
    "user_attempted_value": false
  },
  "storage": {
    "value": 200,
    "source": "module_contract",
    "rank": 8,
    "note": "用户未填，catalog 无 default，走模块 variables.tf 默认值"
  },
  "tags": {
    "value": {
      "platform-managed": "true", "platform-team": "dba",
      "platform-bundle": "orders", "platform-stack": "rds-orders-prod",
      "env": "prod", "tenant": "corp-a",
      "app": "order-service", "owner": "zhangsan"
    },
    "source": "merged",
    "rank": null,
    "layers_applied": ["L1","L2","L3","L4","L5","L6","L7"],
    "user_overrides_blocked": [],
    "layers_merged_summary": {
      "L1": ["platform-managed","platform-team","platform-bundle","platform-stack"],
      "L2": ["env","cost-center"],
      "L3": ["tenant","compliance"],
      "L6": ["app"],
      "L7": ["owner"]
    }
  }
}
```

### 4.1 Provenance 用途

| 场景 | 谁用 | 例子 |
|------|------|------|
| 申请审批 | 审批人 | "vpc_id 哪来的？env_context 自动注入" |
| AI 审计（D17） | AI 审计追溯 | "LLM 决策参数链路、用户填了什么 vs 平台改了什么" |
| 故障排查 | SRE/运维 | "为什么 encrypt=true？layer rule 强制，user 想关但被覆盖" |
| 治理报表 | FinOps/合规 | "多少用户值实际生效 / 多少被治理覆盖" |
| D26 迁移 | MigrationPlanner | "哪些 stack 用了 layer rule v1 的强制 tag" |

### 4.2 provenance 不变量

- 每个 requests MUST 在 codegen 完成后写 `resolved_params_json`
- 每变量 MUST 有 `source` + `rank`（tags 字段例外，source=merged）
- 治理类覆盖用户类 MUST 记 `user_attempted_override=true` + `user_attempted_value`
- L1/L5 永远在最终 tags.layers_applied 中（缺失 → 报警）
- 同变量同阶段不能两个 source 同时为真（rank 高者覆盖）

## 5. 冲突解析示例

### 示例 1：用户填 storage=200，catalog defaults storage=100
```
S2: storage=100 (rank 7, source=catalog_default)
S8: storage=200 (rank 4, source=user_form)
最终: storage=200, provenance.source=user_form, overridden_from.catalog_default=100
```

### 示例 2：vpc_id 用户不填
```
S4: vpc_id="vpc-bp1xxx" (rank 6, source=env_context)
S8: 未传
最终: vpc_id="vpc-bp1xxx", source=env_context, env_id/binding_id 记录
```

### 示例 3：encrypt_at_rest 治理强制 true，用户填 false
```
S3: encrypt_at_rest=true (rank 2, source=layer_rule, rule_id=...)
S8: encrypt_at_rest=false (rank 4, source=user_form)
最终: encrypt_at_rest=true, source=layer_rule
      user_attempted_override=true, user_attempted_value=false（治理违规留痕）
```

### 示例 4：tags 完整合并
```
L1: {platform-managed:true, platform-team:dba, platform-bundle:orders}
L2: {env:prod, cost-center:CC-P-01}  (env tag_namespace)
L3: {tenant:corp-a, compliance:pci}  (tenant tag_namespace)
L4: {team-tag:dba-extra}              (team tags_json)
L5: {platform-stack:rds-orders-prod}  (codegen 自动)
L6: {app:order-service}               (catalog default_tags)
L7: {owner:zhangsan}                  (user form, 白名单内)
   用户尝试加: {platform-managed:false, secret-key:xxx}
   - platform-managed=false: L1 覆盖（silently ignore）→ user_overrides_blocked
   - secret-key: 不在 user_allowed_tag_keys 白名单 → 拒绝整个 form

最终: 9 个 tag（L1+L2+L3+L4+L5+L6+L7 合并），layers_applied=7, user_overrides_blocked=[platform-managed]
```

## 6. 业界对照

| 平台/工具 | 分层模型 | provenance |
|----------|---------|-----------|
| Helm values | subchart → parent chart → -f file → --set | 无显式 provenance |
| Kustomize | base + overlay (strategic merge patch) | per-field source |
| Terraform 变量 | TF_VAR_* > *.auto.tfvars > *.tfvars > -var > default | 无 provenance |
| **Spacelift Contexts** | 多 Context mount + priority | UI 展示来源 |
| **Crossplane Functions** | pipeline + each Function mutate | resource history |
| **AWS Tag Policies** | 组织级 mandatory + 用户白名单 | CloudTrail 审计 |
| **本设计（D28）** | 7 层 tag + 9 阶段参数 | resolved_params_json 全量 provenance |

## 7. 与现有设计的关系

- **specs/05 四输入合并**：D28 演化为 9 阶段（原四输入保留，前后插入新阶段）；specs/05 表述更新为「9 阶段管道，详见 specs/18」
- **docs/09 代码生成**：§4 重写为「9 阶段管道（详见 docs/08）」+ provenance 输出契约
- **docs/14 §3 强制 tag**：改为「7 层 tag 来源（详见 docs/08 §2）」；ingester 校验改为「7 层合并后的 tag 一致性」
- **D26 layer rule**：D28 S3 阶段只是 reader，layer_rule_set_versions 表不动
- **D27 env/tenant**：D28 S4/S5 阶段查询 environment_tenant_bindings + tenants，不重复定义

## 8. 选型

| 用途 | 选型 | 说明 |
|------|------|------|
| Tag 合并 | Go 内置 `merge` + 自实现优先级 | 简单逻辑，无需三方库 |
| Provenance 序列化 | JSON（resolved_params_json） | 可审计、可查询 |
| 白名单校验 | OPA Rego（D7 PolicyEngine） | 复用现有策略引擎 |
| Tag 值校验 | 云厂商 SDK 自带 + 自实现保留字 | per-provider adapter |

## 9. 关键时序

```
工单 generating 阶段：
  [S1 载入模块契约]
  → [S2 注入 catalog defaults]
  → [S3 应用 layer rule（rank 2 治理硬规则）]
  → [S4 解析 env 上下文（rank 6，从 environment_tenant_bindings）]
  → [S5 解析 tenant 上下文（rank 5）]
  → [S6 应用 team policy（rank 3 治理）]
  → [S7 解析跨层依赖（rank 6 上下文，同 rank S4 优先）]
  → [S8 应用用户表单（rank 4）]
  → [S9 平台强制注入（rank 1）]
  → [写 resolved_params_json]
  → [校验门复检：L1 tag 完整性 + 白名单 + 类型]
  → [生成 Terraform 代码]
  → [generating→planning 状态转移]
```
