# 07-环境与租户网络模型

> 对应 design `D27`、spec `specs/17-环境与租户`。回应：多个租户/多个独立 VPC 如何创建环境、分层之间网络如何绑定、跨租户如何互通。

## 1. 为什么需要 env/tenant 一等对象

D1-D26 覆盖了 `layer / stack / bundle / team / cloud_account` 五维，但**多租户、多独立 VPC、env 维度授权全部空白**。痛点：

| 场景 | 当前痛点 | D27 解决 |
|------|---------|---------|
| 业务团队 A 的 prod 环境 ECS 接哪段 VPC？ | 散落在 catalog defaults / 模块变量 / 手填 | Stage 4 自动从 binding 解析 |
| 外部客户 corp-a 隔离内部团队 | 只能靠不同 team_id（弱） | 独立 tenant + 独立 VPC（强） |
| prod 环境严审批 / dev 自助 | 没有治理强度差异化的载体 | env.stage 字段驱动 |
| 内部团队共享 VPC 省成本 | 无明确"共享"概念 | `platform-default` 单租户 + 共享 VPC |

业界现状（2026）：内部平台 / B2B SaaS 收敛到 **VPC-per-env**（一个 tenant × 一个 env = 一个 VPC），账号级退缩到金融/外部客户硬合规。理由：自服务诉求 + FinOps tag 归集成熟 + K8s namespace 思维外溢 → VPC 是云原生等价的"租户边界"。

## 2. 核心抽象（3 表，权威见 docs/04 §2.13）

```
environments(id, env_logical_id, stage, cloud_account_id, region,
             tag_namespace_json, network_topology, status)
tenants(id, tenant_logical_id, name, isolation_level[vpc-per-env|account-per-env],
        kind, owner_team_id, tag_namespace_json, status)
environment_tenant_bindings(id, env_id, tenant_id, layer_logical_id,
                            vpc_stack_id, subnet_blocks_json,
                            security_group_base_id, override_cloud_account_id, status)
```

### 2.1 Environment（一等治理对象）

| 字段 | 说明 | 示例 |
|------|------|------|
| env_logical_id | 稳定身份 | `prod` / `staging` / `dev` / `dr-hot` |
| stage | 治理强度分级 | `prod` → 强审批 + 双签 / `dev` → 自动放行 |
| cloud_account_id | 默认云账号 | escape hatch 时 binding override |
| region | 主区域 | `cn-hangzhou` |
| tag_namespace_json | L2 env tag | `{"env":"prod","cost-center":"CC-P-01"}` |
| network_topology | 网络拓扑模式 | `shared` / `distributed` |

**stacks.env 字段保留**：作为反规范化便利（快速过滤），权威以 environments 表为准。

### 2.2 Tenant（一等对象，默认 `platform-default`）

| isolation_level | 何时用 | 实现 |
|-----------------|--------|------|
| **vpc-per-env**（默认） | 内部 BU / B2B SaaS / 中等合规 | 每 tenant+env 一个独立 VPC，binding.vpc_stack_id 引用 |
| **account-per-env**（escape hatch） | 金融/政企/外部客户硬合规 | binding.override_cloud_account_id 必填，覆盖 environments.cloud_account_id |

**为什么不保留 shared-vpc 档**：
- "内部多团队共享 VPC 省成本"场景用 `platform-default` 单租户 + 共享 VPC 表达即可（一个 VPC，所有团队共享）
- 三档可配是过度设计，UI/表/校验复杂度激增
- 业界 2026+ 已收敛到 VPC 级，shared-vpc 是退步

`kind=external` 仍保留为 informational 字段（不驱动隔离逻辑，仅用于审计/统计"外部客户 vs 内部"占比）。

### 2.3 EnvironmentTenantBinding（三元组，codegen Stage 4 查询入口）

UNIQUE 约束：`(env_id, tenant_id, layer_logical_id)`。

| 字段 | 说明 |
|------|------|
| env_id + tenant_id + layer_logical_id | 三元组（D26 layer_logical_id 引用稳定身份） |
| vpc_stack_id | 引用 Global 层 VPC stack（MUST 输出 `vpc_id` + `vswitch_ids`） |
| subnet_blocks_json | 该 (tenant, env) 的子网 CIDR 列表 |
| security_group_base_id | 基础安全组（业务层加规则继承） |
| override_cloud_account_id | account-per-env 模式必填 |

**多 layer 共享 VPC**：同 (env, tenant) 的 Middleware + Application binding 可引用同一 vpc_stack_id（共一个 VPC），也可引用不同 vpc_stack_id（独立 VPC）。设计自由，由治理策略决定。

## 3. 创建环境向导（5 步）

```
[1. 选 env_logical_id + stage]
   ↓ 平台校验 env_logical_id 唯一
[2. 选云账号 + region]
   ↓ 从 cloud_accounts where status=active 列表选
[3. 配置 env tag_namespace_json（L2 tag）]
   ↓ 默认 {"env": "<logical_id>"}，可加 cost-center/compliance 等
[4. 创建 tenant（可选）]
   ↓ 默认 platform-default；外部客户/独立 BU 时新建，选 isolation_level
[5. 配置 environment_tenant_bindings（每层一条）]
   ↓ 选/创建 Global 层 VPC stack → 填子网块 → 选安全组
[完成] environments + tenants + bindings 落库，UI 入"环境管理"导航
```

**自动校验**（向导提交时）：
- vpc_stack_id 引用的 stack MUST 是 Global 层
- 该 stack outputs MUST 含 `vpc_id` + `vswitch_ids`
- 同 (env, tenant) 的不同 layer binding 引用的 vpc_stack_id MUST 在同 cloud_account_id（除非 account-per-env 显式 override）
- account-per-env 模式下 override_cloud_account_id MUST ≠ environments.cloud_account_id

## 4. PathGenerator 与 D27 的衔接（D24 不动）

D24 PathGenerator 已支持 `${env}` 变量。D27 新增 `${tenant}` 变量（PathGenerator `custom_kv` 扩展）：

```
# AI Generated Start
路径模板（layer rule v1，D29 layer-first）：
  Global:      global/${component}-${tenant}-${env}
  Middleware:  middleware/${tenant}/${component}-${env}
  Application: application/${tenant}/${owning_team}/${component}-${env}

state_key 默认等于 repo_path
# AI Generated End
```

**default tenant = `platform-default`**：路径如 `application/platform-default/team-a/ecs-prod`。历史 tenant-first 路径只能作为 import/迁移场景显式兼容，不能作为新 stack 输出目标。

## 5. 跨租户网络（CEN）

```
┌─────────────────────────────────────────┐
│ Global 层                                │
│                                          │
│ cen-platform-prod stack                  │
│ ├── CEN 实例: cen-xxx                    │
│ ├── 加载: vpc-platform-prod              │
│ ├── 加载: vpc-corpA-prod                 │
│ └── 加载: vpc-corpB-prod                 │
│                                          │
│ 路由: corpA <-> DBA (RDS 共享)            │
│ 路由: corpA x corpB (默认拒绝)           │
└─────────────────────────────────────────┘
```

- 跨租户网络治理是**独立的 Global 层 stack**（`cen-<env>`），不进 environment_tenant_bindings 表
- 路由策略（允许/拒绝）通过 catalog 项 + 审批治理（"corpA 申请访问 DBA 的 RDS"作为 cross-layer 依赖请求）
- 业界对照：阿里云 CEN / AWS Transit Gateway / Azure vNet Peering——成熟方案

## 6. 业界对照

| 平台 | env/tenant 模型 | 隔离边界 |
|------|----------------|---------|
| AWS Control Tower | Account Factory（per-BU account） | 账号级（强合规场景）|
| HashiCorp TFC | workspace + variable set + env label | workspace/VPC 级 |
| Spacelift | stack + Contexts + VPC binding | **VPC-per-env**（事实标准）|
| Crossplane | XR (Environment) composite | namespace/VPC 级 |
| Env0 | environment promotion（dev→prod）| VPC 级 |
| 阿里云 Resource Directory + CEN | 资源账号（escape）/ 共享账号 + VPC | VPC 级主流 |
| **本设计** | **Environment + Tenant + Binding（VPC-per-env 默认）** | **VPC-per-env 默认 + account-per-env escape** |

## 7. 与现有设计的关系

- **D24 PathGenerator**：扩展 `${tenant}` 变量（不破坏现有 `${env}`）
- **D26 layer 规则**：binding.layer_logical_id 引用 layer_logical_refs（稳定身份）
- **D23 cloud_credentials**：account-per-env 模式的 override 账号走 D23 标准 OIDC 凭据流程
- **specs/02 服务目录**：catalog 项不变（layer_logical_id 既有）
- **docs/06 team_cloud_grants**：新增 env_scope_json 字段（env 维度授权）
- **docs/14 CMDB/FinOps**：resources 表加 `tenant_id` 反规范化字段（成本归集）
- **docs/09 codegen**：Stage 4 环境上下文绑定查 environment_tenant_bindings

## 8. 选型

| 用途 | 选型 | 说明 |
|------|------|------|
| VPC 生命周期 | Terraform module（Global 层 stack） | 已有能力，不重新抽象 |
| 跨租户网络 | CEN / VPC Peering / Transit Gateway | 适配器化（CloudProvider interface D7）|
| 子网 CIDR 分配 | 平台内 IPAM（可选） | 简单场景静态分配，规模化引入 phpIPAM/NetBox |

## 9. 关键时序

```
管理员创建环境:
  [创建 env: prod] → [创建/选 cloud_account] → [配置 env tag_namespace]
  → [创建 tenant: corp-a (isolation=vpc-per-env)] → [配置 tag_namespace]
  → [创建/选 Global 层 vpc stack: vpc-corpA-prod]
  → [创建 environment_tenant_bindings: prod+corp-a+Application → vpc-corpA-prod]
  → 落库 + UI 入"环境管理"

业务申请 ECS（自动消费 binding）:
  [用户填表选 env=prod tenant=corp-a]
  → codegen Stage 4: 查 environment_tenant_bindings WHERE env=prod AND tenant=corp-a AND layer=Application
  → 拿到 vpc_stack_id=vpc-corpA-prod, subnet_blocks=[10.0.1.0/24,...]
  → 注入 Terraform 变量 vpc_id/subnet_ids
  → resolved_params_json 记 source=env_context, rank=6
```

## 10. Environment Promotion（商业级扩展）

Phase 2 起，Environment 不只是目标字段，还承载 dev → staging → prod 的晋级工作流。

| 阶段 | 行为 |
|------|------|
| `promote-plan` | 读取源 env 的 catalog item、form_hash、resolved params，生成目标 env 的参数 diff |
| `binding-diff` | 展示目标 env 的 VPC、subnet、cloud_account、team grant 差异 |
| `policy-check` | 按目标 env stage 重新跑 OPA、Run Hooks、预算校验 |
| `approval` | prod 晋级必须走更高审批级别 |
| `apply` | 使用目标 env 的 PathGeneratorOutput 生成独立 stack/state |

核心约束：

- Promotion 不是复制 state，而是同一 catalog item 在新 env 生成新的 stack。
- 用户显式参数可继承，环境上下文必须重新解析。
- prod 不能直接从未验证的 dev 参数静默晋级，必须展示 diff。
- promotion run 与普通 request 共享 RequestLifecycle 和 plan artifact。
