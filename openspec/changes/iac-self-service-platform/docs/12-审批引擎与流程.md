# 12-审批引擎与流程

> 对应 design `D11`、spec `specs/10-审批引擎`。重点回应 Q3：自研 vs Flowable(Java) vs Go 替代。

## 1. 选型结论：自研轻量 DSL，保留 Temporal 升级路径

| 方案 | 适配审批 | 运维成本 | Go 友好 | 结论 |
|------|----------|----------|---------|------|
| 自研 DSL + 状态机 | 中等复杂度够用 | 零外部依赖 | ✅ | **MVP 采用** |
| Temporal | 强（durable、重试） | 高（Temporal Server 集群） | ✅ Go-native | 复杂度爆发后升级 |
| Camunda 8/Zeebe | 强（BPMN 可视化） | 高（Zeebe+ES） | 弱（Go 社区公认过重） | ❌ |
| Flowable | 强 | 中（JVM） | ❌ Java | 排除（团队 Go） |
| Argo Workflows | 偏数据/CI | 需 K8s | 弱审批 | ❌ |

**依据**（2025 WebSearch）：Temporal 是"可靠的工程师"（workflow-as-code、durable），Camunda 是"业务流程规划师"（BPMN、非技术干系人）；Go 社区认为 Camunda 对轻量审批过重。IaC 平台友商（Spacelift/Env0）审批本质是"角色路由"，非完整 BPMN。

## 2. 审批 DSL（YAML）

### 2.1 完整示例（RDS prod 申请，双门禁）

```yaml
# approval_flows/rds-prod.yaml
# 触发条件：catalog 项 + 环境 + 层决定走哪个 flow
match:
  catalog_item: "dba/rds"
  env: ["prod"]                      # dev/staging 走简化 flow（见 §2.2）
  layer: "middleware"

# ===== 第一道门禁：准入审批（pre-plan，OPA 可自动放行低危）=====
gate: pre-plan
flow:
  - id: business_lead_approve
    approver:
      team: "{{ requester.team }}"   # 运行时从 request.team_id 解析
      role: "lead"                   # RBAC 角色，非具体人
    timeout: 24h
    on_timeout:
      escalate:
        approver: { team: "{{ requester.team }}", role: "director" }
        timeout: 12h                 # 升级后再给 12h
        on_timeout: { action: auto_reject, reason: "approval_timeout_escalated" }

  - id: dba_review                   # DBA 会签
    approver:
      team: "dba"
      role: "approver"
    mode: majority                   # any(任一) | all(全员) | majority(过半) | count>=N
    min_approvers: 2                 # 至少 2 人签（会签）
    timeout: 48h
    on_timeout:
      escalate: { approver: { team: "dba", role: "director" } }

  - id: cost_gate                    # 条件分支：成本超阈值才触发
    when: "estimated_cost > 5000"    # USD/月
    approver: { team: "platform-ops", role: "finops-approver" }
    timeout: 24h

  - id: security_review              # 条件分支：敏感数据才触发
    when: "request.form_json.encrypt_at_rest == false or request.form_json.public_access == true"
    approver: { team: "security", role: "reviewer" }
    mode: all
    timeout: 48h

# ===== 第二道门禁：执行确认（pre-apply，不可免审，输入=plan 差异）=====
gate: pre-apply
flow:
  - id: confirm_after_plan
    approver:
      team: "{{ requester.team }}"
      role: "lead"
    inputs:                          # 审批者看到的决策上下文
      - plan_diff                    # terraform plan 差异摘要
      - estimated_cost               # Infracost 预估
      - drift_check                  # 漂移护栏校验结果
      - security_scan                # OPA 策略校验结果
    timeout: 48h
    on_timeout:
      escalate:
        approver: { team: "{{ requester.team }}", role: "director" }
        timeout: 24h

  - id: dba_final_confirm
    approver: { team: "dba", role: "approver" }
    mode: any
    inputs: [plan_diff, drift_check]
    timeout: 24h

# 驳回策略
reject:
  default: { target: "business_lead_approve", allow_comment: true }  # 默认回退到首节点
  nodes:                             # 特定节点驳回到不同目标
    dba_review: { target: "business_lead_approve" }
    confirm_after_plan: { target: "business_lead_approve", reason_required: true }
  terminal:                          # 终态驳回（不可修改重提）
    when: "request.retry_count >= 3"
    action: "rejected"
```

### 2.2 简化 flow（dev/staging 自助，OPA 自动放行）

```yaml
match:
  catalog_item: "dba/rds"
  env: ["dev", "staging"]

gate: pre-plan
flow:
  - id: auto_approve
    auto: true                       # OPA 校验通过后自动放行（低危场景）
    condition: "estimated_cost < 1000 and layer != 'global'"

gate: pre-apply
flow:
  - id: self_confirm
    approver: { team: "{{ requester.team }}", role: "lead" }
    timeout: 12h
```

### 2.3 DSL 语法要点

| 语法 | 含义 | 示例 |
|------|------|------|
| `approver.team + role` | 绑 RBAC 角色（非人），运行时解析 | `{ team: "dba", role: "approver" }` |
| `mode` | 会签模式 | `any`/`all`/`majority`/`count>=3` |
| `min_approvers` | 最少签字数 | `2`（会签至少 2 人） |
| `when` | 条件分支（Go expr 语法） | `estimated_cost > 5000` |
| `timeout` | 超时时长 | `24h` / `48h` |
| `on_timeout.escalate` | 超时升级（可链式） | 升级到 director → 再超时 auto_reject |
| `inputs` | 审批者可见的决策上下文 | `plan_diff`/`estimated_cost`/`drift_check` |
| `reject.target` | 驳回回退节点 | `business_lead_approve`（回退修改） |
| `reject.terminal` | 终态驳回（不可重提） | `retry_count >= 3` |
| `{{ requester.team }}` | 模板变量（Go template） | 运行时从 request 上下文注入 |

## 3. 双门禁 + plan/apply 解耦（D21，回答"如何与执行交互"）

> 关键结论：**两道门，不是一个审批**。同一 `ApprovalEngine`，流水线挂起两个独立审批流；plan 与 apply 是两次独立 Executor 调用，中间状态机阻塞、沙箱释放。

### 3.1 两门语义

| 门 | 位置 | 判断 | 输入 | 审批人 | 可否免审 |
|----|------|------|------|--------|----------|
| **准入审批**（admission） | generating 后 / planning 前 | 此申请是否被授权执行 | 申请元数据 + OPA 结论 + **当前 stack 漂移状态**（最新 drift_record.status，已漂移则告警）+ **迁移静默期标识**（若 stack 在 layer 规则迁移 QuiesceMode 中，阻断）+ **预算预校验**（Infracost 估算 vs cost_budgets 阈值，超则升级节点）| 项目经理/资源 owner | 低危可 OPA 自动放行（但 AI actor 触发的高危场景除外，见 docs/17 §9.1）|
| **执行确认审批**（pre-apply） | planning 后 / applying 前 | plan 产物是否可安全落地 | **plan 差异摘要 + Infracost 成本 + plan 后漂移校验 + 成本趋势**（最近 3 个月 cost_records 历史曲线，便于判断"是否长期上升/突变"）+ **关联 stack 当前漂移状态**（plan 期间若发生漂移，标红警示）+ **迁移期标识**（若涉及 D26 迁移中的 stack，提示风险）| 理解 diff 的人（DBA/运维/资源 owner） | **不可免审**（破坏性 apply 必人审） |

业界全是两门：Terraform Cloud（plan 权限 + confirm&apply）、Spacelift（access + plan approval）、Atlantis（PR + plan 注释 + apply 注释）、Env0。

### 3.2 状态机（两门显式）

```
submitted → generating(codegen→commit→pinned_commit)
  → pending-admission?(Gate1：准入，低危可 OPA 直通)
  → planning(Executor 只读 plan，产出差异/成本/漂移校验 → 上传 plan 产物 → 销毁沙箱)
  → plan-ready(artifact sha256/toolchain/provider lock 校验完成)
  → pending-approval(Gate2：执行确认，UI 展示 plan diff/漂移，审批人决策)
  → applying(新沙箱检出 pinned_commit + 下载 plan 产物 → TerramateAdapter.RunApplySavedPlan → 回写 → 销毁)
  → reconciling(CMDB/通知/成本/outbox 异步补偿)
  → succeeded | reconcile-pending | rejected | expired | waiting-manual | failed-*
```

异常状态语义：

| 状态 | 语义 | 处理 |
|------|------|------|
| `expired` | plan artifact 超过 TTL 或工具链/provider hash 不一致 | 强制重 plan + 重 pre-apply |
| `failed-retryable` | codegen/plan/outbox 等可安全重试失败 | 自动或人工触发重试 |
| `failed-terminal` | 策略拒绝、不可恢复输入错误 | 终态，需新 request |
| `waiting-manual` | apply 中断、state 不确定、导入半成功等 | 生成 `manual_intervention_tasks` |
| `reconcile-pending` | apply 已成功但 CMDB/通知/成本等旁路失败 | outbox/reconcile 重放，不回滚资源 |

### 3.2.1 Request status 与审批子状态边界

为避免 `requests.status` 膨胀成审批引擎内部状态，以下语义必须分层存储：

| 语义 | 存储位置 | `requests.status` 如何表现 |
|------|----------|----------------------------|
| 审批升级 `escalation` | `approval_runs` / `approval_nodes` | 保持 `pending-admission` 或 `pending-approval` |
| 审批超时自动拒绝 | `approval_runs` 记录 timeout，`request_events` 记录迁移 | 迁移到 `rejected` 或 `expired` |
| break-glass 执行中 | `emergency_runs.status=active` | 保持 `applying`，并在 `request_events` 标记 emergency mode |
| break-glass 事后补审批 | `emergency_runs.retroactive_approval_id` + `approval_runs` | apply 成功后仍走 `reconciling` / `succeeded`，超时则创建 `incidents` |
| run hook 阻断 | `run_hook_results.decision=deny` | `blocked-policy` |

`requests.status` 只表示主链路可恢复状态；审批升级、节点会签、break-glass 补审批是子域状态，不作为并列 request status，除非它改变主链路推进。

### 3.3 plan/apply 解耦（关键工程决策）

```
[plan 阶段]
  Executor.Run(terramate run -- terraform plan -out=<plan>)
  → 解析 plan JSON + Infracost 估算 + 轻量漂移校验
  → plan 产物（-out 二进制 + 摘要 JSON）上传对象存储，关联 request_id
  → ★ 销毁沙箱（不占容器/进程等待人数小时的人审）★
[阻塞阶段] 状态机 pending-approval → 挂起执行确认审批流 → 通知 → UI 展示
[apply 阶段]（审批通过）
  → 新沙箱 Executor 检出同一 pinned_commit
  → 下载 plan 产物 → TerramateAdapter.RunApplySavedPlan（`terramate run -- terraform apply "<plan>"`，精确按已审 plan，不重 plan）
  → 回写 → 销毁
[漂移护栏] apply 前若漂移检测发现世界已变 → 告警 + 要求重 plan（已审 plan 过期）
```

**为什么不保持沙箱等审**：人审可能数小时，保持容器/进程占资源不合理（Spacelift/Env0 均释放 worker）。plan 产物持久化保证 apply 精确执行已审内容（不重 plan，diff 与审批一致）。

### 3.4 审批与执行沙箱解耦

审批在**状态机层**阻塞，不依赖任何存活容器/进程。`ApprovalEngine.Start/Decide/Status` 操作的是 `approval_runs` + plan 产物引用，Executor 已销毁也不影响审批进行。这使"plan 在 A 节点跑、审批花半天、apply 在 B 节点跑"成为可能（跨节点/跨时间）。

### 3.5 沙箱销毁与 plan 产物生命周期（精确边界）

| 事件 | 沙箱动作 | plan 产物动作 | 工单状态 |
|------|---------|--------------|---------|
| **plan 完成** | 上传 plan.tfplan 到对象存储 + 写 `artifacts(kind=plan_binary, sha256)` 后**立即销毁** | 保留（artifacts 表引用）| `planning` → `plan-ready` → `pending-approval` |
| **审批通过** | apply 阶段申请新沙箱（按 Executor 配置可能不同节点）| 按 `request_id` 查最新 `plan_binary` 下载 + sha256 校验 | → `applying` |
| **审批驳回** | — | 保留 N 天（默认 7，供审计/复盘）→ GC；工单可修订后重提（生成新 plan_binary）| → `rejected`（终态）|
| **审批超时** | — | 同驳回 | 保持 `pending-approval` 并写审批子状态，或按 DSL 自动驳回到 `rejected` |
| **漂移护栏触发**（apply 前发现世界已变）| apply 沙箱销毁，不执行 apply | 旧 plan_binary 标 `superseded`；要求重 plan，生成新 plan_binary | → 回到 `planning` |
| **apply 成功** | 销毁 | 保留 N 天（默认 30，高危 90）→ GC | → `reconciling` → `succeeded` 或 `reconcile-pending` |
| **apply 失败** | 销毁 | 保留更久（默认 90 天）供排障 | → `failed-retryable` 或 `waiting-manual`（state 不确定时禁止自动重试）|
| **沙箱销毁失败**（容器/进程僵死）| Executor 重试 3 次 → 标 `workspace_checkouts.status=stale`，由对账任务清理（docs/10 §8）| 不影响 plan 产物 | 不阻塞审批/apply |

**核心不变量**：**plan 产物的存活 ≠ 沙箱的存活**。沙箱是临时的执行载体，plan 产物是审计与跨沙箱传递的载体。两者解耦后，审批可以跨小时、跨节点、跨重启进行。

**幂等性**：apply 阶段下载的 plan.tfplan 是 sha256 校验过的二进制快照。正常失败可基于同一 `pinned_commit + plan_binary + toolchain hash` 受控重试；若 Executor 中断、state lock 异常、网络超时导致 state 不确定，必须转 `waiting-manual`，先人工 state 检查，不做盲重试。

```go
func resolveApprovers(node ApproverNode, ctx RequestContext) []Identity {
    // node.Team + node.Role → 查 role_bindings + 当前 identities
    return identityStore.Query(ctx, node.Team, node.Role)
}
```
人员离职/调岗经身份同步自动生效，**流程定义不变**。

## 4. 状态机 × 事件迁移矩阵（精确边界）

> 此矩阵定义 orchestrator（specs/06）在每种状态下收到每种事件时的**精确动作**：目标状态 + worktree 处理 + plan 产物处理。实现时 MUST 遵守。

| 当前状态 | 事件 | → 目标状态 | worktree 动作 | plan 产物动作 |
|----------|------|-----------|--------------|--------------|
| `submitted` | `accepted` | → `generating` | — | — |
| `generating` | `codegen_done` | → `pending-admission` | commit + push，worktree 保留 | — |
| `generating` | `codegen_fail` | → `failed-retryable` | 销毁 | — |
| `pending-admission` | `admit_approved` | → `planning` | 检出 worktree（pinned_commit） | — |
| `pending-admission` | `admit_rejected` | → `rejected`(终态) | 销毁 | — |
| `pending-admission` | `admit_timeout` | → `rejected`(终态) | 销毁 | — |
| `planning` | `plan_done` | → `plan-ready` | **★ 销毁（释放沙箱）** | 上传 plan.tfplan → artifacts(kind=plan_binary) |
| `plan-ready` | `approval_started` | → `pending-approval` | — | 校验 sha256/TTL/toolchain/provider hash |
| `planning` | `plan_fail` | → `failed-retryable` | 销毁 | — |
| `pending-approval` | `approval_pass` | → `applying` | **新 worktree**（检出 pinned_commit） | 下载 plan.tfplan（sha256 校验） |
| `pending-approval` | `approval_reject` | → `rejected`(终态) | — | 保留 7 天 → GC |
| `pending-approval` | `approval_timeout` | → `pending-approval` 或 `rejected` | — | 升级写入 `approval_runs` / `approval_nodes`；若 DSL auto_reject 则转 `rejected` |
| `pending-approval` | `approval_pass_after_escalation` | → `applying` | 新 worktree | 下载 plan.tfplan；升级过程只存在审批子状态 |
| `pending-approval` | `approval_reject_after_escalation` | → `rejected`(终态) | — | 保留 7 天 → GC |
| `pending-approval` | `approval_timeout_auto_reject` | → `rejected`(终态) | — | 保留 7 天 → GC |
| `applying` | `apply_success` | → `reconciling` | 销毁 | 保留 30 天（高危 90）→ GC |
| `reconciling` | `reconcile_success` | → `succeeded`(终态) | — | — |
| `reconciling` | `reconcile_fail` | → `reconcile-pending` | — | — |
| `applying` | `apply_fail` | → `failed-retryable` | 销毁 | 保留 90 天供排障 → GC |
| `applying` | `apply_interrupted` | → `waiting-manual` | 销毁或标 stale | 保留 90 天供人工 state 检查 |
| `applying` | `drift_guard` | → `planning`(重 plan) | 销毁 apply 沙箱 | 旧 plan_binary 标 `superseded` |
| `succeeded` | `drift_detected` | → `succeeded`(不变) | — | 触发漂移事件（docs/13） |
| `failed-retryable` | `retry` | → `generating` | 新 worktree | — |
| 任意状态 | `cancel`(用户主动撤销) | → `cancelled`(终态) | 销毁 | 保留 7 天 → GC |
| `pending-admission` | `break_glass`(D30 双人凭据) | → `applying` | 检出 worktree + **全程录屏** | `emergency_runs.status=active`，request 不新增 break-glass 状态 |
| `applying` | `break_glass_apply_success` | → `reconciling` | 销毁 + 录屏存对象存储 90 天 | emergency 证据链继续保留 |
| `reconciling` | `retroactive_approval`(24h 内补审批) | → `succeeded`(终态) | — | emergency_runs.retroactive_approval_id 关联 |
| `succeeded` | `retroactive_timeout`(24h 超时) | → `succeeded`(不变) | — | 自动开 incident；incident 是子域记录，不是 request status |

### 审批 DSL 与 codegen 数据衔接

审批 DSL 的 `when` 条件变量来源：

| DSL 条件变量 | 来源 | 示例 |
|-------------|------|------|
| `estimated_cost` | Infracost 预估（plan 后写入 `requests.estimated_cost_cents`） | `when: estimated_cost > 5000` |
| `cost_overrun` | codegen S6 阶段写入 `resolved_params_json.cost_overrun` | `when: cost_overrun == true` |
| `catalog_item` | `requests.catalog_item_id` → catalog_items.display_name | `when: catalog_item == "dba/rds"` |
| `env` | `requests.env_id` → environments.stage | `when: env == "prod"` |
| `layer` | catalog_items.layer_logical_id | `when: layer == "global"` |
| `request.retry_count` | requests 表（历史同 catalog+user+24h 的 rejected 数） | `when: request.retry_count >= 3` |

**cost_overrun 传递链**：codegen S6 阶段 → `resolved_params_json.cost_overrun = {true, estimated_cents, cap_cents}` → pre-apply 门审批引擎读此字段 → DSL `when: cost_overrun == true` 命中 → 插入成本升级审批节点。

### Break-Glass 与审计的衔接

emergency 操作 MUST 同时写 `audit_logs`（`actor_type=human`，`action=break_glass_apply`，`correlation_id` 与 `emergency_runs.id` 共用），录屏 URL 存 `emergency_runs.recording_url`。24h 内补审批的 `approval_runs` 标 `gate=break-glass-retroactive`，关联 `emergency_runs.retroactive_approval_id`。

### 关键不变量

0. **plan 产物 TTL**：apply 前 MUST 校验 `plan_age < 4h`（`now - plan_completed_at`），过期 → 强制回 `planning` 重 plan + 重 pre-apply 审批；同时校验 `tf_version_sha256` 匹配（plan 与 apply 必须同 Terraform 版本）。
0a. **幂等键防双击**：requests 表 `idempotency_key UNIQUE`，重复 POST 返回已有 request_id + 状态。

1. **plan 产物的存活 ≠ 沙箱的存活**：plan 上传后沙箱立即销毁；审批在状态机层阻塞不占沙箱。
2. **apply MUST NOT 重 plan**：通过 `TerramateAdapter.RunApplySavedPlan` 使用 plan.tfplan 精确执行已审内容（`terramate run -- terraform apply "<plan>"`）。
3. **worktree 不跨审批保持**：plan 和 apply 是两个独立 worktree（可能不同节点），通过 plan.tfplan 桥接。
4. **终态不可逆**：`succeeded`/`failed`/`rejected`/`cancelled` 只能新建工单（新 request_id），不能恢复。
5. **drift_guard 仅 apply 前触发**：apply 沙箱检出后、执行前跑一次轻量 `terraform plan -detailed-exitcode`，exit 2=漂移→回 planning。

## 5. Temporal 升级路径（接口化）

```go
type ApprovalEngine interface {
    Start(ctx, flow FlowDef, reqID string) (RunID, error)
    Decide(ctx, runID, decision Decision) error
    Status(ctx, runID) (RunStatus, error)
}
```
- MVP：`StateMachineEngine` 实现。
- 未来：`TemporalEngine` 实现（DSL → Temporal workflow 编译）。
- 上层 API 不变，切换引擎零业务改动。
