# 05-身份与组织同步

> 对应 design `D10` + `D10.1`、spec `specs/09-身份与组织同步`。重点回应 Q1：飞书/钉钉/企业用户中心/LDAP 如何同步组织，业界最优解。

## 1. 认证架构（多 OIDC issuer 并存 + dex 可选，D10.1）

### 1.0 Standalone 优先原则

平台必须能在不对接外部用户中心、OA、ITSM 的情况下独立运行：

| 能力 | 平台内建 | 外部对接 |
|------|----------|----------|
| 用户身份 | `identities` 本地表、OIDC 登录或本地 bootstrap admin | 企业 OIDC、CAS proxy、dex、飞书/钉钉等可选 |
| 团队与角色 | `teams`、`role_bindings`、`org_mappings` | 外部组织树可同步后映射 |
| 权限判断 | 平台 RBAC 引擎为权威 | 外部组/部门只作为输入，不直接决定权限 |
| 审批人解析 | 平台 role binding 解析 | OA/ITSM 可作为通知或工单联动 |
| 审计 | 平台 audit/request_events 为权威 | 外部系统可接收同步事件 |

原则：

- 外部用户中心是 identity source，不是权限事实源。
- OA/ITSM 可以承载外部流程或单号联动，但不能替代平台 RequestLifecycle、RBAC、审计。
- 未配置任何外部目录同步时，平台管理员仍可在本地维护 identity、team、role binding 并完整使用平台。

### 1.1 架构图

```
[浏览器] --OIDC--> [平台(OIDC SP，多 issuer 信任)]
                        ├── 直接信任 → 企业自建 OIDC OP（Keycloak/Authing/手写）   ← 不经 dex
                        ├── 直接信任 → 商业 OIDC OP（Azure AD/Okta/Auth0）         ← 不经 dex
                        ├── 直接信任 → cas-oidc-proxy → 企业 CAS Server            ← CAS 代理接入
                        └── 直接信任 → dex → SAML/LDAP/AD/飞书/钉钉（非 OIDC 源）  ← dex 桥接
```

**核心原则（D10.1）**：
- 平台**只讲 OIDC**——认证代码只做 OIDC 验证 + claim 映射，永不引入 CAS/SAML/LDAP 客户端库。
- **多 OIDC issuer 并存**——平台同时信任 N 个 OIDC provider 的 JWT，每个 provider 一个 `oidc.Verifier`。
- **dex 从必选降为可选适配器**——企业已有 OIDC OP 时**直接对接**，不经 dex，零额外组件。
- **CAS 等非标协议通过 OIDC 代理接入**——平台代码零改动。

### 1.2 配置模型（oidc_providers 表，DB 存、Web 可改、热加载）

```yaml
auth:
  oidc_providers:
    # 场景 1：企业自建 OIDC OP 直连（最常见，不经 dex）
    - name: "enterprise-op"
      issuer: "https://sso.corp.com"
      client_id: "iac-platform"
      client_secret: "${OIDC_SECRET}"
      claim_mapping:
        username: "preferred_username"   # 标准 OIDC
        email: "email"
        groups: "groups"
      scopes: ["openid", "profile", "email", "groups"]

    # 场景 2：Azure AD 直连（不经 dex，claim 格式不同需 mapping）
    - name: "azure-ad"
      issuer: "https://login.microsoftonline.com/{tenant}/v2.0"
      client_id: "..."
      client_secret: "..."
      claim_mapping:
        username: "upn"                  # Azure AD 用 upn 非 preferred_username
        email: "email"
        groups: "groups"                 # Azure AD 可能是 group object IDs

    # 场景 3：CAS 代理接入（CAS Server → cas-oidc-proxy → 平台）
    - name: "cas-legacy"
      issuer: "https://cas-proxy.internal"
      client_id: "iac-platform"
      client_secret: "..."
      claim_mapping:
        username: "cas:user"             # cas-oidc-proxy 签发的 claim
        email: "cas:attributes:mail"
        groups: "cas:attributes:memberOf"

    # 场景 4：dex 桥接（SAML/LDAP/AD 等非 OIDC 源，需多源联邦时才部署）
    - name: "internal-dex"
      issuer: "https://dex.internal"
      client_id: "platform"
      client_secret: "..."
      bridge_mode: true                  # dex 已归一化 claim，不需 mapping

  default_provider: "enterprise-op"      # 登录页默认跳转
```

### 1.3 各企业 SSO 场景接入指南

| 企业 SSO 类型 | 接入方式 | 是否需要 dex | 配置 |
|---------------|----------|-------------|------|
| 自建 OIDC OP（Keycloak/Authing/手写） | **直接对接** | 否 | `issuer + client_id + claim_mapping` |
| 商业 OIDC OP（Azure AD/Okta/Auth0） | **直接对接** | 否 | 同上（注意 claim 字段差异） |
| SAML 2.0 IdP（ADFS/OneLogin） | dex SAML connector | **是** | dex 配 SAML upstream + 平台配 dex issuer |
| LDAP/AD | dex LDAP connector | **是** | dex 配 LDAP upstream + 平台配 dex issuer |
| CAS（高校/国企） | **cas-oidc-proxy** → 平台 | 否 | 部署 cas-oidc-proxy + 平台配 proxy issuer |
| 飞书/钉钉 SSO | dex + 平台 DirectorySyncer | **是** | dex 配 connector + DirectorySyncer 同步组织 |
| 自定义非标协议 | 写 OIDC 代理 或 dex connector | 看情况 | 代理转 OIDC 或自写 dex connector（Go） |

### 1.4 CAS 接入详解

CAS（Central Authentication Service）是部分企业/高校的统一身份认证协议。平台**不直接支持 CAS 协议**，而是通过 **cas-oidc-proxy** 接入：

```
用户 → 平台登录页 → 点 "cas-legacy" 按钮
     → redirect → cas-oidc-proxy → CAS Server（CAS 协议认证）
     → cas-oidc-proxy 验 CAS ticket → 签发 OIDC JWT（含 CAS 用户信息）
     → 回调平台 → 平台按 OIDC 验证 JWT → claim_mapping → 建 session
```

cas-oidc-proxy 是轻量 Go 服务（~200 行），开源选项：
- [github.com/LutzGehlen/cas-oidc-proxy](https://github.com/) 或自研
- 部署一个实例，配置 CAS server URL + OIDC issuer URL + signing key
- 平台侧只配一个 `oidc_providers` 条目（issuer 指向 proxy）

### 1.5 登录流程（多 provider）

```
1. 用户访问平台 → 未携带 session → 重定向到登录页
2. 登录页渲染 provider 按钮（enterprise-op / azure-ad / cas-legacy / internal-dex）
3. 用户点某 provider → OIDC authorize redirect → 企业 IdP 认证 → callback
4. 平台用 code 换 token → 从 token header 的 iss 路由到对应 Verifier → 验签
5. claim_mapping 将 OP 特有 claim → 平台内部模型 {sub, email, name, groups}
6. 查 identities 表（external_id = sub + provider_name）→ 建/更新 session
```

### 1.6 业界对照

- **Kubernetes**：`--oidc-issuer` 多 flag 并存，API server 信任多个 issuer 的 JWT
- **Grafana**：`auth.generic_oauth` 多 provider 配置，登录页多按钮
- **ArgoCD**：`oidc.config` 多 issuer，统一 claim 映射
- **Vault**：JWT auth method 多 role，每个 role 绑一个 issuer
- → **共识：多 OIDC issuer 并存 + claim 映射 + 登录页多按钮 是标准模式**

## 2. 组织数据同步：DirectorySyncer 抽象

```go
// server/core/adapters/identity/directory.go
type DirectorySyncer interface {
    PullFull(ctx) (OrgDelta, error)              // 全量拉取
    Subscribe(events chan<- Event) (Unsub, error) // 增量（事件订阅）
    Health() Health                              // 同步健康
}
```

三个默认实现：

| 适配器 | 协议 | 增量通道 | 适用 |
|--------|------|----------|------|
| SCIM 2.0 | `/Users` `/Groups` REST | IDP 主动推送 | 国际标准、Azure AD/Okta/Keycloak |
| 飞书 | 开放平台通讯录 API | 事件订阅（通讯录变更回调） | 国内，飞书租户 |
| 钉钉 | 开放平台通讯录 API | 回调订阅 | 国内，钉钉租户 |

每个适配器：增量为主（秒级）+ 定时全量兜底（对账，如每日）。

## 3. 组织 → 平台归属映射

```
IDP 组织树                          平台实体
部门: 数据/DBA         ──映射──>    team: DBA
部门: 平台工程/网络    ──映射──>    team: 平台运维 (layer=Global)
组: RDS-审批组         ──映射──>    role: dba-approver
用户: 张三             ──归属──>    identity + 多 role_binding
```

- 映射规则可配（部门路径匹配 → team/layer；组名匹配 → role）。
- 业务项目组 = IDP 业务部门；space 由平台层维护（IDP 不感知 space）。
- 映射变更入审计，避免越权。

## 4. 多源去重与主源

- 管理员配置身份源优先级（主源 first）。
- 同一自然人按主源合并，次要源记录为别名。
- 冲突（如两源角色不一致）标记并告警，人工裁定。

## 6. Go 选型

| 用途 | 选型 | 说明 |
|------|------|------|
| OIDC bridge | [dex](https://github.com/dexidp/dex) | CNCF，支持 OIDC/SAML/LDAP 后端 |
| OIDC client | coreos/go-oidc | 平台作 SP 校验 token |
| LDAP | go-ldap/ldap | dex 后端用，平台不直连 |
| SCIM server | 自实现（基于 RFC 7643/7644）或 elimity-com/scim |
| 飞书/钉钉 | 官方 Go SDK / openapi | 通讯录 + 事件订阅 |

## 7. 关键时序

**登录**：浏览器 → 平台 → dex → 企业 IdP → 回调 → 平台发会话。
**增量同步**：飞书事件 → 平台 webhook → 落 org_nodes/identities → 触发映射 → 更新 role_bindings → RBAC 实时生效。

## 8. 业界依据与增强（2025 调研验证）

基于业界调研（Spacelift/HCP Terraform/Scalr/Env0 + SCIM/dex/Zitadel + 飞书/钉钉），对前文设计的关键增强与依据：

### 8.1 SSO 协议基线
SAML 2.0 是企业 SSO 事实基线（Okta/Entra/ADFS 普遍），OIDC 是趋势；平台经 dex 同时支持，SP 侧只讲 OIDC。业界对照：

| 平台 | SSO 实践 |
|------|----------|
| Spacelift | SAML（Teams 属性绑定）+ OIDC；IdP 组驱动 Space 角色 |
| HCP Terraform | SAML SSO，assertion 自动映射 Team，成员由 IdP 驱动（自动移除） |
| Scalr | SAML + 2025.5 新增 OIDC；Team RBAC 控 workspace 级 read/plan/apply |
| Env0 | SAML（Okta）+ OIDC |

### 8.2 Go-native IdP 替代
除 dex 外，[Zitadel](https://github.com/zitadel/zitadel)（Go 原生身份平台，OIDC+SAML，云原生）是自建 IdP 的 Go-native 备选。选型取舍：**桥接异构源用 dex；需自建 OP（OIDC Provider）用 Zitadel**。

### 8.3 统一身份抽象层（认证+供应统一）
比前文 `DirectorySyncer` 更完整——把认证与供应统一到单一接口：

```go
type IdentityProvider interface {
    GetUserInfo(ctx, token) (User, error)         // 认证流
    GetGroups(ctx, token) ([]Group, error)
    SyncUsers(ctx) (<-chan User, error)           // 供应流
    SyncGroups(ctx) (<-chan Group, error)
}
```
所有源（OIDC/SCIM/LDAP/SAML/飞书/钉钉）实现该接口；RBAC 引擎只消费统一 `Group` 模型，不感知上游协议差异。

### 8.4 RBAC 映射模型（业界共识）
```
IdP Group → Platform Team → Role → Scope(Space/Stack) → Permissions
```
引入 **Space** 概念做多项目/多租户隔离（对照 Spacelift Spaces / HCP TF workspace / Scalr scope），与平台 space/layer 正交：一个 Space 可跨层包含多个 stack，Group 在 Space 级别绑 Role，可在 Stack 级别覆盖。

### 8.5 SCIM SP 实现
用 [elimity-com/scim](https://github.com/elimity-com/scim)（符合 RFC 7643/7644）实现 SCIM 2.0 SP endpoint，接收 IdP（Entra ID/Okta）主动推送的用户/组供应。

### 8.6 同步策略（分场景）
- 国际：SCIM 2.0（IdP 主动推送）
- 国内：飞书/钉钉开放 API 轮询 + 事件订阅 webhook
- LDAP/AD：dex connector 实时查询（不缓存）
