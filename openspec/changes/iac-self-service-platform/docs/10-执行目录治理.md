# 10-执行目录治理

> 对应 design.md `04 D4`、spec `specs/06-编排引擎` 的详细展开。**重点回应**：执行层如何初始化、平台重启时执行目录怎么管理最优、是否有必要做内置 git 还是直接存元数据。

## 1. 核心决策：内置 git（go-git）+ 元数据驱动恢复

**结论：必须内置 git，不能"只存元数据"。**

| 方案 | 能否重启恢复 | 能否追溯变更历史 | 能否并发隔离 | 结论 |
|------|--------------|------------------|--------------|------|
| 仅存元数据（每次重新生成代码丢弃 git） | 否（无 commit 锚点） | 否 | 困难 | ❌ 舍弃 |
| 内置 git + 元数据记录 commit | ✅ 按 commit 重建 | ✅ | ✅ worktree/分支锁 | ✅ 采用 |
| 外部 CI 仓库存代码 | 依赖外部 | ✅ | 受限 | 职责分散，运维复杂 |

**理由**：Terramate 在一个 git 工作目录里执行（change detection、generate、run 都依赖 git 上下文）。平台必须自主把这个工作目录管起来——`clone / fetch / commit / push`、记录 commit、重启重建。元数据只记录"指针"（remote + branch + commit + worktree 路径），不存代码本体。

## 2. 工作仓库拓扑

```
bare 仓库（自建 Gitea / 托管）  iac-repo.git
        ▲ push
        │
平台执行节点（每个节点本地）
  /var/tm/worktrees/
    ├── <workspace>/                          # workspace（一个逻辑仓库）
    │   ├── repo/                             # 主 clone（共享 .git）
    │   └── worktrees/
    │       ├── <req-123>-<stage>/            # 工单独占 worktree（并发隔离）
    │       └── <req-124>-<stage>/
```

- 用 **go-git Shared Clone**（`CloneOptions.Shared`，共享 `.git/objects` via alternates，独立 refs）实现并发隔离：多工单各占独立目录，共享 objects 省盘。**演进注记**（2026-07-29）：原设计用 `git worktree`，但 go-git v5 不支持 `git worktree add` API，改用 `Clone --shared`（`git clone --shared` 等价），效果一致（共享 objects + 省盘 + 独立 refs）。squash merge + push 用 git CLI（go-git 不支持 squash merge，唯一 shell out 点）。
- 每个工单（request）独占一个 Shared Clone 目录，避免并发互改。

## 3. checkout 生命周期（代码生成 → git 提交 → 执行 衔接）

> 这条链回答"代码生成后是否提交到内置 git 执行仓库、中间如何衔接"。**是的**：codegen 产物写入内置执行仓库的工单分支，commit SHA 成为 `pinned_commit`，Executor 据此检出 worktree 运行。

```
[工单 generating]
   1. workspace 管理器：克隆/复用 workspace 主仓，创建 worktree + 分支锁（auto/req-123）
   2. codegen（specs/05）写产物到 worktree 暂存区：
      stack.tm.hcl / main.tf / backend.tf / 跨层 data 注入
   3. workspace 管理器：git add + commit（确定性消息，如 "req-123 rds-prod generated"）
   4. 持久化 pinned_commit = 该 commit SHA（workspace_checkouts.pinned_commit）
[工单 planning/applying]
   5. Executor 检出 pinned_commit 为 worktree（docs/11 §3，process/container/k8s/remote 之一）
   6. Executor.Run(terramate run ... plan / apply) → 退出码 + 日志回写 request_events
   7. apply 成功后合并（详见 §3.1 合并策略）；失败 → 保留 worktree 供排障
   8. 终态 → 释放 worktree（leased_until 到期或显式 release）
[漂移检测（异步）]
   9. DriftScheduler 经 Executor 检出该 stack 最新 pinned_commit → 只读 plan（docs/13）
```

### 3.1 合并到 main 的策略（2026-07-16 补充）

> **核心原则**：`main` 分支 = 已成功部署的真实状态（source of truth）。未 apply 的代码不进 main。

**合并时机**：terraform apply 成功（exit 0）后，在释放 worktree 之前。不在 generating / planning / pending-approval 阶段合并（那些阶段代码未验证或资源未创建，合并会污染 main）。

**合并方式**：**squash merge**（1 个工单 = main 上 1 个 commit），不用 fast-forward / merge commit。

| 策略 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **squash merge** | main 历史干净（1 工单 1 commit）；易回滚（git revert）；审计清晰 | 丢失中间 commit 细节（codegen 不需要）| ✅ 采用 |
| fast-forward | 保留中间 commit | 并发工单改 main 后 ff 失败 | ❌ |
| merge commit | 保留分支拓扑 | main 历史复杂；回滚难 | ❌（IaC 不需要）|

**完整 step 7 流程**（apply 成功后）：
```
a. Executor 确认 terraform apply exit 0 + state 已写入远程 backend
b. workspace manager：git checkout main + git pull --ff-only origin main（拉最新 main）
c. git merge --squash req-123（把工单分支改动压成暂存区）
d. git commit -m "req-123: <component> applied (stack: <stack_id>)"
e. git push origin main
f. 删除 req-123 分支
g. 更新 workspace_checkouts.status = 'released'
h. 更新 stacks.pinned_commit = main 最新 SHA（漂移检测下次用 main SHA）
```

**失败处理**：
- **merge 冲突**（极少见，因 D20 stack 级串行锁保证同 stack 不并发）→ 工单标 `waiting-manual`，保留 worktree，生成 `manual_intervention_tasks`，通知运维。**不自动 rebase**（IaC 代码冲突需人工判断）。
- **push 失败**（远端 main 有新 commit，如另一工单刚合并）→ `git pull --rebase origin main` 重试 1 次；仍失败 → `waiting-manual`。
- **apply 失败** → **不合并**，保留 worktree + req 分支供排障；main 保持干净。

**并发工单隔离**：workspace_checkouts 的 `leased_by_request_id` 锁 + D20 Executor 双锁（PG 行锁 `SELECT FOR UPDATE WHERE id=stack_id` + state backend DynamoDB lock）保证同一 stack 不会有两个工单同时 apply。不同 stack 的工单改不同文件，squash merge 不冲突。

**不变量**：main 分支的每个 commit 都对应一个 `succeeded` 工单 + 已 apply 的真实云资源状态。`git log main` = 平台部署历史审计日志。

**衔接契约**：
- codegen（specs/05）只产"文件树"，**不感知 git**——把文件写入由 workspace 管理器给的目录。
- workspace 管理器（specs/06）负责 git add/commit/push + pinned_commit 持久化。
- Executor（specs/11）只按 `pinned_commit` 检出 worktree 执行，不感知 codegen。
- 三者通过 `pinned_commit` + 目录路径解耦，任何一段可独立替换/重放（幂等：同工单重跑 generating 产相同 commit）。

对应表 `workspace_checkouts`（见 `docs/04-数据库设计.md` §2.5）：
- `leased_by_request_id`：当前持有工单。
- `pinned_commit`：codegen 提交后锚定的 commit（用于恢复 + Executor 检出 + 漂移检出）。
- `status`：`active`（使用中）/`released`（已释放）/`stale`（异常遗留）。
- **plan 产物不入 worktree**（D21 衔接）：plan 阶段 Executor 在 worktree 内跑 `terraform plan -out=plan.tfplan`，但销毁沙箱前**必须上传到对象存储**（`s3://tm-plans/<req_id>/plan.tfplan`，详见 docs/11 §3.7）并写 `artifacts(kind=plan_binary)`；worktree 随沙箱销毁，apply 阶段新沙箱按 `request_id` 拉取 plan 产物，**不依赖原 worktree 存活**——这是 D21 plan/apply 解耦的关键不变量。

## 4. 平台重启恢复流程（重点）

平台启动时执行 **reconcile**：

1. 读 `workspace_checkouts where status in (active, stale)`。
2. 对每条记录：
   - 若本地 worktree 存在：`git fetch` 后 `checkout pinned_commit`，校验一致 → 标记 `active`。
   - 若本地缺失：按 `remote_url + branch` 重新 `clone`，`checkout pinned_commit` 重建 worktree。
3. 读所有 `requests where status in (generating, pending-admission, planning, plan-ready, pending-approval, applying, reconciling, reconcile-pending)`：
   - `generating` / `planning` 可从断点重试。
   - `plan-ready` / `pending-approval` 只恢复 plan artifact 引用，不重新 plan，除非 artifact 过期。
   - `applying` 若 Executor 心跳丢失，标记 `waiting-manual`，生成 `manual_intervention_tasks` 做 state 检查，**不自动重试 apply**。
   - `reconciling` / `reconcile-pending` 只重放 outbox/reconcile，不影响已完成的 apply。
4. 标记无法恢复的（如 pinned_commit 已被 GC）为 `waiting-manual`，生成恢复任务。

**幂等保证**：代码生成和 plan 可基于相同输入安全重试；apply 只允许在同一 `pinned_commit + plan_binary + sha256 + toolchain_profile_hash` 下恢复，并且 apply 中断后默认转人工检查，不做盲重试。

## 5. 并发隔离与分支锁

- **worktree 隔离**：每工单独立 worktree，文件系统级隔离。
- **分支锁**：同一 space 的并发写，用 DB 行锁 + 短分支（`auto/req-123`）+ 合并串行化，避免 push 冲突。
- **state 锁**：由远程 backend（DynamoDB/etcd）保证 apply 串行；平台不重复造锁。

## 6. 与 Terramate 的协作边界（D29）

### 职责划分

- **平台负责**：工作仓库的 git 生命周期、worktree 准备、commit/push、元数据管理、codegen（含 `stack.tm.hcl` 生成）。
- **Terramate 负责**：在已准备好的 worktree 内执行栈发现 + 依赖排序 + 标签过滤 + `terraform plan/apply`。
- **Terramate 不感知平台**：它在普通 git 仓库里工作，无平台耦合。

### Worktree 中的 Terramate 调用方式

```bash
# 平台为工单 req-123 创建独立 worktree（§3 checkout 生命周期）
/worktrees/req-123/          ← git worktree，完整 Terramate 项目结构
├── terramate.tm.hcl         ← 项目根（required_version 非空）
├── global/
├── middleware/
└── application/

# 平台 TerramateAdapter 在 worktree 中调用 Terramate：
cd /worktrees/req-123/

# Plan 阶段（双门禁第一道：准入审批通过后）
terramate run \
  --tags "tenant:corp-a,env:dev,layer:application" \
  --parallel 3 \
  -- terraform plan -out="/shared/req-123/plan.tfplan"
# Terramate 发现 corp-a+dev+application 的 stack → DAG 排序 → 并行 plan

# Apply 阶段（双门禁第二道：执行确认审批通过后，新 worktree）
cd /worktrees/req-123-apply/  ← 新 worktree（plan/apply 解耦，D21）
terramate run \
  --tags "tenant:corp-a,env:dev,layer:application" \
  --parallel 3 \
  -- terraform apply "/shared/req-123/plan.tfplan"
```

### Worktree 兼容性（源码级保证）

- `config/config.go:121-162` `TryLoadConfig`：基于文件系统路径向上递归找 `terramate.tm.hcl`，**不依赖 git root**。worktree 中有完整项目结构→Terramate 正常定位项目根。
- `stack/manager.go` `ListChanged`：在 worktree 中 `git diff` 正常工作（worktree 是真实 git checkout）。
- `config/stack.go:HostDir(root)`：stack 路径基于项目根的 HostDir 计算，worktree 中路径一致。

### 不用 Terramate generate

平台 codegen（D19）直接生成 `stack.tm.hcl` + `main.tf` + `backend.tf`，MUST NOT 依赖 `terramate generate`。Terramate generate 是静态模板引擎，不适合动态表单驱动的 9 阶段参数解析管道。

### TerramateAdapter 命令矩阵（Phase 0 必须冻结）

> 该矩阵是 P0 工程契约：平台不得在 Orchestrator 中直接拼 `terraform` 命令，必须通过 `TerramateAdapter` 在已准备好的 worktree 内执行；同时不得误用 Terramate Cloud sync 专用 plan-file flags 作为本地 saved-plan apply 机制。

| 阶段 | Adapter 动作 | 工作目录 | 命令形态 | 输入 | 输出契约 |
|------|--------------|----------|----------|------|----------|
| plan | `RunPlan` | `pinned_commit` worktree | `terramate run --tags <scope> -- terraform plan -out=<shared_plan_path>` | stack tags、toolchain profile、provider lock | exit code、stdout/stderr、plan binary、plan JSON summary |
| saved-plan apply | `RunApplySavedPlan` | 新建 `pinned_commit` worktree | `terramate run --tags <scope> -- terraform apply -input=false <downloaded_plan_path>` | 已审 plan artifact、sha256、toolchain hash、provider lock hash | exit code、stdout/stderr、apply log、state lock result |
| drift-plan | `RunDriftPlan` | stack 当前 `pinned_commit` worktree | `terramate run --tags <scope> -- terraform plan -detailed-exitcode -out=<drift_plan_path>` | stack tags、read-only credential | exit code 0/2/1、diff summary |
| import-verify | `RunImportVerify` | import worktree | `terramate run --tags <scope> -- terraform plan -detailed-exitcode` | import blocks、generated config | zero-diff 证明或 diff summary |

不变量：

- apply 必须执行已审 plan artifact，不能重新 plan。
- plan artifact 下载后必须校验 `sha256`、`pinned_commit`、`toolchain_profile_hash`、`provider_lock_hash`。
- `terraform apply` 只能作为 `terramate run -- ...` 的子命令出现，不能由 Orchestrator 绕过 Terramate 直接调用。
- 若 saved-plan apply 阶段发现 world drift、artifact 过期或 hash 不一致，工单进入 `expired` 或 `blocked-state-health`，要求重 plan。

### Terramate OSS 适配验证策略

平台依赖 Terramate CLI，但不修改 Terramate 核心。为避免 CLI 行为变化在实现后期暴露，Phase 0 必须把以下能力作为兼容性验证项：

| 验证项 | 方案级要求 |
|--------|------------|
| stack discovery | worktree 内 `terramate list` 能发现 PathGenerator 生成的 stack |
| tags filter | `terramate run --tags` 能准确过滤 layer/tenant/env/team |
| DAG order | `after` / `watch` 生成后执行顺序符合跨层依赖 |
| changed stack | PR-first / Scheduled Runs 使用 changed stack 语义时必须有兼容测试 |
| saved-plan apply | saved plan 只能通过 `terramate run -- terraform apply <plan>` 包裹执行 |
| version pin | Terramate CLI 版本升级前必须跑 adapter compatibility suite |

验收口径：Terramate 适配风险不靠人工阅读 release note 兜底，必须有最小兼容性测试集。若某版本 Terramate 行为不兼容，平台只能升级 adapter 版本范围，不能临时绕过 Terramate 直接调用 Terraform。

## 7. 失败与悬挂处理

- 工单失败：worktree 保留 N 天（配置），供排障；超期回收。
- checkout 过期（`leased_until` 到期且工单终态）：自动 release。
- 对账任务（§8）发现孤儿 worktree：标记 stale 并清理。

## 8. 一致性对账（定期）

定时任务校验三方一致：
```
元数据 stacks  ↔  工作仓库目录  ↔  远程 state key 列表
```
- `missing`：元数据有但仓库/state 无 → 告警。
- `orphan`：仓库/state 有但元数据无 → 标记待清理（人工确认）。

### 8.1 Git/DB/ObjectStore Saga

| 故障窗口 | 目标状态 | 补偿动作 |
|----------|----------|----------|
| 临时目录生成失败 | `failed-retryable` | 丢弃临时目录，不写 worktree |
| git commit 失败 | `failed-retryable` | 清理 worktree，允许重跑 generating |
| git commit 成功但 `requests.pinned_commit` 写库失败 | `failed-retryable` | reconcile 扫描 commit marker，找回或回滚孤儿 commit |
| plan 上传成功但 `artifacts` 写库失败 | `failed-retryable` | 对象存储扫描补 artifact row；超时标 orphan artifact |
| apply 成功但 push 主分支失败 | `reconcile-pending` | outbox 重试 push；失败转人工任务 |

所有外部副作用必须先写 `outbox_events`，由 worker 投递并记录 `correlation_id`。worker 重试失败进入 dead-letter，并生成 `manual_intervention_tasks`。
