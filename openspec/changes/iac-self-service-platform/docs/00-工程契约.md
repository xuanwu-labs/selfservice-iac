# 00-工程契约

> 本文是商业级实现前的 Phase 0 硬门槛。目标不是新增功能，而是把架构意图冻结为可测试、可实现、可复用的工程契约。没有通过本文验收，不进入大规模编码。

配套产物规划见 `specs/03-平台契约.md`（Connect-native 实际契约）与 `contracts/README.md`。本文定义契约原则与领域边界；实际 proto 契约（5 域 × srv/dto/enum）、错误码注册表、状态机 fixture、Adapter golden tests、walking skeleton seed 已冻结在 `contracts/`。

## 1. 契约原则

- **契约先于实现**：API、schema、状态机、错误码、幂等、审计字段先冻结，再写服务端和前端。
- **单一语义**：HTTP API、gRPC API、CLI、CICD gate、MCP tools 必须复用同一 service 层语义，不各自定义状态或错误。
- **协议边界清晰**：核心平台只提供 HTTP/gRPC；Dubbo、OA、ITSM、老系统协议转换由未来 Go Gateway 承担。
- **核心能力内建**：identity、team、role binding、RBAC、审批、CMDB、FinOps 是平台内建能力；外部用户中心、OA、ITSM 只是可选对接，不是平台运行前提。
- **幂等默认**：创建类 API 必须支持 `Idempotency-Key` 或声明业务幂等键。
- **可追踪默认**：所有响应必须携带 `correlation_id`；所有状态变化必须写 `request_events`。
- **失败可解释**：错误响应必须包含机器可读 `error.code`、人可读 `message`、可选 `remediation`。

## 2. API 基础规范

| 项 | 规范 |
|----|------|
| API 前缀 | `/api/v1` |
| 内容类型 | JSON 为默认；`POST /requests` 额外支持 YAML |
| 认证 | Human 使用 OIDC session；machine/CI/agent 使用 AK/SK HMAC |
| 幂等头 | `Idempotency-Key`，缺省时由平台按业务字段计算 |
| 追踪头 | `X-Correlation-Id`，客户端不传则服务端生成 |
| 分页 | `page_size` + `page_token`，响应返回 `next_page_token` |
| 乐观锁 | 状态变更必须使用 `version` 或 `expected_status` |
| 错误 envelope | `{error:{code,message,details,remediation}, correlation_id}` |

## 3. 核心 API 契约

| API | 语义 | 幂等键 | 关键响应 |
|-----|------|--------|----------|
| `POST /api/v1/requests` | 创建 Web/YAML 申请 | `sha256(actor + catalog_item + form_hash + 24h_window)` | `request_id,status,correlation_id` |
| `GET /api/v1/requests/{id}` | 查询工单详情 | 无 | `status,version,current_stage,resolved_params,artifacts` |
| `GET /api/v1/requests/{id}/events` | 查询状态轨迹 | 无 | `request_events[]` |
| `GET /api/v1/requests/{id}/gate` | 查询 CI/CD gate | 无 | `gate_status,until,summary` |
| `POST /api/v1/requests/{id}/plan` | 触发或恢复 plan | `request_id + pinned_commit + expected_status` | `status,plan_artifact_id` |
| `GET /api/v1/artifacts/{artifact_id}` | 查询 artifact metadata | 无 | `artifact_id,kind,sha256,expires_at,status` |
| `POST /api/v1/approvals/{run_id}/decide` | 审批决策 | `run_id + node_id + approver + decision` | `approval_status,next_node` |
| `POST /api/v1/requests/{id}/apply` | 触发已审批 saved-plan apply | `request_id + plan_artifact_id + expected_status` | `status,executor_run_id` |
| `GET /api/v1/catalog` | 查询可申请目录 | 无 | `catalog_items[]` |
| `GET /api/v1/requestable-cloud-accounts` | 查询团队可用云账号 | 无 | `cloud_accounts[]` |
| `POST /api/v1/webhooks/subscriptions` | 注册 webhook（P1 预留，不阻塞 Phase 0 golden path） | `target_url + event_filter` | `subscription_id,secret_ref` |

## 4. 核心 Schema 契约

### 4.1 RequestCreate

| 字段 | 必填 | 说明 |
|------|------|------|
| `catalog_item_id` | 是 | 服务目录项 |
| `env_id` | 是 | 目标环境 |
| `tenant_id` | 否 | 默认 `platform-default` |
| `team_id` | 是 | 申请团队 |
| `bundle_id` | 否 | 项目组分组 |
| `form_values` | 是 | 表单值，canonical JSON 后计算 `form_hash` |
| `source` | 是 | `web` / `cli` / `cicd` / `ai` |
| `source_context` | 否 | CI pipeline、PR、agent skill 等上下文 |

### 4.2 ResolvedParams

| 字段 | 说明 |
|------|------|
| `values` | 最终变量值 |
| `provenance` | 每个变量的 `{source,rank,overridden_from,user_attempted_override}` |
| `tags` | 7 层 tag 合并结果和 `user_overrides_blocked` |
| `policy_flags` | `cost_overrun`、`high_risk`、`binding_missing` 等治理标记 |
| `schema_version` | 解析结果 schema 版本 |

### 4.3 PathGeneratorOutput

| 字段 | 说明 |
|------|------|
| `repo_path` | 工作仓库相对路径 |
| `state_key` | Terraform backend key，默认等于 `repo_path` |
| `stack_id` | Terramate stack 全局唯一 ID |
| `terramate_tags` | 至少包含 layer、tenant、env、team |
| `after` | 上游 stack 相对路径 |
| `watch` | 上游 outputs 变更传播路径 |

### 4.4 PlanArtifact

| 字段 | 说明 |
|------|------|
| `artifact_id` | plan 产物 ID |
| `request_id` | 所属工单 |
| `pinned_commit` | plan 对应代码 commit |
| `sha256` | plan 二进制 sha256 |
| `toolchain_profile_hash` | Terramate/Terraform/OpenTofu 版本指纹 |
| `provider_lock_hash` | `.terraform.lock.hcl` 指纹 |
| `created_at` | 创建时间 |
| `expires_at` | TTL，过期必须重 plan |
| `status` | `active` / `superseded` / `expired` / `orphan` |

## 5. 状态机契约

RequestLifecycle 权威状态：

`submitted → generating → pending-admission? → planning → plan-ready → pending-approval → applying → reconciling → succeeded`

异常状态：

`rejected` / `cancelled` / `expired` / `failed-retryable` / `failed-terminal` / `waiting-manual` / `reconcile-pending` / `blocked-policy` / `blocked-state-health` / `paused-drift`

状态迁移必须满足：

- 每次迁移用 `WHERE id=? AND status=? AND version=?` 乐观锁。
- 每次迁移写 `request_events`。
- 外部副作用先写 `outbox_events`。
- 不能自动闭环的异常必须写 `manual_intervention_tasks`。
