# 13-漂移检测设计

> 对应 design.md `04 D5`、spec `specs/07-状态与漂移` 的详细展开。开源 Terramate 无漂移引擎，本设计为平台自研。

## 1. 架构

```
┌──────────────────────────────────────────────────────┐
│  DriftScheduler（单实例/leader选举）                   │
│  - 读 schedule 配置（分层/团队/stack 频率与时间窗）    │
│  - 生成检测任务 → 投入队列（限流）                     │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│  DriftWorker 池（水平扩展）                            │
│  for each drift_run:                                  │
│    1. 申请 workspace checkout（复用执行目录治理）       │
│    2. terramate run -- terraform plan -out=plan       │
│    3. terraform show -json plan → 解析差异             │
│    4. 写 drift_runs + (有差异时) drift_records         │
│    5. 发 drift.detected 事件 → Notifier                │
└──────────────────────────────────────────────────────┘
```

## 2. 检测流程（单 stack）

> 漂移只读 plan **走与工单完全相同的 `Executor`（specs/11 D20）**——同一 worktree 治理（docs/10）、同一工具链（预装或 worker 镜像）、同一四模式可插拔、同一隔离契约。漂移不另造执行路径。

1. **准备执行目录**：复用 `docs/10` 的 workspace checkout 机制（只读语义，用独立 worktree，检出该 stack 最新 `pinned_commit`）。
2. **只读 plan（经 Executor）**：`Executor.Run(cmd = terramate run -- terraform plan -detailed-exitcode -out=<plan>)`。
   - 退出码 `0`：无漂移。
   - 退出码 `2`：有差异（漂移）。
   - 退出码 `1`：错误，记录并告警。
3. **解析差异**：`terraform show -json <plan>`，提取 `resource_changes` 中 `change.actions != ["no-op"]` 的资源，生成 `diff_summary_json`。
4. **写记录**：`drift_runs`（本次运行）+ 若有差异则 `drift_records`（status=open）。
5. **发事件**：`drift.detected`，Notifier 通知归属团队。

## 3. 调度与限流

| 层 | 默认频率 | 时间窗 | 并发上限 |
|----|----------|--------|----------|
| Global | 每日 1 次 | 凌晨 | 低（2） |
| Middleware | 每 12 小时 | 工作时间外 | 中（5） |
| Application | 每 6 小时 | 任意 | 高（可配） |

- 全局令牌桶限流，避免后端被打满。
- 失败退避：连续失败 stack 降低频率并告警。
- 支持手动触发"立即检测某 stack"。

### 3.1 Scheduled Runs（商业级扩展）

Phase 2 起，调度器从“漂移专用”扩展为通用 scheduled run 能力，对标 Spacelift/env0 的 scheduled runs：

| run 类型 | 行为 | 是否 apply |
|----------|------|------------|
| `drift-plan` | 周期只读 plan，发现云侧漂移 | 否 |
| `nightly-plan` | 夜间对关键 stack 跑 plan，提前发现 provider/toolchain 问题 | 否 |
| `maintenance-apply` | 在维护窗口执行已批准低风险变更 | 是，必须有有效 approval |
| `stack-health-check` | 检查 backend lock、provider mirror、OIDC、state 可读性 | 否 |

所有 scheduled runs 复用 RequestLifecycle、Executor、artifacts、Run Hooks 与审计，不另造执行路径。

## 4. 事件时序：发现到处置

```
DriftWorker    DB                Notifier         前端/审批人
   │ plan 有差异  │                  │                 │
   │ drift_record(open) ─────────▶ │                  │
   │ drift.detected ──────────────▶│ ──通知─────────▶ │ 看到漂移
   │              │                  │                 │ 用户选择策略
   │              │   ◀── adopt-cloud / restore-desired│
   │              │                  │                 │
   │ [按策略执行]  │                  │                 │
   │  adopt-cloud: terraform import/state 调整         │
   │  restore-desired: terramate run apply             │
   │ drift_record(resolved) ───────▶│ ──通知完成──────▶│
```

## 5. 同步策略执行

- **adopt-cloud（采用云端状态）**：生成 `terraform import`（或对 state 的受控调整）使 state 与云一致。适用于"手工改动是预期内的、应保留"。
- **restore-desired（恢复期望状态）**：`terramate run ... apply`，把云改回期望配置。适用于"手工改动是违规的、应回滚"。
- **不自动处置**：必须人工选择，避免误覆盖。

### 5.1 漂移修复工单（drift-remediation request）

两种策略都走**专用工单**（`requests.kind=drift-remediation`，复用 orchestrator/codegen/Executor/审批 全链路，不另造）：

| 属性 | 值 |
|------|-----|
| **触发源** | 漂移记录页"采用云端"/"恢复期望"按钮（归属团队 owner 决策）|
| **准入审批（Gate1）** | 默认 OPA 放行（低危，无新增资源），但**漂移导致资源数减少 > 阈值时升级人工审批**（防误删）|
| **执行确认审批（Gate2）** | **不可免审**（破坏性操作必人审），输入含：漂移差异摘要、原 vs 期望状态、操作影响范围 |
| **执行** | adopt = `terraform import` + state 调整；restore = `terramate run apply`（走标准 plan/apply 解耦 D21）|
| **闭环** | apply 成功 → 关闭 drift_record（status=adopted/reverted）→ 通知归属团队 |

### 5.2 与双门禁的关系（D21 衔接）

漂移修复走与正常申请**完全相同的双门禁状态机**：
- Gate1 准入：漂移修复默认 OPA 自动放行（因为修复 = 已认定漂移存在 + 已决策方向），但若修复会引发资源 destroy/replace 仍走人工审批。
- Gate2 执行确认：**不可免审**——漂移修复本质是破坏性操作（动 state 或 apply），必人审。
- 漂移修复工单的 plan 产物走同样的对象存储链路（docs/11 §3.7），apply 阶段 sha256 校验。

## 6. 与 Terramate / Executor 的复用

漂移检测的 plan 执行**复用 `TerramateAdapter`（`terramate run`）+ `Executor`（specs/11 D20，四模式同一沙箱）**，保证与正常流水线一致的目录、backend、env、工具链与隔离上下文。差异仅在：只读 plan + 解析 JSON + 不 apply。漂移与工单 plan 共享 Executor，确保隔离/资源/网络策略一致，不因检测另造路径。

**Executor 配置继承**：漂移检测器**不单独配置** Executor 模式，继承全局/团队的 Executor 配置（process/container/k8s/remote）；限流策略上漂移检测与工单执行**共享同一限流池**（避免漂移扫爆 Executor 资源影响在线工单，docs/13 §3 分层时间窗已含此约束）。凭据注入与工单一致（D23 占位符 + env，漂移只读 plan 不需写凭据但读凭据仍按 team_cloud_grants 注入）。

## 7. 测试策略

- 单测：构造 plan JSON 样本 → 断言 `diff_summary_json` 正确。
- 集成：fake 后端（localstack / 模拟 state）→ 触发手工改动 → 检测器识别 → 断言 drift_record。
- 限流：模拟 N 个 stack 同时到期 → 断言不超并发上限。
