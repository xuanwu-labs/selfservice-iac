# 04-数据库设计（元数据）

> 对应 design.md `04 D4/D6`、spec `03/05/07` 的详细展开。重点回应："执行层的执行和元数据库表设计"。这是平台的"控制面真相源"，与执行面（工作仓库 + 远程 state）分离。

## 1. 设计原则

- **元数据是控制面真相源**：工单、归属、审批、目录项、漂移状态。
- **代码与 state 是执行面真相源**：在工作仓库（git）与远程 backend，**不复制进 DB**。
- **二者通过对账任务保持一致**：定期校验 `元数据.stack ↔ 工作仓库目录 ↔ 远程 state key`。
- **审计不可变**：审计日志 append-only。
- **跨系统最终一致**：DB 与 Git、对象存储、state backend、CMDB、通知系统之间不假设分布式事务，统一通过 `outbox_events` + reconcile job 补偿。
- **人工兜底可追踪**：平台不能自动恢复的异常必须进入 `manual_intervention_tasks`，而不是只返回错误码。

### 1.1 核心实体收敛

MVP 的一等实体只保留六类：`CatalogItem`、`Request`、`Stack`、`Environment`、`Tenant`、`Team`。`Space` 是 stack 分组与成本/审批维度，Phase 1 不作为强治理边界；`Layer` Phase 1 固定三层，Phase 2 才开放 D24 可配置与 D26 迁移。

### 1.2 事实源边界

| 数据 | 事实源 | DB 中的定位 |
|------|--------|-------------|
| 控制面意图 | `requests` + `resolved_params_json` | 强一致 |
| 生成代码 | Git `pinned_commit` | DB 只存 commit 引用 |
| 资源状态 | Terraform state | DB 只存 `state_key` 与资源索引 |
| 资源查询 | `resources` | 可重建索引，不覆盖 state |
| 成本实际值 | 云账单 | `cost_records(cost_source=bill)` |
| 成本估算 | Infracost | `cost_records(cost_source=estimate)` |

## 2. 表清单与关键字段

### 2.1 组织与归属
```
-- AI Generated Start
teams(id, name, kind[platform|dba|middleware|business],
      tags_json, policy_json,                         -- D28 L4 + S6 team policy
      created_at)
projects(id, name, team_id)                       -- 业务项目组（kind=business 的子集合）
spaces(id, name, project_id, layer_logical_id, repo_path,

```
- `spaces.repo_path`：工作仓库中的目录根，如 `application/platform-default/team-a/orders`。
- `teams.policy_json`：Phase 2 用于 S6 team policy（allowed_regions / cost_cap / mandatory_tags）；Phase 1 可为空。
- `teams.tags_json` / `spaces.tags_json`：D28 L4 tag 来源，解决参数管道依赖但 schema 缺失的问题。

### 2.2 模块与目录
```
modules(id, namespace, source_url, ref, layer, owner_team_id,
        status[pending-validation|validated|validation-failed|superseded],
        variables_contract_json, created_at)            -- 纯 scalar 契约（零侵入，D25）
module_versions(id, module_id, ref, extracted_at, is_current)   -- 版本历史
catalog_items(id, module_version_id, display_name, form_schema_json,
              defaults_json, visibility[team_ids...], layer, owner_team_id,           -- layer deprecated（D24 前硬编码枚举），权威见 layer_logical_id
              status[active|deprecated|archived],                                       -- L5 生命周期：active=正常 / deprecated=禁新申请(存量可用) / archived=拒引用(存量待迁移)
              -- D24+D26 stack 模型可配置（层引用稳定身份，不直接绑版本）
              layer_logical_id, stack_grouping[per-component|per-space|per-team|custom],
              -- D25 模块零侵入的多实例配置（catalog 项层面，不污染 modules 表）
              cardinality[single|list|map], instance_key,
              per_instance_fields_json, shared_fields_json,
              -- D28 标签分层：catalog 注册者可声明默认 tag + 用户白名单
              default_tags_json, user_allowed_tag_keys_json)
```
- `variables_contract_json`：从 `variables.tf` 提取的**纯 scalar 契约**（D25 零侵入——不含 cardinality，cardinality 归 catalog 项）。
- `form_schema_json`：从契约裁剪出的"用户可见字段 + 校验规则"。
- `defaults_json`：最佳实践默认值覆盖。
- `cardinality` / `instance_key` / `per_instance_fields_json` / `shared_fields_json`：**catalog 项平台层多实例配置**（D25），codegen 按此在调用方注入 for_each/count。
- `layer_logical_id`：引用**跨版本稳定的层身份**（D26），FK → `layer_logical_refs.logical_id`（§2.9 定义）；layer 规则升版时 catalog_items 此字段不动，新 stack 创建时把 `layer_logical_id` + 当前 active `layer_rule_set_versions.version_id` 解析出具体 `path_template`，pin 到 `stacks.layer_rule_set_version_id`。**这是 D24+D26 数据模型的枢纽**：catalog_items 指稳定身份、stacks pin 具体版本。
- `stack_grouping`：决定 stack 粒度（D24，per-component 默认 / per-space / per-team / custom）。
- `default_tags_json`：catalog 注册者声明的默认 tag（D28 L6 层），如 `{"app":"order-service"}`。
- `user_allowed_tag_keys_json`：用户表单 tag 白名单（D28 L7 层），空数组 = 用户不能加任何自定义 tag；非空时仅允许列出的 key（如 `["owner","ticket"]`），防用户注入非治理 tag。

### 2.3 stack 注册表（连接元数据与工作仓库）
```
-- AI Generated Start
stacks(id, space_id, layer, component, env, tenant_id,
       stack_id, repo_path, state_key, terramate_tags_json,
       owner_team_id, catalog_item_id,
       -- D26 层规则集版本 pin（创建时写入，不可变——保证 path/state_key 稳定）
       layer_rule_set_version_id,
       migration_status[stable|migration_pending|migrating|deprecated],
       sunset_deadline,
       version, created_at)

stack_dependencies(id, from_stack_id, to_stack_id,
                   kind[remote_state|data_source|watch_only],
                   output_key, inject_as,
                   status[active|deprecated], created_at)
-- AI Generated End
```
- `repo_path` = 工作仓库相对路径；`state_key` = 远程 backend key；二者确定性一致。
- `stack_id`：PathGenerator 输出的 Terramate stack 全局唯一 ID，必须与 `stack.tm.hcl` 一致。
- `terramate_tags_json`：PathGenerator 输出的执行过滤 tags，至少包含 layer/tenant/env/team。
- `layer_rule_set_version_id`：创建时 pin 当时的 active layer 规则版本（D26），后续不可变；layer 规则升级不影响已部署 stack 的 path/state_key，除非走显式迁移流程。
- `migration_status`：标识 stack 是否处于迁移中（迁移批次静默、漂移静默用此判断）；`deprecated` 表示该 stack 已被新版本取代（Tier 3），须在 `sunset_deadline` 前 destroy+recreate。
- `stack_dependencies` 是跨层依赖图的事实源：codegen S7、Terramate `after/watch`、Global destroy 阻断、CMDB 关系图均读取此表。
- 这是"对账任务"的核心表。

### 2.4 工单与流水线
```
-- AI Generated Start
requests(id, catalog_item_id, space_id, form_values_json, requester_id,
         status[submitted|generating|pending-admission|planning|plan-ready|
                pending-approval|applying|reconciling|succeeded|rejected|
                cancelled|expired|failed-retryable|failed-terminal|
                waiting-manual|reconcile-pending|blocked-policy|
                blocked-state-health|paused-drift],
         current_stage, created_at, updated_at,
         version,                                             -- 乐观锁：status + version CAS
         -- D27 环境与租户绑定（codegen Stage 4 查询入口）
         env_id, tenant_id,
         -- D28 参数解析 provenance（每个变量含 source/rank/override 链路）
         resolved_params_json,
         -- 运维韧性（§07c）：幂等键防双击 + pinned_commit 锚点
         form_hash, idempotency_key,                           -- sha256(user+catalog+form_hash+24h) UNIQUE
         pinned_commit,                                        -- git commit hash（codegen 产出锚点，Executor 检出依据）
         plan_completed_at,
         layer_rule_set_version_id)                            -- D26 创建时 pin 的 layer 版本
request_events(id, request_id, stage, from_status, to_status,
               actor_id, message, correlation_id, occurred_at)  -- 状态机轨迹
artifacts(request_id, kind[plan_log|apply_log|tf_code_commit|plan_binary],
          ref, sha256, size_bytes,
          status[active|superseded|expired|orphan],
          toolchain_profile_hash, provider_lock_hash,
          created_at, expires_at)
executor_runs(id, request_id, phase[plan|apply|drift|import],
              pinned_commit, artifact_id nullable,
              toolchain_profile_hash, provider_lock_hash,
              credential_session_id nullable,
              exit_code, started_at, finished_at,
              status[running|succeeded|failed|interrupted])
-- AI Generated End
```
- `artifacts.ref`：plan/apply 日志指向对象存储；`tf_code_commit` 指向工作仓库 commit sha；**`plan_binary` 指向 D21 plan/apply 解耦的 terraform plan 二进制产物**（对象存储路径如 `s3://tm-plans/<req_id>/plan.tfplan`）。
- `env_id` / `tenant_id`：工单提交时绑定（默认 `platform-default` tenant + 用户选定 env），codegen Stage 4 用此查询 `environment_tenant_bindings` 解析网络上下文。
- `resolved_params_json`：**参数解析 provenance 审计**（D28）。每个解析后变量值含 `{value, source, rank, ...}`，rank 以 `docs/08 §3` 为唯一权威。
- **D21 plan 产物链路**（关键）：plan 阶段 Executor 通过 TerramateAdapter 跑 `terramate run -- terraform plan -out=plan.tfplan`，销毁沙箱前把 `plan.tfplan` 上传对象存储并写 `artifacts(kind=plan_binary)`；apply 阶段新沙箱检出 `pinned_commit` 后，**按 `request_id` 查最新 `plan_binary` 下载**，通过 `TerramateAdapter.RunApplySavedPlan` 跑 `terramate run -- terraform apply "plan.tfplan"`（不重 plan）。`sha256` 用于完整性校验（apply 下载后比对，防篡改）。
- `artifacts.expires_at`：plan TTL，过期必须重 plan + 重 pre-apply 审批。
- `executor_runs`：连接 request、commit、plan artifact、工具链、凭据 session 和执行结果，是事故复盘与重试判断的事实源。

### 2.5 执行目录治理（重点：回答"平台重启后如何恢复"）
```
workspaces(id, name, remote_url, default_branch, created_at)   -- 工作仓库注册
workspace_checkouts(id, workspace_id, node_id, worktree_path,
                    branch, pinned_commit, purpose, leased_by_request_id,
                    leased_until, status[active|released|stale],
                    updated_at)                                  -- 执行节点本地副本
```
- **重启恢复**：平台启动时读 `workspace_checkouts where status=active`，按 `remote_url + branch + pinned_commit` 用 go-git `clone/fetch + checkout` 重建本地 worktree。
- **并发隔离**：每个工单 `leased_by_request_id` 独占一个 checkout（worktree），互不覆盖。
- **过期回收**：`leased_until` 到期且工单已终态的 checkout 释放。

### 2.9 Layer 规则集版本化与 stack 粒度（D24 可配置 + D26 版本化迁移）
```
-- (1) 层的逻辑身份：跨版本稳定，catalog_items 引用此
layer_logical_refs(
  logical_id uuid primary key,    -- 如 "layer-global-net" / "layer-middleware"，跨版本不变
  current_display_name,           -- 当前展示名（cosmetic，可变）
  notes, created_at)

-- (2) 整套分层方案的不可变版本快照（D26 核心表）
layer_rule_set_versions(
  version_id int primary key,     -- v1, v2, v3...，单调递增
  layers_json,                    -- 该版本所有层的完整定义快照（name/order/path_template/owning_team_pattern/depends_on/logical_id）
  status[active|superseded|deprecated|archived],
  is_default bool,                -- 是否出厂默认（v1 true）
  created_at, created_by,
  deprecated_at, sunset_at,       -- Tier 3 强制迁移窗口
  superseded_at, superseded_by)   -- 被哪个 version 取代

-- (3) stack 粒度策略（D24）
stack_grouping_rules(id, scope_type[catalog_item|layer|global],
                     scope_id, granularity[per-component|per-space|per-team|custom],
                     custom_rule_json, priority)

-- (4) 迁移审计 + 回滚（D26）
layer_migrations(
  id, from_version_id, to_version_id,
  batch_id,                       -- 迁移批次（QuiesceMode 粒度）
  stack_id, tier[1|2|3],
  old_path, new_path,             -- dry-run 对比快照
  state_mv_script_path,           -- Worker 跑的脚本路径（审计可溯）
  backup_token,                   -- StateBackup 回滚令牌
  status[planned|running|succeeded|rolled_back|failed],
  operator, approved_by,          -- 2 人签（Tier 2 必须）
  silence_until,                  -- 该 stack 漂移静默期
  created_at, completed_at)
```
- **核心模型**（D24+D26）：**整套分层方案不可变版本化**（layer_rule_set_versions，整体 v+1），不是单 layer 版本化；每个层有**跨版本稳定的逻辑身份**（layer_logical_refs.logical_id）。
- **引用规则**：`catalog_items.layer_logical_id`（稳定身份）+ `stacks.layer_rule_set_version_id`（创建时 pin，不可变）；layer 规则升 v 时 catalog_items **零改动**，自然只影响新 stack。
- **出厂 seed**：v1 包含三条默认 layer_logical_refs（global/middleware/application）+ 一条 layer_rule_set_versions（v1, status=active, is_default=true），对应 docs/02 §1 三层。
- **stack_grouping_rules**：决定 stack 粒度（per-component 默认 / per-space / per-team / custom），catalog 项可声明 `stack_grouping` 字段直接覆盖。
- **layer_migrations**：记录每次迁移的 per-stack 分类（Tier 1/2/3）、state mv 脚本、备份令牌、2 人审批、静默期，是审计 + 回滚的真相源；Tier 3 stack 在 sunset 前必须有对应 destroy+recreate 计划。
- **owning_team_pattern**（存在 layers_json 内）：如 `dba|middleware` 表达"DBA + 中间件两部门并列同层"，`business-*` 表达"不同业务部门"。

### 2.10 审批引擎（D11/D21，权威定义；docs/12 §6 同步引用此）

```
approval_flows(id, name, trigger[dsl_when], dsl_yaml, version, active)        -- 审批流定义（YAML DSL 编译产物）
approval_runs(id, request_id, flow_id, current_node, status[pending|approved|rejected|timeout|cancelled],
              gate[pre-plan|pre-apply],                 -- D21 双门：准入 vs 执行确认
              started_at, finished_at)
approval_node_runs(id, run_id, node_id, mode[single|countersign|conditional],
                   decided_count, required_count, status, timeout_at)
```

- **D21 双门禁**：`approval_runs.gate` 区分 `pre-plan`（准入，OPA 可自动放行低危）与 `pre-apply`（执行确认，输入=plan 差异 + 成本 + 漂移校验，不可免审）。
- **节点绑角色不绑人**：`approval_node_runs.node_id` 关联 `approval_flows.dsl_yaml` 中的节点定义（节点声明 `roles: [dba-approver]` 而非具体人），由 RBAC `role_bindings`（§2.7）解析实际审批人。
- **升级节点**：DSL 支持条件升级（如成本超预算 → 自动插入成本审批节点），`approval_runs.status` 体现当前流态。

### 2.11 CMDB 与 FinOps（D18，权威定义；docs/14 §2 同步引用此）

```
resources(id, stack_id nullable, space_id nullable, team_id nullable, layer, address, type,
          cloud_provider, region, cloud_resource_id, name,
          tags_json, attributes_json, monthly_cost_estimate_cents, currency,
          managed bool,                                  -- true=平台管理 / false=孤儿（云侧有 CMDB 无）
          first_seen_at, last_synced_at)
cost_records(id, period_month, team_id, space_id, stack_id, resource_id nullable,
             cloud_provider, service_code, amount_cents, currency,
             cost_source[bill|estimate],                 -- 双源：云账单 vs Infracost 估算
             tags_json, recorded_at)
cost_budgets(id, scope_type[team|space|stack|layer], scope_id,
             period_month, budget_cents,
             alert_thresholds_json,                      -- 多级阈值如 [50%,80%,100%]
             alert_status[ok|warning|exceeded])

                       resource_id, detail_json, estimated_saving_cents,
                       status[open|dismissed|applied], created_at)
```
- **CMDB 不复制 state**：`resources.attributes_json` 只存可查询元数据（type/cloud_id/tags/估算成本），不存 state 全文；state 仍在远程 backend（§2.3 stacks.state_key 指向）。
- **apply 后入库**：apply 成功后 ingester 从最新 state JSON 解析资源 upsert `resources` 表（spec/15 Scenario）；`stack_id` 关联归属。
- **孤儿判定**：`resources.managed=false` 表示云侧有但 CMDB 平台管理集合外（漂移检测 + 云资源清单对账产出，docs/13 §5 衔接）。
- **双成本源**：`cost_source=bill` 来自云账单 API（按 tag 归集，延迟天级），`=estimate` 来自 Infracost（实时，决策用）；预算判定**用 estimate 实时触发告警 + 升级审批，用 bill 月末核销**（避免账单延迟漏报）。

### 2.12 云账号与凭据（D23，权威定义；docs/06 §4 同步引用此）

```
cloud_accounts(id, provider[alicloud|aws|azure], account_id, alias, display_name,
               default_region, credentials_ref,                -- bootstrap 凭据引用
               billing_enabled bool, default_team_id,          -- 账单归集默认归属团队
               tags_json, oidc_trust_configured bool,          -- 平台是否已作该账号 Trusted Issuer
               bootstrap_status[ok|rotate|none], created_at)
team_cloud_grants(id, team_id, space_id nullable, cloud_account_id,
                  allowed_layers,                              -- [Global|Middleware|Application] 子集，驱动申请过滤
                  iam_role_template,                           -- TmExec-<Team>-<Capability>
                  budget_quota_cents, expires_at,              -- 授权额度 + 过期
                  -- D27 env 维度授权：空数组=全 env；非空限定 env_logical_id
                  env_scope_json,                              -- 如 ["prod","staging"]，prod 严 dev 松分级治理
                  granted_by, granted_at)
cloud_credentials(id, cloud_account_id, team_id nullable, space_id nullable, -- team_id NULL=bootstrap
                 credential_type[bootstrap|execution_long_lived|execution_oidc],
                 name, secret_ref,                             -- 密文存 Vault/KMS，DB 仅存引用
                 iam_role_assumed,                             -- execution: assume 的云侧角色
                 status[active|rotating|revoked|expired],
                 rotated_at, rotate_after,                     -- 轮换窗口（长存强制 90 天）
                 guardians_json,                               -- bootstrap: 守护人列表（双审）
                 last_used_at, last_used_by_request, created_at)
catalog_items_required_permissions(catalog_item_id, provider, permission)   -- 如 (dba/rds, alicloud, rds:*)
iam_role_templates(id, name, team_id, cloud_account_id,
                   permissions_json,                           -- 聚合自 catalog required_permissions
                   cloud_role_name,                            -- 云侧实际角色名
                   oidc_audience, oidc_sub,
                   managed_by_bootstrap bool,                  -- 是否由 bootstrap 凭据 provision
                   version, updated_at)
```
- **三层凭据**（D23）：`bootstrap`（每云账号 1 套，vault 级，`guardians_json` 双审 + 强制轮换）/ `execution_*`（per-team，OIDC 优先免长存，fallback `execution_long_lived` 90 天强轮换）/ 个人**仅 RBAC**（不进此表，禁持执行凭据）。
- **team_cloud_grants 驱动申请过滤**：申请页"目标云账号"由 `team_cloud_grants where team_id=?` 决定（"看部门开通了哪些云厂商/账号"的实现）。`space_id` 为空表示 team 级授权；非空表示更小爆炸半径的 space 级授权。
- **team_cloud_grants.env_scope_json**：D27 引入的 env 维度授权。空数组 `[]` = 全 env；非空如 `["prod"]` 表示仅 prod。与 `allowed_layers` 一起驱动"申请页可选云账号+env+层"三维过滤，实现"dev 自助 / prod DBA 审批"的分级治理。
- **凭据不入 git/日志/codegen**：codegen 写占位符 `__TM_SECRET_<NAME>__`，Executor 运行期从 `cloud_credentials.secret_ref` 解析注入 env（详见 docs/11 RunSpec.Env）。
- **OIDC 联邦**：`cloud_accounts.oidc_trust_configured=true` 时，平台作 Trusted Issuer；`cloud_credentials.credential_type=execution_oidc` 走 ephemeral token（无轮换）。
- **IAM 角色模板化**：`iam_role_templates.permissions_json` 聚合自 `catalog_items_required_permissions`，由 `bootstrap` 凭据在云内 provision 实际角色；OPA 二次校验申请项 ↔ 角色权限。

### 2.13 环境与租户网络模型（D27，权威定义；docs/07 §2 同步引用此）

```
environments(id, env_logical_id,                       -- dev/staging/prod/dr（稳定身份）
             stage[dev|staging|prod|dr],               -- 决定治理强度（prod 强审批/dev 自动放行）
             cloud_account_id,                          -- 默认云账号（escape hatch 时 binding override）
             region, network_topology[shared|distributed],
             tag_namespace_json,                        -- D28 L2 层来源：env 级 tag 默认
             status[active|frozen|deprecated], created_at)
tenants(id, tenant_logical_id, name,
        isolation_level[vpc-per-env|account-per-env],  -- 仅 2 档（D27 简化）
        kind[internal|external],                        -- 外部客户/独立 BU；informational，不驱动隔离逻辑
        owner_team_id,                                  -- 租户归属团队（治理负责人）
        tag_namespace_json,                             -- D28 L3 层来源：tenant 级 tag
        status[active|frozen|deprecated], created_at)
environment_tenant_bindings(id, env_id, tenant_id, layer_logical_id,   -- 三元组 UNIQUE
                            vpc_stack_id,                -- 引用 Global 层 VPC stack（输出 vpc_id/vswitch_ids）
                            subnet_blocks_json,          -- 子网 CIDR 列表
                            security_group_base_id,      -- 该租户环境的基础安全组
                            override_cloud_account_id,   -- account-per-env 模式必填，覆盖 environments.cloud_account_id
                            status[active|pending-cleanup], created_at)
```
- **Environment 一等对象**：env 是治理对象（不是 stack 字段）。`stacks.env` 保留为反规范化便利，权威以 `environments` 表为准。每个 env 决定 stage→治理强度（prod 强审批 / dev 自动放行）、region、默认 tag 命名空间。
- **Tenant 一等对象**：默认存在 `platform-default` 单租户（"内部共享"语义）。内部多 BU / 外部客户场景创建独立 tenant。
- **isolation_level 仅 2 档**（业界 2026+ 已收敛）：
  - `vpc-per-env`（默认）：**一个 tenant × 一个 env = 一个独立 VPC**。如"corp-a 的 test 环境 = 一个 VPC"。目录划分清晰、state 命名空间天然隔离、跨租户通 CEN。
  - `account-per-env`（escape hatch）：强合规/外部客户场景，每 tenant+env 独立云账号（binding.override_cloud_account_id 必填）。
- **EnvironmentTenantBinding = (env × tenant × layer) 三元组 → 网络作用域解析**：codegen 参数解析 Stage 4 的查询入口。Application 层 stack 创建时 MUST 有对应 binding，否则 codegen 拒绝（结构化错误："管理员未配置 env=prod + tenant=corp-a + Application binding"）。
- **vpc_stack_id 引用规则**：MUST 指向 Global 层 stack（`layer_logical_id = Global`）；该 stack 的 outputs MUST 含 `vpc_id` + `vswitch_ids`（codegen 校验）；同一个 VPC stack 可被多个 (env, tenant, layer) binding 引用（如 Middleware + Application 共享同一 VPC）。
- **account-per-env 不变量**：binding.override_cloud_account_id MUST ≠ environments.cloud_account_id；该 cloud_account_id MUST 在 cloud_accounts 表存在且 active；rotation/credential 流程走 D23 §2.12 标准 cloud_credentials 表（per-team OIDC 优先）。
- **跨租户网络**：CEN / VPC Peering / Transit Gateway 不进此表，由 Global 层独立的 `cen-<tenantA>-<tenantB>-prod` stack 治理。
- **创建顺序约束**：先 environments → 再 tenants → 再 environment_tenant_bindings（依赖前两者）；binding 引用的 vpc_stack_id 必须先存在（Global 层 VPC stack 预创建）。

### 2.14 标签命名空间（D28，权威定义；docs/08 §2 同步引用此）

```
tag_policies(id, scope_type[platform|env|tenant|team|space|catalog_item],
             scope_id,                                  -- 对应表 id（platform 时为常量 'platform'）
             tag_namespace_json,                        -- 强制 tag 键值对
             mandatory_keys_json,                       -- 强制必须存在的 key 列表（值可空）
             user_allowed_tag_keys_json,                -- 用户白名单（默认空数组=用户不能加自定义 tag）
             version, updated_at)
```
> 实际 tag 来源分层在 D28 §（1）定义为 7 层（L1 platform-mandated / L2 env / L3 tenant / L4 team-space / L5 stack / L6 catalog / L7 user）。本表是 L2/L3/L4/L6 的配置存储；L1/L5 由 codegen 派生不存表；L7 存 catalog_items.user_allowed_tag_keys_json + requests.form_values_json。
- **scope_type 决定合并优先级**：L2(env) < L3(tenant) < L4(team/space) < L6(catalog)；同 key 后层覆盖前层（L4 覆盖 L2 的同名 key）；L1 永远赢，用户尝试覆盖 silently ignore + 审计告警。
- **mandatory_keys_json**：声明"这些 key 必须存在"，缺失时 codegen Stage 9 校验失败（强制 tag 治理）。平台初始化时为 `scope_type=platform` 注入 `mandatory_keys_json=["platform-managed","platform-team","platform-space","platform-stack"]`。
- **版本化**：tag_policies.version 递增，old version 保留审计；改动写 `tag_policy_versions` 副表（结构同 tag_policies + `superseded_by`）。
- **脱敏/校验**：tag 值在 codegen Stage 9 经过云厂商约束校验（长度/字符集/保留字），违规 sanitize 或拒绝（结构化错误：`"tag value '...' exceeds alicloud 128 char limit"`）。

### 2.15 CICD 触发记录（D16）
```
-- AI Generated Start
cicd_triggers(id, request_id nullable, cicd_kind[pipeline|webhook|manual],
              pipeline,                          -- CI pipeline 标识（如 gitlab-ci:project-abc:main 或 jenkins:job-xyz）
              commit, artifact,                  -- CI commit hash + 制品引用
              catalog_item_id, form_hash,
              triggered_by,                      -- 触发者身份（CI 服务账号 AK/SK）
              idempotency_key,                   -- sha256(pipeline + ":" + commit + ":" + catalogItem + ":" + form_hash) UNIQUE
              created_at)
gate_subscriptions(id, request_id, mode[poll|webhook],
                   webhook_url, secret_ref, expires_at)
gate_events(id, request_id,
            status[pending|admission-approved|plan-ready|approval-granted|
                   applying|apply-succeeded|rejected|timeout|failed],
            occurred_at, actor_id, detail_json)
-- AI Generated End
```
- **幂等键**：`idempotency_key` 全局 UNIQUE，必须包含 `form_hash`，避免同 pipeline+commit+catalogItem 但参数不同误复用旧工单。
- **与 requests 的关系**：`request_id` nullable。校验通过才写 requests 并回填 `request_id`；校验失败不写 requests 但保留 `cicd_triggers` 记录供审计。
- **Gate 语义**：`approval-granted` 仅表示审批已通过；`apply-succeeded` 才表示资源已落地，CD 默认应等待后者。
- **权威定义见 docs/16 §3 + §8**。

## 4. 关键查询

- **工单当前状态**：`requests` + 最新 `request_events`。
- **某团队可见目录**：`catalog_items` join `visibility ∋ team_id`。
- **漂移看板**：`drift_records where status=open`，按团队/层聚合。
- **执行目录一致性**：对账任务遍历 `stacks`，对照工作仓库目录与远程 state key 列表，标记 `missing`/`orphan`。

## 5. 扩展与迁移

- 所有 JSON 字段（contract/schema/defaults/diff）单独存储，便于演进，避免频繁 schema 迁移。
- 表采用 `id`（UUID/雪花）主键 + 业务唯一约束（如 `stacks(space_id, component, env)` 唯一）。
- 迁移：平台自带 schema migration（如 goose/atlas），`scripts/迁移/` 存放迁移脚本（对应 config 产物规整约定）。
