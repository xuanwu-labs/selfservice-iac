# 09-代码生成机制

> 对应 design `D3/D19`、spec `specs/05-代码生成引擎`（codegen 是 specs/05，编排引擎是 specs/06）。回应：表单如何生成对应的 Terraform 代码；for_each 多实例怎么最优解（要不要 wrapper）。

## 1. 一句话定位

**平台自研 Go codegen**（`server/core/codegen`，Go `text/template` 驱动），输入四要素动态合并，输出完整 stack 目录树（Terramate stack + Terraform module 调用 + backend + 跨层 data）。**不**依赖 Terramate generate 生成业务代码。

## 2. 关键澄清：与 Terramate generate 的关系

| | 平台 codegen | Terramate generate |
|---|---|---|
| 定位 | 表单 → 业务代码的主路径 | 编译期静态模板（可选辅助） |
| 输入 | 9 阶段参数解析（动态合并，详见 §3 + docs/08） | 静态模板 + 固定上下文 |
| 何时用 | 每次工单 generating 阶段 | 批量初始化环境/骨架（可选） |

design D3「generate 生成骨架 + for_each 运行」中的 generate 指**代码生成动作**（平台 codegen），非特指 `terramate generate` 子命令。主路径是平台 codegen，因表单是动态的需要 9 阶段参数解析合并（详见 §3 + docs/08）；Terramate generate 是静态模板不适合。

## 3. 参数解析管道（权威见 docs/08 §3）

codegen 不重复定义 rank。参数优先级、冲突解析、tag 合并和 provenance 结构以 `docs/08-标签分层与参数解析管道.md` 为唯一权威。

Phase 1 可使用 5 阶段简化管道：`contract → defaults → governance → user → dependency`；Phase 2 切换到完整 S1-S9。两者的字段名、source 名称和 provenance 输出必须可兼容，避免后续迁移时改变审批展示与审计语义。

## 4. 合并算法（核心，9 阶段伪码）

```
resolved = {}                                  # 最终输出
provenance = {}                                # 每变量的来源审计（写入 resolved_params_json）

# S1 模块契约兜底骨架
for var in module_contract.variables:
    resolved[var.name] = var.default
    provenance[var.name] = {source: "module_contract", rank: 8}

# S2 catalog defaults 覆盖（rank 7）
merge_overwrite(resolved, catalog.default_values_json, provenance, rank=7, source="catalog_default")
merge_tag_layer(resolved.tags, catalog.default_tags_json, layer="L6")

# S3 layer rule 治理覆盖（rank 2，治理硬规则）
for rule in layer_rule_set.applies_to(catalog_item):
    enforce(resolved, rule, provenance, rank=2, source="layer_rule")

# S4 env 上下文（rank 6，注入 vpc_stack_id 元变量 + 网络上下文）
binding = lookup_environment_tenant_binding(env_id, tenant_id, layer_logical_id)
if not binding: reject("binding_missing")
merge_overwrite(resolved, {vpc_stack_id: binding.vpc_stack_id, subnet_ids: binding.subnet_blocks, ...},
                provenance, rank=6, source="env_context")

# S5 tenant 上下文（rank 5）
merge_tag_layer(resolved.tags, tenant.tag_namespace_json, layer="L3")
merge_overwrite(resolved, tenant.network_context_vars, provenance, rank=5, source="tenant_context")

# S6 team 策略（rank 3，治理类）
enforce_team_policy(resolved, team.policy_json, provenance, rank=3, source="team_policy")
merge_tag_layer(resolved.tags, team.tags_json, layer="L4")

# S7 跨层依赖（rank 6 上下文，同 rank 时 S4 优先——S4 注入 vpc_stack_id，S7 用它生成 remote_state）
inject_remote_state_and_data_sources(resolved, stack_dependencies, resolved.vpc_stack_id)

# S8 用户表单（rank 4，用户显式）
validate_user_tags(user_form.tags, catalog.user_allowed_tag_keys_json)  # 白名单校验
merge_overwrite(resolved, user_form.values, provenance, rank=4, source="user_form")
merge_tag_layer(resolved.tags, user_form.tags, layer="L7")

# S9 平台强制注入（rank 1，绝对）
resolved.tags = enforce_L1_platform_mandatory(resolved.tags, provenance)  # L1 永远赢
resolved.state_key = path_generator_output                                   # D6
resolved.tags.platform_stack = stack_logical_id                              # L5 自动派生

# 校验门复检
validate_required_fields(resolved, contract)
validate_tag_completeness(resolved.tags)  # L1 四 tag 必须存在
validate_tag_cloud_constraints(resolved.tags, cloud_provider)

# 写 provenance 审计
write_requests_resolved_params_json(request_id, resolved, provenance)
```

**冲突解析示例**：用户填 storage=200（rank 4）vs catalog default storage=100（rank 7）→ 最终 storage=200，provenance 记 user_form 覆盖 catalog_default。layer rule 强制 encrypt=true（rank 2）vs 用户填 false（rank 4）→ 最终 true，provenance 记 user_attempted_override=true。

## 5.1 Phase 0 输出契约（实现前冻结）

codegen 的输出不是“若干文件”，而是一个可测试契约。`server/core/codegen` 必须返回以下结构给 orchestrator，workspace 只负责写文件和 commit。

| 契约 | 字段 | 说明 |
|------|------|------|
| `ResolvedParams` | `values` | 最终变量值 |
| `ResolvedParams` | `provenance` | 每变量 `{source,rank,overridden_from,user_attempted_override}` |
| `ResolvedParams` | `tags` | 7 层 tag 合并结果 |
| `ResolvedParams` | `policy_flags` | `cost_overrun`、`high_risk`、`binding_missing` 等 |
| `PathGeneratorOutput` | `repo_path` | stack 目录路径 |
| `PathGeneratorOutput` | `state_key` | backend key |
| `PathGeneratorOutput` | `stack_id` | Terramate stack ID |
| `PathGeneratorOutput` | `terramate_tags` | layer、tenant、env、team 等 |
| `GeneratedFile` | `path` | 相对 stack 目录文件名 |
| `GeneratedFile` | `content_sha256` | 文件内容哈希，用于确定性测试 |
| `GeneratedFile` | `kind` | `stack_tm` / `backend` / `main` / `providers` / `outputs` / `cross_layer` |

Phase 1 golden test 必须断言：同一输入两次 codegen 的 `repo_path`、`state_key`、`stack_id`、`terramate_tags`、`GeneratedFile.content_sha256` 完全一致。

### 6.1 增量生成（2026-07-16 补充）

> **性能保证**：codegen 不全局重新生成。每次工单只生成该工单涉及的 stack（1 个 catalog_item → 1 个 stack 目录）。其他 stack 代码不动，git diff 干净。

| 场景 | 生成范围 | 耗时 |
|------|---------|------|
| 用户申请 1 个 RDS | 生成 1 个 stack 目录（stack.tm.hcl + main.tf + backend.tf + cross-layer.tf）| 秒级 |
| 全局初始化（首次部署）| 生成所有 stack | 分钟级（仅一次）|
| 上游 VPC outputs 变更 | stack.tm.hcl 的 `watch` 字段触发下游 stack 标 changed；Terramate `--changed` 只重 plan 变更的 | Terramate 自动处理 |

**不变量**：同工单重跑 generating 产相同 commit（确定性，D19）。codegen 只写文件，不感知 git（doc 10 §3 衔接契约：workspace manager 负责 git add/commit）。

### 6.1 module source 构造（git 源 vs TF Registry 源）

> **Gap 记录（2026-07-24，W1-03 审查发现）**：doc 09 模板用 `{{.ModuleSource}}` 但未定义来源。Terraform module 有两种来源（git 源 / TF Registry 源），source URL 构造方式不同。本节补充设计。

#### 两种 module 来源

| 来源 | source 格式 | 版本锁定 | 凭证 | 适用 |
|------|------------|---------|------|------|
| **git 源**（MVP 默认）| `git::ssh://...//atomic/ecs?ref=commit_sha` | `?ref=commit_sha`（不可变）| GIT_SSH_COMMAND env | 自建原子层仓库（terraform-alicloud-modules/atomic/）|
| **TF Registry 源**（W2 扩展）| `namespace/name/cloud` | `version = "1.0.0"` | .terraformrc token（私有 registry）| 公共/私有 TF Registry 模块 |

#### modules 表加 source_type 字段（W2 migration）

```sql
ALTER TABLE modules ADD COLUMN source_type TEXT NOT NULL DEFAULT 'git';
  -- 'git'       = git 仓库源
  -- 'registry'  = TF Registry 源
ALTER TABLE modules ADD COLUMN registry_source TEXT NOT NULL DEFAULT '';
  -- source_type='registry' 时填，如 "terraform-aws-modules/vpc/aws"
```

#### codegen 构造逻辑（W2 实现）

```go
func buildModuleSource(mod Module, ver ModuleVersion) (source, version string) {
    switch mod.SourceType {
    case "registry":
        source = mod.RegistrySource  // "terraform-aws-modules/vpc/aws"
        version = ver.Version        // "5.0.0"
    default: // "git"（MVP 默认）
        source = fmt.Sprintf("git::%s//%s?ref=%s",
            mod.GitSource, mod.ModulePath, ver.CommitSha)
        version = ""  // git 源用 commit_sha 锁定，不用 version
    }
    return
}
```

#### 生成的 main.tf 对比

```hcl
# git 源（当前原子层）
module "ecs" {
  source = "git::ssh://git@github.com/org/tf-modules.git//atomic/ecs?ref=abc123"
  instance_type = "ecs.g7a.2xlarge"
}

# TF Registry 源（W2 扩展）
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"
  cidr    = "10.0.0.0/16"
}
```

#### MVP 决策

- MVP 只支持 git 源（source_type 默认 'git'），因为原子层代码在 `terraform-alicloud-modules/atomic/`（git 仓库）
- W2 扩展 registry 源（source_type='registry' + registry_source 字段）
- codegen 的 `buildModuleSource` 按 source_type 分支

## 7. 生成流程

```
[表单提交 form_values]
    ▼
[Load] 契约 + defaults_json + 依赖图（元数据）
    ▼
[Merge] 9 阶段参数解析（优先级算法见 §4，provenance 写 resolved_params_json）+ 校验 required
    ▼
[Render] Go 模板渲染每个 .tf（按 cardinality 决定是否 for_each）
    ▼
[Inject] 强制 tag + state key + 跨层 data
    ▼
[fmt] terraform fmt（保证格式）
    ▼
[Write] 写入 worktree（确定性路径）
    ▼
[git commit] 到 auto/<request-id> 分支
    ▼
[Next] planning（terramate run plan）
```

## 8. 多实例策略（cardinality 驱动，模块零侵入，D25 重点）

### 8.1 核心原则：模块零侵入

**模块定义单实例语义，平台调用方注入多实例语法**——`for_each` 是 Terraform **调用语法**不是**定义语法**，模块零感知。

- 模块的 `variables.tf` **永远是 scalar**（`variable "instance_type" { type = string }`）
- 模块的 `main.tf` 是**单实例 resource 定义**
- 多实例配置（`cardinality` 等）属于 **catalog 项平台元数据**（DB 表 `catalog_items`），**MUST NOT 写入模块仓库**
- codegen 在**生成的 stack main.tf** 注入 `for_each`/`count`
- **社区模块（terraform-aws-modules / 官方 alicloud）直接复用零适配**

### 8.2 三种方案对比

| 方案 | 做法 | 评价 |
|------|------|------|
| A 裸 for_each | stack main.tf 直接 `module { for_each = toset(...) }` | 原生，但 codegen 要懂多实例维度，耦合业务 |
| B wrapper module | 注册时把原子模块包一层 wrapper，wrapper 内 for_each | **反模式**：多一层 module、state 路径复杂、版本双重维护 |
| **C codegen 调用方注入（推荐，D25）** | **catalog 项**声明 cardinality，codegen 在调用方生成原生 for_each/count | 最优：原子模块零感知，TF 原生，社区模块直接用 |

### 8.3 业界对照
- **HashiCorp 官方 module registry**：模块按单实例设计，消费者 for_each（社区共识）
- **Spacelift**：stack 级 TF for_each/count，不在模块层包装
- **Env0**：同上，workflow 内 TF 原生 for_each
- **共识**：**模块单实例设计 + 消费侧 for_each**，不用 wrapper

### 8.4 最优解（方案 C 详细，三种 cardinality）

**catalog 项配置**（`catalog_items` 表，**不污染 modules 表**）：
```json
{
  "cardinality": "map",                  // single（默认）/ list / map
  "instance_key": "role",                // map 模式的 key 含义（角色名）
  "per_instance_fields": ["instance_type", "disk_size", "instance_count", "tags"],
  "shared_fields":     ["vpc_id", "zone", "security_group"]
}
```

**模块契约**（`modules.variables_contract_json`，**纯 scalar，零侵入**）：
```json
{
  "variables": [
    {"name":"instance_type","type":"string","required":true},
    {"name":"disk_size","type":"number"},
    {"name":"instance_count","type":"number"},
    {"name":"vpc_id","type":"string","required":true},
    {"name":"zone","type":"string"}
  ]
}
```

**codegen 生成——cardinality=single**（默认，无 for_each）：
```hcl
module "rds" {
  source  = "github.com/org/tf-rds"
  instance_type = "mysql.n2.large.1c"
  disk_size     = 200
  vpc_id        = data.terraform_remote_state.vpc.outputs.vpc_id   # shared 注入
}
```

**codegen 生成——cardinality=list**（同质多实例，count）：
```hcl
module "ecs" {
  source  = "github.com/org/tf-ecs"
  count   = 3
  instance_type = "ecs.c6.large"   # shared
  name    = "order-${count.index + 1}"
  vpc_id  = data.terraform_remote_state.vpc.outputs.vpc_id
}
```

**codegen 生成——cardinality=map**（异构多实例，for_each tomap，key=角色名）：
```hcl
module "ecs" {
  source   = "github.com/org/tf-ecs"   # 同一模块，variables.tf 全 scalar 不变
  for_each = tomap({
    web   = { instance_type = "ecs.c6.large",   disk_size = 40,  instance_count = 3 }
    api   = { instance_type = "ecs.c6.xlarge",  disk_size = 100, instance_count = 2 }
    batch = { instance_type = "ecs.r6.2xlarge", disk_size = 200, instance_count = 1 }
  })
  # per_instance 字段（从 each.value 取，模块 var 仍是 scalar）
  instance_type  = each.value.instance_type
  disk_size      = each.value.disk_size
  instance_count = each.value.instance_count
  # shared 字段（不进 map，stack 级直接注入）
  vpc_id         = data.terraform_remote_state.vpc.outputs.vpc_id
  zone           = var.zone
}
```

**原子模块不变**：模块的 `variable "instance_type" { type = string }` 永远是 scalar，**不知道**自己被 for_each。

**stack outputs 自动聚合**（codegen 生成 outputs.tf）：
```hcl
output "instance_ids" {
  value = { for k, m in module.ecs : k => m.instance_id }
  # → { web = "i-xxx", api = "i-yyy", batch = "i-zzz" }
}
```

### 8.5 为什么不用 wrapper（B）

- 额外 module 层 → state 路径 `module.wrapper["i"].module.atomic.x`，diff 噪音大
- wrapper 要随原子模块版本同步维护，注册负担 ×2
- TF 原生 for_each 已足够，wrapper 无收益
- 业界（Spacelift/Env0/官方）都不用 wrapper，属反模式

### 8.6 for_each vs count

- **for_each（推荐）**：key 有语义（`each.key = "web"`），增删实例不影响其他（key 稳定）
- **count**：索引 key，删除中间项会触发整列重建，**避免**

codegen 默认用 for_each（key = 实例标识变量），除非 catalog 项显式声明 `cardinality: count`（少见场景）。

### 8.7 同模块不同 cardinality（零侵入的灵活性）

同一 ECS 模块可被多个 catalog 项以不同 cardinality 调用：
- catalog 项 A（单实例场景）→ cardinality=single
- catalog 项 B（多角色场景）→ cardinality=map

**模块仓库 0 字节改动**，差异全在 catalog 项配置（DB）。

### 8.8 与 PathGenerator 的衔接（codegen 单管道）

codegen 是单一管道，PathGenerator（D24 算路径）与 CardinalityInjector（D25 注入调用语法）是管道里的两个阶段（详见 docs/02 §8）。两者都消费 catalog 项元数据，都不污染模块仓库。

## 9. 关键技术点

- **契约提取**：注册时解析 `variables.tf`（terraform-config-inspect）→ variables_contract_json，**纯 scalar 契约（零侵入，不含 cardinality）**。
- **cardinality 归属**：catalog 项层面配置（`catalog_items` 表），不在 modules 表；codegen 按 catalog 项的 cardinality 在调用方注入 for_each/count。
- **表单裁剪**：契约几十个变量，只暴露 form_schema_json 指定的少数字段，其余走 defaults（产品化核心）。
- **敏感字段**：sensitive=true 的变量不进 git 明文，占位符 `__TM_SECRET_<NAME>__` + 运行期 Executor 从 secret store 注入 env（详见 docs/06 §5 + specs/16）。
- **跨层注入**：依赖图告诉 codegen 依赖谁，自动生成 remote_state data + 变量绑定（docs/02 §4）。
- **PathGenerator**：codegen 调用 PathGenerator（D24）按 layer.path_template 渲染 stack 路径与 state key，MUST NOT 字符串拼接。
- **确定性**：同工单重跑 generating 产出相同代码（路径 + 内容确定），git diff 可验证。

## 9.5 stack.tm.hcl 生成（D29 Terramate 元数据）

> codegen 为每个 stack 目录生成 `stack.tm.hcl`，使 Terramate 能做栈发现、依赖排序、标签过滤、变更传播。**不用 `terramate generate`**，由平台 codegen 直接产出。

### 生成模板

```hcl
# {stack_dir}/stack.tm.hcl — codegen 生成，MUST NOT 手动编辑
stack {
  id    = "{layer}-{tenant}-{team}-{component}-{env}"   # PathGenerator 输出，全局唯一
  name  = "{component} for {team} in {env}"
  tags  = [
    "layer:{global|middleware|application}",             # 层过滤（terramate run --tags "layer:application"）
    "tenant:{tenant}",                                   # 租户隔离（terramate run --tags "tenant:corp-a"）
    "env:{env}",                                         # 环境过滤
    "team:{team}",                                       # 团队归属
  ]
  after = [{上游 stack 相对路径列表}]    # 跨层依赖序（Application after Global VPC）
  watch = [{上游 stack}/outputs.tf]     # 上游输出变了→本 stack 标 changed
}
```

### 字段来源

| 字段 | 来源 | 备注 |
|------|------|------|
| `id` | PathGenerator 输出（D24） | 全局唯一，`^[a-zA-Z0-9_-]{1,64}$`，全小写 |
| `tags` | codegen 从 request 上下文派生 | tenant/env/team/layer 四维，Terramate `--tags` 过滤依据 |
| `after` | stack_dependencies 表（跨层依赖图） | Application→Global VPC；CEN→所有关联 VPC |
| `watch` | 自动推导（依赖的上游 stack 的 outputs.tf） | VPC 变更→Application 自动感知重 plan |

### 生成时机
