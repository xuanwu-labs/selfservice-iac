# 06-云账号与凭据管理

> 对应 design `D23`、spec `specs/16-云账号与凭据管理`。重点回应"如何管理云厂商 AK/SK / 平台是否配 admin / 每团队还是每人 / 生命周期 / 用于 terraform/terramate 执行的凭据 / 申请时如何看部门开通了哪些云厂商"。

## 1. 设计目标（一句话）

**平台代跑（不是人手跑）+ per-team 而非 per-person + OIDC 优先免长存 + 角色模板化最小权限 + 团队↔云账号授权驱动申请过滤。**

业界共识：Spacelift / Env0 / Terraform Cloud / HashiCorp Vault 全部走 OIDC 联邦 + 平台代跑 + 动态凭据； Atlantis（GitOps 派）也强制在 runner 内执行不发个人 AK/SK。"给每个人发云 AK/SK 跑 terraform"是公认反模式。

## 1.1 Day-0 Bootstrap 权威流程

云账号从 0 到首个真实 apply 的启动顺序以 `docs/06a-云账号Bootstrap手册.md` 为准。本文定义长期凭据模型；`docs/06a` 定义第一天如何接入首个云账号、写入 bootstrap 凭据、配置 OIDC trust、创建首个 execution role、发放 `team_cloud_grants` 并完成首个 plan/apply。

实现要求：

- 没有通过 bootstrap 验收的云账号不得出现在申请页。
- `team_cloud_grants` 必须由 bootstrap 流程或后续授权流程创建，不允许手工绕过审计写库。
- 首个 apply 必须验证日志和 git 中无 AK/SK 明文。

## 2. 三层凭据模型

| 层 | 作用域 | 用途 | 形态 | 谁配置 | 风险等级 |
|----|--------|------|------|--------|----------|
| **Bootstrap / Admin**（引导） | 每云账号 **1 套** | 开通云账号、IAM 配置、配 OIDC trust、读账单、建子角色 | 长期 AK/SK（vault 级） | 平台运维（1–2 守护人，**双人审批 + 轮换 + 全审计**） | 极高 |
| **执行凭据**（Execution） | **per-team / per-space × per-cloud_account** | 平台代跑 `terraform/terramate` 时 assume 的 IAM 身份 | **OIDC 联邦优先**（短期 ephemeral STS，无长存 AK/SK）；fallback 长 AK/SK（强制轮换） | 平台运维 + 团队 owner | 中 |
| **个人**（Personal） | 每用户 | UI 操作 RBAC、查看、审批、提交申请 | **平台身份（OIDC token）/ 不发云凭据** | 用户自助（无云凭据） | 低 |

**关键约束**：个人 MUST NOT 持有执行云凭据——平台执行（平台代跑 terraform），不是人手跑；个人只走 RBAC + 平台身份认证。

### 2.1 为什么 per-team 不是 per-person

1. **执行主体是平台不是人**——terraform 由 Executor 跑（specs/11），用户只在 UI 提申请，不需要个人云凭据。
2. **team/space 是治理边界**——成本归集、爆炸半径、审计都以 team/space 为单位（与 D18 FinOps 对齐）。
3. **审计可追溯**——"哪个团队的执行身份动了什么资源"比"哪个人"更稳定（人离职/调岗即风险，团队稳定）。
4. **个人零云凭据 = 零泄漏面**——人离职不需要吊销一堆个人 AK/SK。

### 2.2 为什么 OIDC 联邦优先

- **零长期凭据**——按需签发 STS（1h 过期），不存 AK/SK。
- **业界事实标准**——aws/alicloud/azure 全支持 OIDC trust，Spacelift/Env0/TFC/Vault 全用。
- **泄漏面 = 零**——吊销 = 撤 trust policy，无需轮换密钥。
- **离线/不支持 OIDC 才 fallback**——长存 AK/SK 仅作逃生通道，强制 90 天轮换。

## 3. 团队↔云账号授权（`team_cloud_grants`，驱动申请过滤）

> 这是"看部门开通了哪些云厂商/账号"的实现。

```
team_cloud_grants(team_id, cloud_account_id, allowed_layers, iam_role_template,
                  budget_quota, expires_at, granted_by, granted_at)
```

- **作用**：显式声明"哪个团队可在哪个云账号下申请哪些层的资源"。
- **申请入口过滤**：`GET /catalog` + `GET /requestable-cloud-accounts` 按调用者 `team_id` join 此表 → 只返回授权的云账号 + catalog 项；前端"目标云"下拉只列这些。
- **多维过滤**：①云账号白名单（部门能从哪些云厂商申请）；②layer 限制（业务团队不能申请 Global 层）；③IAM 角色模板（决定能 assume 哪个角色）；④配额（与 D18 预算联动）；⑤过期（动态失效）。

### 3.1 申请页"目标云"过滤示例

| 团队 | 授权的 cloud_account | 申请页可见 |
|------|---------------------|-----------|
| 平台运维 | alicloud:corp-prod-1, aws:corp-prod-2 | 两个云账号 + Global/Middleware/Application 全层 |
| DBA | alicloud:corp-prod-1 | 仅 alicloud + Middleware(RDS) 层 |
| 业务 A | alicloud:corp-prod-1 | 仅 alicloud + Application 层 |
| 业务 B | （无 grant） | 申请页"目标云"空 → 引导联系平台运维 |

## 4. 数据库表（补充 docs/04）

```sql
-- 云账号纳管
cloud_accounts(
  id, provider,              -- alicloud/aws/azure
  account_id, alias,         -- 云侧账号 ID + 平台别名
  default_region,
  oidc_trust_configured,     -- 是否已配 OIDC trust
  bootstrap_credential_ref,  -- 指向 secret store（密文不在此）
  enabled, created_at, updated_at
)

-- 团队↔云账号授权（驱动申请过滤，权威定义见 docs/04 §2.12）
team_cloud_grants(
  id, team_id, cloud_account_id,
  allowed_layers,            -- [Global|Middleware|Application] 子集
  iam_role_template,         -- TmExec-<Team>-<Capability>
  budget_quota,              -- 月度预算（联动 D18）
  env_scope_json,            -- D27 env 维度授权：[] 全 env；非空限定 env_logical_id（如 ["prod"]）
  expires_at,                -- NULL=永久；到期自动失效
  granted_by, granted_at
)

-- 凭据元数据（密文存 secret store，DB 仅存引用）
cloud_credentials(
  id, cloud_account_id, team_id,  -- team_id NULL 表示 bootstrap
  credential_type,          -- bootstrap|execution_long_lived|execution_oidc
  name,                     -- 人类可读名
  secret_ref,               -- 指向 Vault/KMS/内嵌 secret store
  iam_role_assumed,         -- execution: assume 的角色
  status,                   -- active|rotating|revoked|expired
  rotated_at, rotate_after, -- 轮换窗口
  guardisans,               -- bootstrap: 守护人列表
  last_used_at, last_used_by_request,
  created_at
)

-- catalog 项声明 required_permissions（specs/02 补充）
catalog_items_required_permissions(
  catalog_item_id, provider, permission  -- 如 (dba/rds, alicloud, rds:*)
)

-- IAM 角色模板
iam_role_templates(
  id, name, team_id, cloud_account_id,
  permissions_json,        -- 聚合自 catalog required_permissions
  cloud_role_name,         -- 云侧实际角色名
  oidc_audience, oidc_sub,
  managed_by_bootstrap,    -- 是否由 bootstrap 凭据 provision
  version, updated_at
)
```
> **权威定义见 docs/04 §2.12**（含 `cloud_accounts.tags_json` / `oidc_trust_configured` / `bootstrap_status` 等字段完整说明，docs/06 与 docs/14 旧版差异已统一）。

## 4a. 源码仓库凭据（git clone 凭证，D23 扩展）

> **Gap 记录（2026-07-24，W1-03 审查发现）**：D23 三层凭据模型覆盖云账号（bootstrap/execution/personal），但**未覆盖 git clone 私有模块仓库的凭证**。本节补充设计，复用 D23 骨架（SecretStore + 注入 + 审计 + 不落盘）。

### 问题场景

模块注册（W1-03 RegistryService）和 codegen 后 terraform init 都需要 clone 外部 git 仓库（`modules.git_source`）。如果仓库是 **private**（企业内部 module 仓库、私有 fork），需要凭证。

### 设计：扩展 credentials 表 kind 字段

```sql
-- 扩展 cloud_credentials → credentials（通用凭据表，W2 落地）
-- 新增 kind 字段区分云/git/registry
credentials (
    id              BIGINT PK,
    kind            TEXT NOT NULL,  -- 'cloud'（D23 原有）| 'git'（新增）| 'registry'（新增，TF Registry token）
    -- kind='cloud' 字段（D23 已有）
    cloud_account_id BIGINT NULL,
    team_id          BIGINT NULL,
    -- kind='git' 字段（新增）
    git_provider     TEXT NULL,     -- 'github'|'gitlab'|'gitea'|'generic'
    -- 通用字段
    scope_type       TEXT NOT NULL, -- 'platform'|'team'|'module'
    scope_id         TEXT NOT NULL, -- platform=常量 / module=module_id
    name             TEXT NOT NULL, -- "GitHub Deploy Key"
    credential_type  TEXT NOT NULL, -- git: 'ssh_key'|'https_token'|'github_app'
                                    -- cloud: 'bootstrap'|'execution_long_lived'|'execution_oidc'
    secret_ref       TEXT NOT NULL, -- Vault/KMS 引用（不存明文）
    status           TEXT NOT NULL DEFAULT 'active',
    rotated_at       TIMESTAMPTZ,
    rotate_after     INT,           -- 轮换天数（git 同 execution_long_lived 90 天）
    last_used_at     TIMESTAMPTZ,   -- 审计
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
)

-- modules 表加字段（W2 migration）
ALTER TABLE modules ADD COLUMN git_credential_id BIGINT NULL REFERENCES credentials(id);
  -- NULL = public repo（无需凭证）
```

### 注入路径（两条独立链路）

```
链路 A：注册时 clone（RegistryService，W1-03）
  1. 按 modules.git_credential_id 查 credentials → secret_ref
  2. SecretStore.GetSecret(secret_ref) → SSH key / token 明文（短期内存）
  3. GoGitProvider.CloneOptions.Auth = BasicAuth(token) 或 GIT_SSH_COMMAND
  4. clone + 提取契约 → 销毁内存凭据
  5. 审计：audit_logs(action="git.clone", target=git_source, credential_id)

链路 B：terraform init 时拉 module（Executor，W2）
  1. Executor.Run 前，按 modules.git_credential_id 解析凭据
  2. 注入子进程 env：GIT_SSH_COMMAND="ssh -i <key>" 或 ~/.netrc（HTTPS token）
  3. terraform init 读 env → clone private module 到 .terraform/modules/
  4. 执行完清除 env（D23 §5 不入 git/日志模式）
```

### MVP vs W2 分界

| 阶段 | git 凭证方式 | 适用场景 |
|------|------------|---------|
| **MVP（当前）** | 环境变量（GIT_TOKEN / GIT_SSH_COMMAND），全平台单一身份 | public repo 或单一 private org |
| **W2（完整）** | credentials 表 kind='git' + SecretStore + per-module credential_ref | 多 org 不同凭证 + 审计 + 轮换 |

### 为什么复用 credentials 表（不新建 git_credentials）

- 统一 SecretStore（一套 Vault/KMS 集成，不重复）
- 统一轮换策略（rotate_after + rotated_at）
- 统一审计（last_used_at + audit_logs）
- 统一注入路径（CloneOptions.Auth / Executor env）

## 5. 凭据注入 Executor（不入 git/日志）

```
[codegen 阶段] 敏感字段写占位符 __TM_SECRET_<NAME>__（不写真值）
   ↓
[Orchestrator 调 Executor.Run 前]
   凭据解析器 CredentialResolver.Resolve(team, cloud_account, catalog_item)
       → OIDC 路径：拿平台内部 token → AssumeRoleWithWebIdentity → STS（1h）
       → 长存路径：从 secret store 取 AK/SK
       → 返回 env map
   ↓
[Executor.Run] 注入子进程/容器 env（AWS_* / ALICLOUD_*）
   - worktree/git 始终只有占位符
   - 日志经 LogSink → 脱敏管道 → request_events
   ↓
[Run 结束] STS 自然过期 / 长 AK/SK 留 secret store（不落子进程文件）
```

### 5.1 日志脱敏管道

- **正则规则**：AKIA[0-9A-Z]{16}（aws AK）、LTAI[0-9A-Za-z]{12,}（alicloud AK）、已知 secret 值的 SHA256 前缀匹配 → 替换 `***REDACTED-<hash6>***`。
- **覆盖范围**：terraform stdout/stderr、terramate 输出、Executor 日志、审计日志全链路。
- **兜底**：CI 跑 GitHub secret scanning 同款规则扫描工作仓库提交。

### 5.2 占位符填充契约

```hcl
# codegen 生成的 staging（占位符）
provider "alicloud" {
  access_key = "__TM_SECRET_ALICLOUD_ACCESS_KEY__"
  secret_key = "__TM_SECRET_ALICLOUD_SECRET_KEY__"
  region     = "cn-hangzhou"
}
# Executor.Run 执行前：
#   ① 不改文件（保持占位符进 git）
#   ② 解析占位符 → 注入 env ALICLOUD_ACCESS_KEY/SECRET_KEY
#   ③ provider 块在 terraform 解析时 env 优先于字面值 → 用 env 跑
```

## 6. IAM 角色与权限模板化

```
catalog 注册 dba/rds → 声明 required_permissions=[alicloud:rds:*, vpc:DescribeVSwitches]
   ↓
平台聚合 catalog required_permissions → 生成/更新 iam_role_templates
   → TmExec-DBA-RDS（策略：rds:* + vpc:DescribeVSwitches，最小权限）
   ↓
bootstrap 凭据在云账号内 provision 实际角色（alicloud RAM role）
   + 配 OIDC trust（audience/sub 映射 platform team）
   ↓
执行时 OIDC token assume TmExec-DBA-RDS → STS
   ↓
OPA 二次校验"申请项(dba/rds) ↔ 团队执行角色权限" 一致
```

### 6.1 标准角色示例

| 团队 | 角色 | 权限（聚合自 catalog） |
|------|------|-----------------------|
| 平台运维 | TmExec-Platform-VPCAdmin | vpc:*/slb:*/nat:*/ack:* |
| DBA | TmExec-DBA-RDS | rds:*/redis:*/vpc:DescribeVSwitches |
| 中间件 | TmExec-MW-Kafka | kafka:*/rocketmq:* |
| 业务 A | TmExec-BusinessA-ECS | ecs:Run*/slb:* (只读 vpc) |

## 7. 凭据生命周期与轮换

| 类型 | 轮换 | 注销 | 检测 |
|------|------|------|------|
| OIDC ephemeral | 无需（自然过期） | 撤 trust policy | 不需要 |
| 长期执行 AK/SK | **强制 90 天**（可配）+ 泄漏紧急 | 删 grant 即失效 | 到期 7 天前告警 |
| Bootstrap Admin | **双人审批** + 全审计 | 平台下线/迁移 | 操作即审计 |

**扫描任务**：
- 每天 02:00 扫 `cloud_credentials` 找 `rotate_after < now()+7d` → 告警运维 + owner。
- 每天 03:00 跑泄漏检测（secret scanning 规则扫近期日志 + 工作仓库）→ 命中即强制轮换。

## 8. 申请页"目标云"过滤实现

```go
// GET /requestable-cloud-accounts?team_id=X&env=Y
func listRequestableCloudAccounts(ctx, teamID, envLogicalID) []CloudAccount {
    // join team_cloud_grants + cloud_accounts，过滤 expires_at + env_scope_json
    return db.Query(ctx, `
        SELECT ca.* FROM cloud_accounts ca
        JOIN team_cloud_grants g ON g.cloud_account_id = ca.id
        WHERE g.team_id = ?
          AND g.expires_at > now()
          AND ca.enabled = true
          AND (g.env_scope_json = '[]' OR JSON_CONTAINS(g.env_scope_json, ?))
    `, teamID, envLogicalID)
}

// GET /catalog?team_id=X&cloud_account_id=Y&env=Z&layer=W
//   过滤掉 team 无 grant 的云账号下的 catalog 项 + allowed_layers 不匹配 + env_scope 不匹配
//   D27 引入 env 维度授权：dev 自助 / prod DBA 审批 的分级治理载体
```

## 10. 安全检查清单（落地验收）

- [ ] 任意工单的 worktree / git 提交内容 grep 不到明文凭据（含占位符除外）
- [ ] 任意日志（terraform/terramate/Executor/审计）grep 不到 AK 形态字符串
- [ ] 个人用户在 DB 查不到关联的执行云凭据（只有平台身份）
- [ ] 未授权团队 GET /catalog 看不到未授权云账号 + catalog 项
- [ ] bootstrap 凭据轮换走双人审批 + 全审计
- [ ] OIDC trust 撤销后该团队执行立即失败（无长存兜底）
