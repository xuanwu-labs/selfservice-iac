# 15-存量导入

> 对应 design `D14`、spec `specs/12-存量导入`。重点回应 Q6：存量资源如何 import 纳管，输入 ID 从注册表模块导入。

## 1. 技术基础：Terraform 1.5+ 声明式 import 块

```hcl
import {
  to = module.rds.alicloud_db_instance.this
  id = "rm-bp1xxxxxxx"
}

# 配合 plan 自动生成配置
# terraform plan -generate-config-out=generated.tf
```
- 声明式、HCL 原生、可版本控制、可 `for_each` 批量。
- `plan -generate-config-out` 自动生成 resource 配置骨架（需 review 清理）。
- import 后 `plan` 应显示 `0 to add/change/destroy`（代码与存量一致）。

**业界引用**：
- [HashiCorp Import 官方文档](https://developer.hashicorp.com/terraform/language/import)
- [Terramate 官方 import 指南](https://terramate.io/rethinking-iac/a-comprehensive-guide-to-importing-existing-infrastructure-into-terraform-and-opentofu/)（与平台引擎契合）

## 2. 平台向导流程（4 步）

```
[选目录项/模块] → [输入资源 ID] → [生成 import 块 + module 骨架] → [import + plan 验证 + 纳管]
```

1. **选模块**：从模块注册表（`module-registry`）选已 validated 的原子模块（决定生成的代码结构）。
2. **输入资源 ID**：用户填云端资源 ID（如 `rm-bp1xxx`）；平台预检：provider 是否支持该资源 import。
3. **生成并 import**：平台生成 `import {}` 块 + module 调用骨架 → 容器内 `terraform apply`（仅 import）落 state → `plan -generate-config-out` 生成配置 → 标记待 review。
4. **验证纳管**：review 清理配置后，`plan` 须 0 变更 → 创建 stack 记录、纳入漂移检测、加入 bundle 归属。全程走工单（审批 + 审计）。

### 2.0 存量生命周期（从观察到可变更）

存量资源默认不直接进入“标准可变更”状态。平台先接管可观测性，再逐步开放自动化变更：

| 生命周期 | 含义 | 平台能力 | 退出条件 |
|----------|------|----------|----------|
| `discovered` | 云侧 inventory 发现但未确认 owner | 只展示清单和疑似归属 | owner 确认或标记忽略 |
| `candidate` | 已确认要纳管，尚未 import | import 预检、模块匹配建议 | 选择 catalog/module + 输入 ID |
| `imported-limited` | 已写 state，但 schema 不完整或 provider/import 有限制 | state 观察、人工修复任务 | 修复 limited/sensitive 字段 |
| `managed-readonly` | 已有 stack/state/CMDB/drift，但禁止平台 apply | 漂移检测、成本归属、审计查询 | 人工 review + plan 零变更 |
| `managed-changeable` | 允许平台受控变更，但仍标记为存量来源 | plan/审批/apply | tag、依赖、模块契约全部达标 |
| `standard` | 与平台新建资源等价 | 全能力 | 无 |

`managed-readonly` 是默认安全落点：当用户手工习惯、资源命名、tag、依赖图与平台规范冲突时，平台先保证“看得见、审得清、可追踪”，而不是立刻允许自动变更。

### 2.1 纳管时补全 stack 元数据（D24/D26 衔接，关键）

第 4 步"创建 stack 记录"必须补全以下字段，否则存量资源与新生成资源在治理上不一致：

| stacks 表字段 | 来源 | 说明 |
|--------------|------|------|
| `layer_logical_id` | 用户在向导选择归属层（Global/Middleware/Application） | 引用 layer_logical_refs 稳定身份（D26） |
| `layer_rule_set_version_id` | 创建时 pin 当前 active 版本 | 与新生成 stack 一致，遵循 D26 版本化契约 |
| `migration_status` | 默认 `stable` | 同新生成 stack，参与后续 layer 规则迁移流程 |
| `bundle_id` | 用户在向导选归属项目组 | nullable（无 bundle 时 NULL） |
| `owner_team_id` | 用户在向导选归属团队 | 决定 RBAC/审批/成本归集 |
| `repo_path` / `state_key` | PathGenerator 按 layer.path_template 渲染 | **存量导入也走 PathGenerator**（D24），不字符串拼接 |
| `catalog_item_id` | 关联到向导选择的 catalog 项 | 决定后续变更走哪个 codegen 模板 |

### 2.2 与主干流水线衔接（复用，不另造）

存量导入**复用主干流水线，但默认进入 read-only 过渡**：
- **codegen**：复用 `platform/internal/codegen`（specs/05），import 块由 codegen 在 PathGenerator + CardinalityInjector 之后追加（不另写 codegen）。
- **worktree + pinned_commit**：复用 `platform/internal/workspace`（docs/10），import 工单的 commit 同样锚定 pinned_commit。
- **Executor**：复用 `platform/internal/executor`（docs/11 D20），import 走四模式之一，与 plan/apply 同一沙箱。
- **审批双门禁**：复用 `platform/internal/approval`（docs/12 D21），import 工单走 Gate1（准入，可能 OPA 放行）+ Gate2（执行确认，必人审，因为 import 涉及 state 写入）。
- **漂移检测**：`managed-readonly` 阶段即可加入漂移检测池，但 drift 修复只能生成工单，不能自动 apply。
- **CMDB**：import 完成后 ingester 读 state 入 `resources` 表（docs/14），标记 `managed=true` 且记录 import lifecycle。
- **变更开放**：只有 `plan=0`、敏感字段处理完成、tag/owner/依赖图补齐后，才能从 `managed-readonly` 升为 `managed-changeable`。

### 2.3 与 D26 层规则迁移的关系

已纳管的存量 stack 与新生成 stack **同等参与** layer 规则集版本迁移：
- layer 规则升 v 时，MigrationPlanner 对存量 stack 也 dry-run 分类 Tier 1/2/3。
- 存量 stack 若 path_template 改了，同样走 StateMover Worker 跑 state mv。
- 这是为什么 §2.1 强调"补全 layer_rule_set_version_id pin"——没有这字段，存量 stack 在迁移期会失联。

## 3. 难点处理

| 难点 | 处理 |
|------|------|
| 资源与模块 schema 不匹配 | 向导按模块地址 `module.xxx.resource` 生成 import target；不一致则提示调整变量/换模块 |
| provider 不支持 import | 标 `limited`，提供半自动 state 编辑指引，apply 受限、漂移检测仍生效 |
| 敏感字段（密码/token）不可读 | 配置留空标 `sensitive`，工单提示补填，补填前 apply 受限 |
| 批量 | `for_each` 生成一组 import 块，批量录入 ID，逐台报告 |
| 生成代码冗余/敏感默认 | 标"待 review"，人工清理（移除明文密码、归整字段）后才纳管 |
| 资源缺标准 tag / owner | 进入 `managed-readonly`，生成 `manual_intervention_tasks` 要求 owner/team 补齐 |
| 用户继续手工改云控制台 | 漂移记录不自动覆盖，先通知 owner；连续漂移可暂停该 stack 新申请 |

### 3.1 managed-readonly 运营规则

`managed-readonly` 不是永久状态，而是安全过渡状态。平台必须避免“只观察、不治理”的半纳管债务。

| 条件 | 动作 |
|------|------|
| 进入 `managed-readonly` 超过 30 天 | 通知 owner 提交晋级计划或标记豁免原因 |
| 超过 60 天仍未晋级 | 进入治理看板，降低资源目录推荐等级 |
| 超过 90 天仍未晋级且无豁免 | 升级到 owner 上级或平台治理例会 |
| owner 缺失 | 自动创建 P2 `manual_intervention_tasks`，禁止晋级 |
| 连续 3 次漂移 | 暂停该 stack 新变更，要求 owner 选择 adopt-cloud 或 restore-desired |
| tag/成本归属缺失 | 只允许查询和漂移，不允许 `managed-changeable` |

晋级到 `managed-changeable` 的最小条件：

- owner/team 明确。
- 必填 tag 完整。
- `plan=0`。
- 敏感字段处理完成。
- 依赖图或固定 dependency seed 完整。
- 最近一次 drift 已关闭或被接受。

允许长期停留在 `managed-readonly` 的豁免场景：

- 云厂商/provider 不支持安全 import。
- 资源属于外部系统托管，只允许平台观察。
- 合规要求禁止自动变更。

豁免必须有 owner、到期时间和复核周期。

## 4. 与模块注册表联动

- import 向导的"选模块"= 模块注册表（`specs/01-模块注册`）的已 validated 模块。
- 模块的变量契约（`variables_contract_json`）决定生成的 module 调用骨架 + import target 地址。
- 模块版本与 import 兼容（旧版模块可能字段变化）。

## 5. 数据库表（补充 docs/04）

```
-- AI Generated Start
import_jobs(id, module_version_id, catalog_item_id, bundle_id, requester_id,
            lifecycle[discovered|candidate|imported-limited|managed-readonly|
                      managed-changeable|standard|failed],
            status[pending|running|waiting-review|succeeded|failed|cancelled],
            review_required bool, created_at)

                 import_status[pending|imported|limited|sensitive|failed],
                 limited bool, sensitive_fields_json)
-- AI Generated End
```

## 6. 关键时序

```
用户选模块 + 输入 ID → 创建 import_job(工单)
  → 生成 import 块 + module 骨架 → commit 到 worktree
  → 容器内 terraform apply(import only) → 落 state
  → plan -generate-config-out → 生成配置(待 review)
  → 人工 review 清理 → plan 验证 0 变更
  → 创建 stack + managed-readonly(漂移检测/CMDB生效，禁止自动apply)
  → owner review + plan=0 + tag/依赖补齐
  → managed-changeable 或 standard → 归档 import_job
```

## 7. 辅助发现（可选）
对"不知道有哪些存量资源"的场景，可集成 [terraformer](https://github.com/GoogleCloudPlatform/terraformer)/[Terracognosa] 做云账号自动发现，但仅作"发现清单"辅助，正式纳管仍走上述声明式 import 流程（质量更可控）。
