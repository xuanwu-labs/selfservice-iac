# 01-目录骨架设计

> 对应 `design.md §03.2`。承载完整目录树、每个包职责、分层哲学。
> **本 change 采用领域核心顶层分层**（package-by-feature），与 internal-heavy（golang-standards/project-layout）流派不同：领域核心 `core/` 是顶层一等公民，`internal/` 只装私有基建。

## 1. 分层哲学（为什么不全塞 internal/）

业界两个流派，本 change 选 **领域核心顶层（package-by-feature）**：

| 流派 | 做法 | 代表 | 评价 |
|---|---|---|---|
| **internal-heavy** | 几乎所有应用代码塞 `internal/` | golang-standards/project-layout | `internal/` 本意是 Go 编译器访问控制，不是架构分层；把领域塞进去让系统心脏"藏起来" |
| **领域核心顶层（本 change）** | 领域核心 `core/` 顶层，`api/` 放 handler，`internal/` 只装私有基建 | DDD 项目、Kratos layout | 领域是一等公民显眼可见；`internal/` 回归"私有基建"本意；package-by-feature 业务演进友好 |

**关键洞察**：`api/` 字面即"API 实现"，放 handler 代码语义自洽；proto 契约是"接口定义"，归 `internal/proto/`（生成代码）+ 仓内/仓外 `.proto` 源（本平台 proto 源在仓库根 `contracts/`）。

## 4. 三层模型分离（DDD 规范）

这是最容易被忽视的优雅点。平台有三种"模型"，必须分开存放：

| 模型类型 | 是什么 | 放哪 | 示例 |
|---|---|---|---|
| **Entity**（数据模型）| 对应 DB 表的 struct | `internal/model/entity/` | `Team` struct（对应 teams 表）|
| **DTO / Proto Message**（传输模型）| API 请求/响应结构（proto 生成）| `internal/proto/` | `CreateTeamRequest` proto message |
| **Domain Object**（领域对象）| 业务逻辑 struct（含行为方法）| `core/<domain>/` | `CatalogService`（含 `ListItems()` 方法）|

**为什么不混在一起？**
- DB 表字段 ≠ API 返回字段（如 user 表有 password_hash，API 不返回）
- DB 表结构变化不该直接影响 API 契约
- 领域对象有业务方法（如 `Stack.CanApply()`），entity 不该有

**sqlc 项目的特殊形态**：
- sqlc 从 SQL 自动生成 model struct → `pkg/db/generated/models.go`（这是 sqlc 输出的一部分，checked in）
- 手写的 entity（如果有额外字段/校验标签/表名方法）→ `internal/model/entity/`
- `data/dbset/` 组合 sqlc 生成的 Queries + entity（如 `type Template struct { entity.Template }` 嵌入额外字段/方法）
- `internal/mapping/` 做 entity ↔ proto message 转换

**数据流**：
```
API 请求（proto message）→ mapping 转 entity → core 业务逻辑 → data/dbset 写 DB
                                                                      ↓
                                                          pkg/db/generated（sqlc 执行 SQL）
```

## 5. 与 iac-self-service-server/...s/03 的对照

原 docs/03 规划的 `server/internal/{api,auth,registry,catalog,...}` 扁平结构，本 change **重构为领域核心顶层三层**：
- 原 `internal/api` → 拆成 `api/{http,grpc}`（传输）+ `internal/server`（启动装配）
- 原 `internal/{registry,catalog,codegen,orchestrator,...}` → **提升到 `core/`**（领域核心顶层）
- 原 `internal/store` → `core/store`（薄包装）+ `data/`（pgxpool）+ `pkg/db`（sqlc）
- 原 `internal/{config,auth,httpclient}` → `internal/{micro/config,auth,httpclient}`（归类到基建）

**原 docs/03 作为权威业务包清单**保留参考，但物理位置以本 docs/01 为准（core 顶层）。

## 6. 边界约定（守护 D1）

- `server/go.mod` 是独立 module，与 Terramate 主 module 物理隔离。
- `.golangci.yml` 的 depguard 用**模块前缀 deny** `github.com/terramate-io/terramate`（根 + 全部子包），allow-list 默认空。
- **D1 内嵌 carve-out**：D1 保留了"未来可选 import Terramate Go 包做内嵌实现"。为兼容该未来路径，depguard 配置命名 allow-list（默认空），仅当未来启用内嵌适配器时，在 `core/terramate/embedded`（带 `//go:build terramate_embedded` 标签）显式 allow。本 change 不实现内嵌，allow-list 保持空。
- 平台只能通过 `core/terramate`（D1 exec 适配器）调用 terramate CLI 二进制。
- `make build` 与 `make test` 在 server/ 子树自洽，不依赖 Terramate 主 module。
