## D31 — 数据访问层：sqlc + pgx/v5

### 决策矩阵

| 维度 | GORM | sqlc（选定）| ent | sqlx/pgx |
|---|---|---|---|---|
| 类型安全 | ⚠️ 运行时反射 | ✅ 编译期 codegen | ✅ 编译期 codegen | ❌ 无 |
| SQL 控制力 | 隐藏/生成 | ✅ 手写 | 生成 | ✅ 手写 |
| D28 审计适配 | ⚠️ 不透明 | ✅ SQL 显式可追溯 | ⚠️ 间接 | ✅ 显式 |
| N+1 风险 | ⚠️ 高（懒加载）| ✅ 无 | ✅ 内置 eager | ✅ 无 |
| 迁移工具解耦 | ❌ 绑 AutoMigrate | ✅ 无关 | ⚠️ 耦合 | ✅ 无关 |
| 动态查询 | ✅ 易 | ⚠️ 需 squirrel | ✅ fluent | ✅ 手写 builder |
| 2025-2026 社区 | 下降（新项目搬离）| **上升（最推荐）** | 小众/忠诚 | 稳健兜底 |

### 拒绝理由

- **GORM**：反射式魔法 SQL + N+1 风险 + 审计不透明（D28 provenance 要求每行可追溯）→ 不满足审计硬要求。社区共识：2025-2026 新生产项目在搬离 GORM（Bytebase、Brandur 实证）。
- **ent**：schema-as-code 学习曲线高 + 与迁移工具耦合（ent generate 与 migration 绑定）→ 对 18 表关系型 + 审计场景，复杂度不成比例。
- **sqlx/pgx 裸写**：失去类型安全，scan 代码重复 → 作为 sqlc 不可用时的兜底，不作主力。

### 选定理由

1. **审计透明（守护 D28）**：sqlc 从手写 `.sql` 生成代码，审计员能把任何写入追溯到一行被 PR review 的 SQL。
2. **类型安全**：编译期检查，无运行时反射。
3. **multica 实证**：multica 用 sqlc + pgx/v5 跑 142 迁移、~700 query 稳定。
4. **与 goose 共用 SQL 真相源**：sqlc query 与 goose migration 都是 `.sql`，审计链路一致。

### 参考

- [Bytebase: Choose the Right Golang ORM or Query Builder (2025)](https://www.bytebase.com/blog/golang-orm-query-builder/)
- [Brandur: sqlc 2024 check in](https://brandur.org/fragments/sqlc-2024)
- [Jason Fowler: Why GORM Is Overrated (2025)](https://jsnfwlr.com/blog/2025/03/30/why-gorm-is-overrated/)
- [multica-ai/multica server/pkg/db](https://github.com/multica-ai/multica/tree/main/server/pkg/db)

## D33 — 数据库迁移：goose（`//go:embed` + 完整版本历史 + advisory lock）

### 决策矩阵

| 维度 | golang-migrate | goose（选定）| atlas | tern | 手写（multica 式）|
|---|---|---|---|---|---|
| 迁移格式 | 版本化 SQL | SQL 或 Go 函数 | 声明式 schema + 版本 | 版本化 SQL | 版本化 SQL |
| 版本历史 | ⚠️ 仅最后版本 | ✅ 完整历史 | ✅ 完整 + 哈希校验 | ✅ 完整 | ⚠️ 自实现 |
| //go:embed | ✅ iofs | ✅ **原生最佳** | ✅ SDK | ✅ | ⚠️ 自实现 |
| advisory lock | ✅ | ✅ | ✅ | ✅ | ❌ **（multica #3647 bug）**|
| 审计可审 | ✅ SQL 在 PR | ✅ SQL 在 PR | ✅ SQL 在 PR + atlas.sum | ✅ SQL 在 PR | ⚠️ 无篡改检测 |
| 依赖重量 | 轻 | **轻** | **重** | 轻 | 零（但自维护成本高）|
| 生产推荐 2025 | 广泛 | **Go 应用最推荐** | 先进/现代 | PG 专用 | 不推荐 |

### 选定理由（goose）

1. **原生 `//go:embed` 最佳**：goose 在所有迁移库里 `embed.FS` 支持最干净（`goose.Up(db, "migrations", goose.WithEmbedFS(fs))`），`aether` 单一产物分发零摩擦。
2. **advisory lock（关键）**：goose 内置锁，多实例/并发启动安全。**反例**：multica 手写迁移器因无锁导致 [issue #3647](https://github.com/multica-ai/multica/issues/3647) 并发冲突 bug —— 实证不该手写。
3. **完整版本历史**：goose 记录每个已应用版本（golang-migrate 只记最后版本），满足审计。
4. **依赖最轻**：单一库，符合"最小依赖"偏好。
5. **SQL + Go func 迁移**：数据回填场景可写 Go migration。

### 拒绝理由（含曾考虑过的 Atlas）

- **Atlas**：声明式 schema-as-code 与 Terraform 心智一致是吸引力，且 `atlas.sum` 哈希校验 + `migrate lint` 检测危险变更很强。但实证后放弃：(1) **依赖树最重**；(2) 两个参考项目（Terramate 无 DB / multica 手写）都没用 Atlas；(3) 学习曲线（diff/plan/apply + atlas.hcl）。**留作次选**：若未来想要声明式 schema drift 检测再评估。
- **golang-migrate**：只记最后版本 + 失败留 dirty 状态需手动修。
- **tern**：PG 专用，pgx 同源，但社区比 goose 小 + 锁定 PG。
- **手写（multica 式）**：无锁（#3647）+ 无篡改检测。
- **gorm AutoMigrate**：生产反模式。

### 参考

- [pressly/goose: Embedding migrations](https://pressly.github.io/goose/blog/2021/embed-sql-migrations/)
- [multica #3647: 手写迁移器无锁 bug](https://github.com/multica-ai/multica/issues/3647)（反例：不该手写）
- [Atlas vs Others](https://atlasgo.io/atlas-vs-others)
- [DEV.to: Best DB Migration Tools for Golang](https://dev.to/shrsv/best-database-migration-tools-for-golang-ajf)

## D34 — HTTP 路由：gin

### 决策矩阵

| 维度 | gin（选定）| chi | echo | stdlib net/http |
|---|---|---|---|---|
| 生态 | ✅ 最大 | 中 | 中 | ✅（stdlib）|
| 中间件 | ✅ 丰富 | 中 | 中 | 需自写 |
| 性能 | ✅ httprouter | ✅ | ✅ | ✅ |
| 绑定/校验 | ✅ ShouldBindJSON + validator | 需手工 | ✅ | 需手工 |
| 轻量度 | 中 | ✅ 轻量 | 中 | ✅ 最轻 |

### 选定理由（用户决策）

用户明确选 gin。理由：生态最大、中间件链成熟（RBAC/限流/审计/CORS/JWT 现成）、绑定/校验对 form_schema_json 友好。本平台中间件需求大，gin 的 `r.Use(mw...)` 天然适配。

### 次选

chi 更贴近 stdlib net/http、更轻量；若团队偏好 stdlib 风格可降级。但中间件生态比 gin 小，本平台中间件重，gin 更合适。

## D35 — 日志：zap 原生 Logger

### 选定理由（用户决策）

用户明确选 zap 原生 Logger API（非 SugaredLogger）。理由：
1. **性能**：zap 是 Go 结构化日志性能标杆（高并发下比 slog 快数倍），原生 API 性能最高。
2. **类型安全**：原生 API 强制 `zap.String("k", v)`/`zap.Int("n", n)` 显式字段类型，编译期检查（SugaredLogger 的 printf 风格是运行时反射）。
3. **生态成熟**：Uber 生产验证，与 OpenTelemetry（D41）桥接成熟（otelzap 把 trace_id 注入日志）。

### 备选

- **slog（stdlib）**：零依赖但性能低；zap 在结构化日志领域更久经考验 → 次选（若未来想降级到 stdlib）。
- **zerolog**：与 zap 同级，生态略小 → 拒绝。
- **SugaredLogger**：printf 风格易用但运行时反射，性能低 → 拒绝（用户性能优先选原生）。

### 使用模式

- 生产：`zap.NewProduction()`（JSON、info 级、堆栈采样）
- 开发：`zap.NewDevelopment()`（console、debug 级）
- 全局：`zap.ReplaceGlobals(logger)`，业务代码用 `zap.L().Info("msg", zap.String("k", v))`
- OTel 桥接：用 `otelzap`（go.opentelemetry.io/contrib/instrumentation）把 trace_id/span_id 注入每条日志

## D36 — 代码规范：Google Go Style Guide + golangci-lint

### 选定理由

Google Go Style Guide 是 Go 社区最完整的风格指南（含 StyleDecisions、Best Practices）。ECC 的 `golang-patterns` skill 与 `rules/golang/` 基于社区谚语，不引用谷歌规范 → 需独立固化。

### golangci-lint 启用规则

- `gofmt` / `goimports`：格式强制
- `govet`：基础静态检查
- `staticcheck`：深度静态检查
- `depguard`：自定义规则禁止 import terramate 内部包（守护 D1）

### ECC golang-patterns 的角色

作为**补充**（社区谚语 + 惯用法），不作为替代（它不引用谷歌规范）。

## D37 — 配置管理：viper（多源合并 + 热更新）

### 选定理由（用户决策）

用户明确选 viper。理由：
1. **多源合并**：平台需支持"配置文件（部署默认）+ env（K8s ConfigMap/Secret 注入）+ flag（运维临时覆盖）"三层优先级（D15），viper 是 Go 生态多源合并的事实标准。
2. **热更新**：viper 的 `WatchConfig` + `OnConfigChange` 支持 DB 连接池/日志级别等热调，对 D15（Web 可改配置）友好。
3. **生态最大**：Go 配置库采用度最高，文档/示例最多。

### 取舍（如实记录）

- viper 用 `interface{}` 取值（`viper.GetString("db.dsn")`），需类型断言或 `Unmarshal` 到 struct，配置错误运行时才报（不像 caarlos0/env 编译期检查）。
- 比"env+struct"重（反射 + 运行时魔法），但灵活性收益对多环境部署平台值得。

### 使用模式

```go
type Config struct {
    HTTPAddr   string        `mapstructure:"http_addr"`
    DB         DBConfig      `mapstructure:"db"`
    LogLevel   string        `mapstructure:"log_level"`
}
type DBConfig struct {
    DSN      string `mapstructure:"dsn"`
    MaxConns int32  `mapstructure:"max_conns"`
    Timeout  string `mapstructure:"timeout"`
}

func Load() (*Config, error) {
    viper.SetConfigName("platform")          // platform.yaml/json/toml
    viper.AddConfigPath("/etc/platform/")
    viper.AddConfigPath(".")
    viper.AutomaticEnv()                      // env 覆盖
    viper.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
    viper.BindPFlag("http_addr", pflag.Lookup("addr"))  // flag 覆盖
    viper.SetDefault("http_addr", ":8080")
    viper.SetDefault("log_level", "info")
    if err := viper.ReadInConfig(); err != nil { return nil, err }
    var cfg Config
    if err := viper.Unmarshal(&cfg); err != nil { return nil, err }
    viper.WatchConfig()                       // 热更新
    viper.OnConfigChange(func(e fsnotify.Event) {
        zap.L().Info("config reloaded", zap.String("file", e.Name))
    })
    return &cfg, nil
}
```

启动时 `zap.L().Info("config loaded", zap.Any("config", redact(cfg)))` 打印脱敏 Config（DSN 密码脱敏 `****`）。

### 备选

- **env+struct（手写 helper）**：零依赖、最显式（multica 实证），但不支持文件/flag 多源 → 次选。
- **koanf**：viper 的轻量替代，模块化无反射，但生态小 → 次选。
- **caarlos0/env**：纯 env → struct，极轻但不支持配置文件 → 拒绝（需要文件源）。

## D38 — 依赖注入：google/wire（编译期 codegen）

### 选定理由

理由：
1. **编译期检查**：缺失/歧义依赖在 `wire gen` 失败，不是启动才报。对 14 核心层的中大型平台，依赖图复杂，wire 收益大。
2. **生成代码可审计**：`wire_gen.go` 是手写风格 Go（无反射/运行时容器），守护 D28 审计透明。
3. **各层解耦**：`ProviderSet` 按层聚合，`cmd/wire.go` 只组装，符合分层架构。

### 接线模式

```go
// core/core.go
var ProviderSet = wire.NewSet(
    registry.ProviderSet,
    codegen.ProviderSet,
    orchestrator.ProviderSet,
    // ... 各业务服务
)

// cmd/server/wire.go
//go:build wireinject
func InitializeApp(cfg *Config) (*App, func(), error) {
    panic(wire.Build(
        api.ProviderSet,
        core.ProviderSet,
        data.ProviderSet,
        config.ProviderSet,
    ))
}
```

### 备选

- **手动构造器**：最显式但接线超一文件后冗长 → 次选（降级路径）。
- **uber-go/fx**：运行时容器 + 生命周期钩子，反射与 D28 审计冲突 + 过重 → 拒绝。
- **samber/do**：generics 运行时容器，采用度小 → 拒绝。

### 参考

- [google/wire](https://github.com/google/wire)
- [Kratos layout wire 约定](https://github.com/go-kratos/kratos-layout)（cmd/server/wire.go）

## 补充：作为开源项目的 DB 层选择（gorm vs sqlc 开源视角）

selfservice-iac 选 sqlc 而非 ORM（如 gorm），核心原因是**审计要求与场景**：

| 维度 | ORM（gorm/xorm）| sqlc（本平台选定）|
|---|---|---|
| 审计透明度 | 反射拼 SQL + hooks 可悄悄改写 → **审计死穴** | 每条 SQL 明文在 `.sql` 文件，PR 可 review |
| DB 适配 | 多 DB 抽象（优势在需多 DB 时）| PG-only（本平台只需 PG，ORM 优势无用）|
| 迭代速度 | CRUD 重、快迭代 | 需手写 SQL，迭代稍慢但可控 |

**开源项目实测（go.mod 实证）**：
- bytebase/bytebase（DB DevSecOps）→ **裸 database/sql + pgx**（要每条 query 可见）
- multica-ai/multica → **sqlc + pgx**
- casdoor/casdoor → gorm（需支持 5+ DB）
- go-gitea/gitea → xorm（多 DB）

**规律**：数据越敏感、审计越严 → 越倾向裸 SQL/sqlc；越要快迭代/多 DB → 越倾向 ORM。selfservice-iac 的 D28/D30 审计要求是 ORM 的死穴（反射 SQL + hooks 可绕过 PR review 悄悄改写），故选 sqlc。

## D45 — RPC 框架：Connect-RPC（proto 唯一真相源 + gRPC-Web 原生 + 与 gin 共存）

### 选定理由（用户决策 + 约束推导）

用户要求：proto 唯一真相源 + 前端 gRPC-Web + 最小依赖 + 不引 Kratos + gin 做 webhook/运维。Connect-RPC 是唯一同时满足所有的：

1. **proto 唯一真相源（决定性）**：一个 `.proto` 生成一个 handler，同时说 gRPC + gRPC-Web + Connect/JSON 三协议 —— 避免手写 HTTP/gRPC 两套 handler（两套会漂移，违背"唯一真相源"）。
2. **前端 gRPC-Web 无 Envoy**：Connect 原生说 gRPC-Web 协议。标准 gRPC-Web 需 Envoy 代理转换 + 有"失败返回 HTTP 200"观测陷阱（trailer 丢失）。Connect 把 EOS metadata 嵌入 JSON 消息，避免该问题。
3. **与 gin 共存**：Connect handler 是标准 `http.Handler`，和 gin 挂同一 `http.ServeMux`（一进程一端口）。gin 服务 webhook/运维，Connect 服务全部业务 RPC。
4. **最小依赖**：1 核心库 + 2 代码生成插件 + 0 基础设施（无 Envoy）。
5. **wire-compatible 与 grpc-go**：服务间调用可用任何 gRPC 客户端连。
6. **CNCF 项目 + Anthropic 生产用**。

### 协议分工（明确边界）

| 调用方 | 协议 | 工具 |
|---|---|---|
| 业务 RPC（全部）| Connect handler | connect-go |
| 前端 React | gRPC-Web（Connect 原生）| connect-es |
| aether CLI | Connect/JSON（HTTP/1.1，curl 可调）| connect-go client |
| 服务间（orchestrator→executor）| gRPC（HTTP/2）| connect-go / grpc-go client |
| Webhook 回调 | HTTP/JSON | gin（D34）|
| 运维端点（/healthz、/metrics）| HTTP/JSON | gin（D34）|

### 备选

- **grpc-go + Envoy（gRPC-Web）**：成熟但需 Envoy 基础设施 + 200-on-error 陷阱 → 拒绝（违背最小依赖 + 观测有坑）。
- **grpc-gateway**：proto 生成 REST，成熟但 5 插件 + OpenAPI 只 v2 + 无 bidi + 前端要 REST 而非 gRPC-Web → 拒绝。
- **手写 gin + grpc-go 两套 handler**：违背 proto 唯一真相源（两套真相源会漂移）→ 拒绝。
