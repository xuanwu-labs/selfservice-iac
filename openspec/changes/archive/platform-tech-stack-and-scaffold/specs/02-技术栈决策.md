# 02-技术栈决策（tech-stack-decisions）

能力 ID：`tech-stack-decisions`
覆盖：15 个实现级技术栈决策（D31–D45），每项含决策/理由/备选/影响，续 `iac-self-service-platform` 的 D1–D30 编号，可追溯。

## ADDED Requirements

### Requirement: 数据访问层决策（D31）
平台 SHALL 用 sqlc（codegen from hand-written SQL）+ pgx/v5（驱动）作为数据访问层，`core/store` 包装 sqlc 生成的 `*db.Queries`。SQL 文件是查询层与迁移层的共同真相源，守护 D28 provenance 审计可追溯。

#### Scenario: 审计可追溯到 SQL 行
- **WHEN** 审计员检查 `audit_logs` 或 `resolved_params_json` 的某行写入
- **THEN** 该写入对应一个 sqlc 生成的 query 方法，该方法对应 `pkg/db/queries/*.sql` 中一行被 PR review 过的 SQL，无反射/魔法生成

#### Scenario: 动态查询用 squirrel
- **WHEN** catalog 列表需要运行时多过滤组合（tenant/env/layer/status）
- **THEN** 该 query 用 `Masterminds/squirrel` 构造 WHERE，其余 query 全部静态 SQL

### Requirement: CLI 框架决策（D32）
平台 CLI `cmd/aether` SHALL 用 `spf13/cobra`（+ pflag），提供 catalog/request/stack/drift/approval/cost/gate/mcp/ai 9 个子命令。

#### Scenario: 子命令可发现
- **WHEN** 执行 `aether --help`
- **THEN** 输出含全部 9 个子命令名 + 分组（Core/Manage/Observe）+ 每个子命令的简短描述

### Requirement: 迁移工具决策（D33）
平台 SHALL 用 `pressly/goose/v3`，迁移文件 `db/migrations/NN_name.{up,down}.sql`，通过 `//go:embed` 编入 `cmd/migrate` 二进制，记录完整版本历史。

#### Scenario: 完整版本历史
- **WHEN** 执行 `aether migrate status`（或 `cmd/migrate status`）
- **THEN** 输出每个已应用迁移的版本号 + 时间戳，而非仅最后版本

### Requirement: HTTP 路由决策（D34）
平台 HTTP 传输层 `api/http` SHALL 用 `gin-gonic/gin`，支持 `/api/v1` 路由组 + 中间件链（request_id/recovery/logger/RBAC/限流/审计 占位）。

#### Scenario: 健康检查端点
- **WHEN** GET `/healthz`
- **THEN** 返回 200 + `{"status":"ok"}`（DB 可达）或 503 + `{"status":"unhealthy"}`（DB 不可达）

### Requirement: 日志决策（D35）
平台 SHALL 用 `go.uber.org/zap` 原生 `zap.Logger` API（`zap.L()` 全局 logger），生产用 `zap.NewProduction()`、开发用 `zap.NewDevelopment()`。所有包统一 `zap.L().Info/Error/Debug` + 显式类型字段（`zap.String`/`zap.Int`）。

#### Scenario: 结构化日志含 request_id
- **WHEN** 一个请求经 request_id 中间件处理
- **THEN** 该请求的所有 zap 日志行含 `"request_id":"<uuid>"` 字段（类型安全，非 printf 反射），可按 request_id 串联全链路

### Requirement: 代码规范决策（D36）
平台 SHALL 遵循 [Google Go Style Guide](https://google.github.io/styleguide/go/) + Effective Go，由 `.golangci.yml`（gofmt/goimports/vet/staticcheck/depguard）强制，工程契约写入 `server/AGENTS.md`。

#### Scenario: gofmt 不过 CI 红
- **WHEN** 一个 `.go` 文件未 gofmt
- **THEN** `make lint` 报错，退出码非 0，CI 阻断合并

### Requirement: 配置管理决策（D37）
平台 SHALL 用 `spf13/viper` 支持 yaml/json/toml 配置文件 + 环境变量 + 命令行 flag 多源合并（优先级 flag > env > file > default），并支持 `WatchConfig` 文件热更新。启动时 `viper.Unmarshal(&cfg)` 填充强类型 Config 结构。

#### Scenario: 启动打印脱敏配置
- **WHEN** `cmd/server` 启动
- **THEN** zap 日志输出 viper 合并后的 Config 结构（DSN 中的密码脱敏为 `****`），审计员可一眼看清多源合并结果

#### Scenario: 配置文件热更新
- **WHEN** 运维修改配置文件的 `log_level` 字段
- **THEN** viper 的 `OnConfigChange` 回调触发，日志级别热切换，无需重启进程

### Requirement: 依赖注入决策（D38）
平台 SHALL 用 `google/wire`（编译期 codegen）做依赖注入。各层（`api/`、`core/`、`data/`、`internal/`）用 `wire.NewSet(...)` 定义 `ProviderSet`，在 `cmd/server/wire.go` + `cmd/aether/wire.go` 用 `//go:build wireinject` 触发 `wire gen` 生成 `wire_gen.go`（checked in，无反射）。

#### Scenario: 依赖链编译期校验
- **WHEN** 一个 provider 缺失依赖（如 `NewOrchestrator` 需要 `Queue` 但未注册）
- **THEN** `wire gen` 在编译期失败，报缺失依赖，而非运行时启动才报

#### Scenario: 生成的装配代码可审计
- **WHEN** 审查 `cmd/server/wire_gen.go`
- **THEN** 全是手写风格 Go（构造器调用链），无反射/运行时容器，审计员可追溯完整依赖图

### Requirement: 任务队列决策（D39）
平台 SHALL 用 `riverqueue/river`（PostgreSQL-backed）做异步作业队列，入队与业务 DB 写入原子提交（`river.InsertTx`）。工单状态迁移与作业入队必须在同一事务。

#### Scenario: 入队与状态迁移原子
- **WHEN** 工单状态从 `plan-ready` 迁移到 `applying` 且同时入队 apply 作业
- **THEN** 两者在同一 PG 事务内，事务回滚则状态迁移与入队都不发生，无幽灵工单

### Requirement: 事件通知决策（D39）
平台 Phase 1（单进程）SHALL 对事件通知（drift.detected/approval.*/migration.*）**直接调用处理函数**，不引入 EventBus 接口、outbox 表、broker。需要重试的走 River 入队，需要异步的用 `go func()`，审计走 audit_logs 数据库记录。未来拆分多服务需跨进程事件分发时，再评估引入 broker（首选 RabbitMQ，详见 D39 备选）。

#### Scenario: 单进程事件直接处理
- **WHEN** orchestrator 发现漂移，产生 drift.detected 事件
- **THEN** 直接调用 `audit.Log()` + `notify.Send()` + `webhook.Send()` 等同进程函数处理；webhook 如需重试用 River 入队

#### Scenario: 未来拆服务引入 broker
- **WHEN** 平台拆分为多个独立服务，事件需跨进程分发给多个订阅者
- **THEN** 评估引入 RabbitMQ（首选，Go 官方客户端 + 死信原生 + Erlang 稳定性）或 Kafka（海量日志流场景）；Phase 1 不提前引入

### Requirement: JSON Schema 校验决策（D40）
平台 SHALL 用 `santhosh-tekuri/jsonschema/v6`（Draft 2020-12）校验 `form_schema_json`、`resolved_params_json`、API 入参 schema。

#### Scenario: form_schema 校验
- **WHEN** 注册一个 catalog item，其 `form_schema_json` 用 Draft 2020-12
- **THEN** 平台用 santhosh-tekuri 校验该 schema 自身合法 + 后续表单输入符合该 schema

### Requirement: 可观测性决策（D41）
平台 SHALL 用 OpenTelemetry 实现**端到端 trace 贯穿**（入口→RPC→DB→Redis→第三方 HTTP→日志，单一 trace_id 全链路传递）+ `otelzap` Mode 1 桥接 zap 注入 trace_id + metrics 走独立 Prometheus exporter（`/metrics` 端点）。trace 后端地址 SHALL 可通过 env `OTEL_EXPORTER_OTLP_ENDPOINT` 配置。

#### Scenario: 全链路 trace_id 关联
- **WHEN** 一个工单从表单提交流经 codegen→plan→apply→reconcile，涉及 pgx 查询、HTTP 调云 API、Connect 调微服务
- **THEN** 在 Jaeger/Tempo 看到完整 span 树（同一 trace_id），每条 zap 日志含该 trace_id，可按 trace_id 串联日志/事件/审计/DB/外部调用

#### Scenario: trace 跨微服务 RPC 传递
- **WHEN** orchestrator 通过 Connect/gRPC 调用 executor 服务
- **THEN** executor 收到的请求含 traceparent metadata，executor 的 span 是 orchestrator span 的子 span（非新 root trace）；要求 Connect `WithTrustRemote()` 开启内部互信

#### Scenario: trace 跨 DB 查询传递
- **WHEN** 业务逻辑在 traced ctx 内执行 `pool.Query(ctx, sql)`
- **THEN** otelpgx 自动建子 span，含 SQL 文本属性（可 trim），span 挂在同一 trace_id 下

#### Scenario: trace 跨第三方 HTTP 调用传递
- **WHEN** 平台调云 API/OIDC/SCM webhook（经 otelhttp 包装的 client）
- **THEN** 出站请求自动注入 `traceparent` 头，接收方（若支持 OTel）能延续同一 trace

#### Scenario: metrics 独立 Prometheus 管线
- **WHEN** Prometheus 抓取 `/metrics` 端点
- **THEN** 拿到 OTel SDK 经 Prometheus exporter 暴露的指标（不经过 trace 的 OTLP 管线，两条独立）

#### Scenario: trace 后端可配置
- **WHEN** 运维改 `OTEL_EXPORTER_OTLP_ENDPOINT` env 从 Jaeger 切到 Tempo
- **THEN** app 代码零改动，trace 自动导到新后端

### Requirement: 测试数据库决策（D42）
平台测试 SHALL 用 testcontainers-go + pgtestdb（真实 PostgreSQL），严禁 in-memory SQLite 替代。

#### Scenario: 测试用真 PG
- **WHEN** 运行 `go test ./server/core/store/...`
- **THEN** 测试连接 testcontainers 启动的真实 PostgreSQL，跑 sqlc 生成的 pgx 代码，不用 SQLite

### Requirement: 安全库决策（D43）
平台 SHALL 用 argon2id（密码哈希）+ golang-jwt/v5（JWT）+ zitadel/oidc（OIDC 客户端）。

#### Scenario: argon2id 密码哈希
- **WHEN** 用户设置密码
- **THEN** 平台用 argon2id 哈希存储（非 bcrypt、非 MD5），符合 2025 OWASP 首选

### Requirement: 时间抽象决策（D44）
平台 SHALL 定义 `Clock` interface（`Now() time.Time`），业务逻辑注入 Clock，所有 `time.Now()` 走 Clock。时间戳统一 UTC timestamptz。

#### Scenario: drift 检测可确定性测试
- **WHEN** 测试漂移检测的"上次检测时间 +24h 应触发"逻辑
- **THEN** 注入 FakeClock 推进时间，断言触发行为，不依赖真实 sleep

### Requirement: RPC 框架决策（D45）
平台 SHALL 用 Connect-RPC（`connectrpc.com/connect`）实现业务 RPC，`.proto` 是唯一真相源。一个 Connect handler 同时服务 gRPC（服务间）、gRPC-Web（前端 React）、Connect/JSON（aether CLI + curl）。Webhook 回调 + 外部系统对接 + 运维端点（/healthz、/metrics）用 gin（D34），两者挂同一 `http.ServeMux`。

#### Scenario: proto 唯一真相源
- **WHEN** 新增一个业务 RPC（如 `CatalogService.ListItems`）
- **THEN** 只在 `.proto` 定义一次，Connect 生成一个 handler 同时服务 gRPC/gRPC-Web/Connect-JSON 三个协议，不手写多套 handler

#### Scenario: 前端 gRPC-Web 无 Envoy
- **WHEN** React 前端（用 connect-es 客户端）调用业务 RPC
- **THEN** 直连 Connect handler（gRPC-Web 协议原生），无需 Envoy 代理；失败时 HTTP 状态码正确反映错误（非 200-on-error 陷阱）

#### Scenario: gin 与 Connect 共存
- **WHEN** 同一进程同时服务业务 RPC + Webhook 回调
- **THEN** Connect handler 挂 `/api/` 路径（业务 RPC），gin 挂 `/webhooks/` + `/healthz` + `/metrics`，两者在同一 `http.ServeMux` 共存，一进程一端口
